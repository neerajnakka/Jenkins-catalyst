Block 3 · Foundation

Snippet Generator & syntax tooling

Goal: stop memorising step syntax. Generate it, validate it, lint it — and iterate with Replay so you never wait on a Git push to find out a step is wrong.

3.1 The four tools built into every Jenkins

🔧 Snippet Generator

/pipeline-syntax/ — pick a step, fill a form, get the exact Groovy. For steps.

📐 Declarative Directive Generator

/directive-generator/ — same idea, but for sections like options, when, triggers, parameters.

📖 Global Variable Reference

/pipeline-syntax/globals — every built-in variable (env, currentBuild, params, scm) with real values from your own controller.

🔁 Replay

On any finished build: edit the Jenkinsfile in the browser and rerun instantly, without a commit.

🔗How to reach them From any job: click Pipeline Syntax in the left menu. Or go direct: http://<jenkins>:8080/pipeline-syntax/. They're always available on the controller, even before you create a job.

3.2 Using the Snippet Generator (do this once, properly)

  1. Sample Step ▾ → choose the step, e.g. sh: Shell Script. The form changes to match.
  2. Fill the fields — for sh you get Script, plus advanced options like returnStdout and returnStatus.
  3. Click Generate Groovy. Copy the output into your Jenkinsfile's steps block.
groovyOutput of the generator for a few common steps
// 1. sh  ->  Shell Script
sh 'npm ci'

//    ...with advanced options ticked:
sh label: 'install dependencies', returnStdout: true, script: 'npm ci'

// 2. git  ->  Git  (Block 4)
git branch: 'main', credentialsId: 'github-ssh', url: 'git@github.com:you/repo.git'

// 3. checkout  ->  Check out from version control  (modern form, Block 4)
checkout scmGit(branches: [[name: '*/main']],
                extensions: [],
                userRemoteConfigs: [[credentialsId: 'github-ssh',
                                     url: 'git@github.com:you/repo.git']])

// 4. withCredentials  ->  Bind credentials to variables  (Block 8)
withCredentials([usernamePassword(credentialsId: 'dockerhub',
                                  passwordVariable: 'DOCKER_PASS',
                                  usernameVariable: 'DOCKER_USER')]) {
    sh 'echo $DOCKER_USER'
}

// 5. junit  ->  Publish JUnit test result report  (Block 6)
junit testResults: 'reports/junit.xml', allowEmptyResults: true

// 6. archiveArtifacts  ->  Archive the artifacts  (Block 11)
archiveArtifacts artifacts: 'coverage/**', fingerprint: true

// 7. cleanWs  ->  Delete workspace when build is done  (Block 11)
cleanWs()
🎯The professional shortcut You will never remember checkout scmGit(...) by heart. Nobody does. What senior engineers remember is which steps exist and where to generate them. That's the skill. Use the generator for the exact syntax every single time.

3.3 Declarative Directive Generator — for blocks, not steps

When you need correct syntax for when, options, triggers, parameters or tools, use /directive-generator/. Choose the directive, fill the form, paste.

groovyGenerated declarative directives
// when: branch is main          (directive: when -> branch)
when {
    branch 'main'
}

// when: any of / all of / not   (directive: when -> allOf / anyOf / not)
when {
    allOf {
        branch 'main'
        expression { params.DEPLOY == true }
    }
}

// options: timeout + timestamps (directive: options -> timeout / timestamps)
options {
    timeout(time: 30, unit: 'MINUTES')
    timestamps()
}

// triggers: pollSCM             (directive: triggers -> pollSCM)
triggers {
    pollSCM('H/5 * * * *')
}

// parameters: choice            (directive: parameters -> choice)
parameters {
    choice choices: ['dev', 'qa', 'prod'], description: 'Target env', name: 'ENV'
}

3.4 Validate a Jenkinsfile without running it

Jenkins ships a REST endpoint that parses your Jenkinsfile and returns either "successfully validated" or the exact parse error. Wire it into your editor or a pre-commit hook.

bashscripts/validate-jenkinsfile.sh
#!/usr/bin/env bash
# Validate a Jenkinsfile against the controller WITHOUT triggering a build.
# Usage: ./scripts/validate-jenkinsfile.sh nodejs-app/Jenkinsfile
set -euo pipefail
JENKINS_URL="${JENKINS_URL:-http://localhost:8080}"
USER="${JENKINS_USER:?set JENKINS_USER}"
TOKEN="${JENKINS_TOKEN:?set JENKINS_TOKEN}"   # Manage Jenkins -> Users -> API Token
FILE="${1:?path to Jenkinsfile}"

CRUMB=$(curl -s -u "$USER:$TOKEN" "$JENKINS_URL/crumbIssuer/api/xml?xpath=concat(//crumbRequestField,\":\",//crumb)")

curl -s -u "$USER:$TOKEN" -H "$CRUMB" \
     -F "jenkinsfile=<$FILE" \
     "$JENKINS_URL/pipeline-model-converter/validate" | tee /tmp/validate.out

grep -q "successfully validated" /tmp/validate.out \
  && echo "✅ Jenkinsfile is valid" \
  || { echo "❌ Jenkinsfile has errors (see above)"; exit 1; }
⚠️Validation is syntax-only This endpoint checks that the pipeline parses. It does not check that your credentials exist, that the branch is real, or that npm will succeed. Syntax valid ≠ build green.

3.6 The debug loop I actually use

groovyThree tricks that save hours
// 1. Print everything the pipeline can see
sh 'env | sort'                       // shell environment
echo sh(script: 'printenv | sort', returnStdout: true)
echo "Params: ${params}"

// 3. Keep the workspace when a build fails, so you can inspect it

    failure { archiveArtifacts artifacts: '**/*.log', allowEmptyArchive: true }

3.8 💬 Interview Q&A

Q1How do you write a Jenkinsfile without memorising syntax?
I use the built-in Snippet Generator for steps and the Declarative Directive Generator for sections, validate with the pipeline-model-converter/validate REST endpoint, and iterate with Replay so I don't need a Git commit per attempt. What I do memorise is the catalogue of available steps.
Q2What is Replay and when is it useful?
Replay lets you edit the Jenkinsfile of a completed build directly in the browser and rerun it. It's ideal for debugging — you iterate in seconds without pushing commits. Once it's green you copy the final version back into the repo and commit.
Q3Someone says their Jenkinsfile "compiles" but the build fails. Explain.
Validation only proves the Groovy parses and the declarative structure is legal. Runtime problems — a missing credential ID, an unreachable branch, a failing npm ci — are discovered only when steps execute.

3.7 Under the hood — where the generator gets its list

Every Jenkins step is a Java class registered for discovery (@Extension + Describable with @DataBoundConstructor/@DataBoundSetter). The generator reads that metadata, renders a form, and serialises your inputs back to Groovy. Three consequences:

  • A step only appears if its plugin is installed. "No such DSL method" usually means a missing plugin, not bad syntax.
  • Not every step has a form. Older steps expose only raw parameters under Advanced.
  • Generated code is canonical. When unsure, generate — don't invent.

3.9 Editor & CLI tooling

bashLocal lint + a pre-commit hook
# Local Groovy lint (no Jenkins needed)

# Block broken syntax before it reaches CI

#!/usr/bin/env bash
set -e
for f in $(git diff --cached --name-only | grep -E 'Jenkinsfile$'); do
  echo "validating $f"
  ./scripts/validate-jenkinsfile.sh "$f"
done

3.10 More interview Q&A

Q4How do you lint a Jenkinsfile in CI itself?
I run npm-groovy-lint plus the Jenkins /pipeline-model-converter/validate endpoint in a lightweight "pipeline lint" job and in a pre-commit hook, so broken syntax is caught before it ever consumes an executor.
Q5Where do you find the list of available environment variables?
/pipeline-syntax/globals — the Global Variable Reference, which renders the real values from my controller including env, currentBuild, params, docker and scm.
Q6A step you generated isn't recognised at runtime. Why?
The generator lists steps from plugins installed on the controller that rendered it. If the plugin is missing where the pipeline runs, or was updated and the step renamed, you get "No such DSL method". I verify the plugin in Manage Jenkins → Plugins and check the changelog for renames.
