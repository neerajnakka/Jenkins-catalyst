Block 8 · Real engineering

Credentials & secrets management

Goal: never write a secret in a Jenkinsfile again — and be able to explain to an interviewer exactly how Jenkins stores, injects and masks them.

8.1 How Jenkins stores credentials

Credentials live in the credentials store at $JENKINS_HOME/secrets/, encrypted with a master key (secrets/master.key + secrets/hudson.util.Secret). Pipelines never see the raw value in source — they reference an ID and Jenkins injects the value at runtime.

⚠️The disaster rule If you lose master.key, every stored credential becomes permanently unreadable. Back it up separately from the rest of JENKINS_HOME — ideally outside the server. (Block 22.)

8.3 withCredentials — the injection block

groovyAll the binding forms you'll need
// 1. Username + password  ->  two env vars
withCredentials([usernamePassword(credentialsId: 'dockerhub-creds',
                                  usernameVariable: 'REG_USER',
                                  passwordVariable: 'REG_PASS')]) {
    sh 'docker login -u "$REG_USER" -p "$REG_PASS"'
}

// 2. Secret text  ->  one env var
withCredentials([string(credentialsId: 'sonar-token', variable: 'SONAR_TOKEN')]) {
    sh 'sonar-scanner -Dsonar.login=$SONAR_TOKEN'
}

// 3. Secret file  ->  env var holding a PATH to a temp copy (deleted afterwards)
withCredentials([file(credentialsId: 'kubeconfig', variable: 'KUBECONFIG')]) {
    sh 'kubectl --kubeconfig=$KUBECONFIG get pods'
}

// 4. SSH key  ->  sshagent wrapper (safer than writing the key to disk)
sshagent(['deploy-key']) {
    sh 'ssh -o StrictHostKeyChecking=no ubuntu@host "docker pull app && docker compose up -d"'
}

// 5. Several at once
withCredentials([
    usernamePassword(credentialsId: 'dockerhub-creds', usernameVariable: 'U', passwordVariable: 'P'),
    string(credentialsId: 'slack-token', variable: 'SLACK')
]) {
    sh 'echo "using $U and $SLACK"'
}

8.4 Masking — what Jenkins protects, and what it doesn't

Jenkins replaces any occurrence of a bound secret's value in the console log with ****. But masking is string matching, not magic.

groovyMasking behaviour — and the holes
withCredentials([string(credentialsId: 'my-token', variable: 'TOK')]) {
    sh 'echo $TOK'            // ✅ printed as ****
    sh 'echo "$TOK" | base64' // ❌ LEAKS -- base64 no longer matches the raw string
    sh 'echo ${TOK:0:4}'      // ❌ LEAKS a substring
    sh 'echo $TOK > out.txt'  // ⚠️  secret now sits in the workspace -> archive it and it's public
    sh 'set +x; echo done'    // ✅ disable shell tracing around sensitive commands
}
🚨Secrets hygiene rules I follow
  • One credential per purpose per environment — never one shared secret.
  • Name IDs predictably: <system>-<env>-<kind> e.g. dockerhub-prod-push.
  • Never echo a secret, even "just to debug" — and never write one to the workspace.
  • Rotate on a schedule and immediately after anyone with access leaves.
  • Prefer short-lived tokens (OIDC, IAM roles) over long-lived passwords where possible.

8.6 ✍️ Jenkinsfiles v8 — secrets wired in

groovynodejs-app/Jenkinsfile — v8 (secrets)
pipeline {
    agent any
    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment {
        APP_NAME = 'nodejs-app'
        // NOTE: no secrets here -- only IDs and non-sensitive config
        REGISTRY_CREDENTIALS_ID = 'dockerhub-creds'
    }

    stages {
        stage('Checkout') { steps { dir(APP_NAME) { checkout scmGit(
                branches: [[name: '*/main']], extensions: [cleanBeforeCheckout()],
                userRemoteConfigs: [[credentialsId: 'github-ssh',
                    url: 'git@github.com:<you>/jenkins-zero-to-hero.git']]) } } }

        stage('Build') { steps { dir(APP_NAME) { sh 'npm ci' } } }
        stage('Test')  { steps { dir(APP_NAME) { sh 'npm run test:junit' } } }

        stage('Verify registry access') {          // proving the credential works
            steps {
                withCredentials([usernamePassword(
                        credentialsId: env.REGISTRY_CREDENTIALS_ID,
                        usernameVariable: 'REG_USER',
                        passwordVariable: 'REG_PASS')]) {
                    sh '''
                        set +x                          # never trace the login command
                        echo "$REG_PASS" | docker login -u "$REG_USER" --password-stdin
                        docker logout
                    '''
                    echo "Logged in as $REG_USER"        // username is not secret
                }
            }
        }
    }

    post {
        always { dir(APP_NAME) { junit testResults: 'reports/junit.xml', allowEmptyResults: true } }
        cleanup { sh 'docker logout || true' }
    }
}

8.8 💬 Interview Q&A

Q1How do you manage secrets in Jenkins?
In the credentials store, encrypted at rest with the master key, referenced by ID. I bind them at runtime with withCredentials (or the credentials() helper in environment), so the value only exists in the process environment for the duration of the block and is masked in the console. Nothing sensitive goes into the Jenkinsfile or into job parameters.
Q2How does Jenkins mask secrets, and what are the limits?
It pattern-matches the secret's literal value in console output and replaces it with ****. It only works for values Jenkins knows it bound — so transforming the secret (base64, substrings, writing it to a file) defeats masking. That's why I avoid transforming secrets and use set +x around sensitive shell commands.
Q3What happens if you lose master.key?
Every credential becomes permanently undecryptable — you must recreate them all. So I back up master.key separately from JENKINS_HOME and treat it as the crown jewels.
Q4How would you give team A access to their secrets but not team B's?
Put team A's jobs in a Jenkins folder, store the credentials in that folder's domain, and grant the team's role permissions only on that folder (Role Strategy plugin, Block 12). Credentials are then invisible and unusable outside it.

8.9 Under the hood — how credentials are protected

  1. Storage. Credentials are stored in $JENKINS_HOME/credentials.xml (metadata) with secret values encrypted using the key derived from secrets/master.key and secrets/hudson.util.Secret.
  2. Reference. A pipeline names an ID. At runtime the Credentials Provider API resolves that ID to an object — and access can be restricted by folder/domain.
  3. Binding. withCredentials writes the value into the environment of the steps inside it (or a temp file for file()), then removes it.
  4. Masking. Jenkins registers the plaintext value with the log filter, so any occurrence in console output is replaced with ****.
🚨What masking does NOT cover
  • Transformed values: base64, substrings, reversed, URL-encoded.
  • Values written into files that you then archiveArtifacts — the file is downloadable by anyone with read access.
  • Values inside a stash, or baked into a Docker image layer.
  • Values printed by a tool that buffers output differently (rare, but real with some CLIs).

8.11 Lab — see masking work, then defeat it

🧪Lab 8.1 · Prove it yourself
groovyRun this once, then read the console output carefully
withCredentials([string(credentialsId: 'sonar-token', variable: 'SECRET')]) {
    sh 'echo "raw      : $SECRET"'              // masked  -> raw      : ****
    sh 'echo "base64   : $(echo -n $SECRET | base64)"'   // LEAKED (transformed)
    sh 'echo "substring: ${SECRET:0:4}"'        // LEAKED (partial)
    sh 'echo "$SECRET" > secret.txt'            // written to the workspace!
}
// afterwards:
sh 'cat secret.txt'                             // masked here too — but the FILE is archived below
archiveArtifacts artifacts: 'secret.txt'        // anyone with read access can download it
Takeaway: masking protects the console, not the artifact store. Never write a secret to the workspace, and never archive a file that contained one.

8.12 Creating credentials from code (JCasC / Groovy)

groovyScript Console — add credentials programmatically (idempotent)
import com.cloudbees.plugins.credentials.*
import com.cloudbees.plugins.credentials.common.*
import com.cloudbees.plugins.credentials.domains.*
import com.cloudbees.plugins.credentials.impl.*
import org.jenkinsci.plugins.plaincredentials.impl.*
import hudson.util.Secret

def store = Jenkins.instance.getExtensionList(
        'com.cloudbees.plugins.credentials.SystemCredentialsProvider')[0].getStore()
def domain = Domain.global()

def addIfMissing(id, cred) {
    if (store.getCredentials(domain).any { it.id == id }) {
        println "exists: ${id}"
    } else {
        store.addCredentials(domain, cred); println "added: ${id}"
    }
}

addIfMissing('dockerhub-creds',
    new UsernamePasswordCredentialsImpl(CredentialsScope.GLOBAL, 'dockerhub-creds',
        'Docker Hub push token', 'your-user', 'dckr_pat_xxxxxxxxxxxx'))

addIfMissing('sonar-token',
    new StringCredentialsImpl(CredentialsScope.GLOBAL, 'sonar-token',
        'SonarQube analysis token', Secret.fromString('squ_xxxxxxxxxxxx')))
📌Prefer JCasC for this Hard-coding secrets in a script is exactly what we're trying to avoid. In practice I put credentials in jenkins.yaml with values injected from environment variables or a secret manager (see Block 22), and only use the script console for one-off recovery.

8.13 More interview Q&A

Q5How would you migrate secrets from Jenkins to a vault (HashiCorp Vault / AWS Secrets Manager)?
Install the matching credentials provider plugin so the vault appears as another credentials provider — pipelines keep using credentialsId and nothing in the Jenkinsfile changes. Then rotate each secret, move it to the vault, and delete the local copy. I'd do it incrementally per team to keep the blast radius small.
Q6What is a credentials domain?
A scope within the credentials store. The global domain is visible everywhere; folder domains are visible only to items in that folder. Combined with folder-scoped roles, it's how you make secrets physically unreachable by other teams.
Q7Can a malicious Jenkinsfile read credentials?
Yes, if it can run on the controller or use a credential in scope — which is exactly why Jenkinsfiles are code-reviewed, why shared libraries are access-controlled, and why credentials should be folder-scoped and least-privilege. On untrusted branches I restrict which credentials are available to that job.
Q8How do you rotate a credential without downtime?
Create the new credential with a new ID, update the pipeline to read the new ID, deploy, verify, then delete the old one and revoke it at the provider. Having the ID in the Jenkinsfile (not the value) is what makes this a config change instead of an incident.
