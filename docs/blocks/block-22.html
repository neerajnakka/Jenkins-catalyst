Backup, upgrade & maintenance

Goal: be the person who can restore Jenkins at 3 a.m. — and who can upgrade it without an outage. Operations knowledge is what turns a pipeline author into a platform engineer.

22.2 A backup script you can cron

bashscripts/jenkins-backup.sh
#!/usr/bin/env bash
# Backs up the parts of JENKINS_HOME that matter, and nothing else.
set -euo pipefail

JENKINS_HOME="${JENKINS_HOME:-/var/lib/jenkins}"
BACKUP_DIR="${BACKUP_DIR:-/var/backups/jenkins}"
RETENTION_DAYS="${RETENTION_DAYS:-14}"
STAMP=$(date +%Y%m%d-%H%M%S)
OUT="${BACKUP_DIR}/jenkins-${STAMP}.tar.gz"

mkdir -p "$BACKUP_DIR"

# Quiesce: stop new builds while we copy, so nothing changes mid-backup
sudo systemctl stop jenkins

tar --exclude='jobs/*/builds/*/archive' \
    --exclude='jobs/*/workspace*' \
    --exclude='workspace/*' \
    --exclude='caches/*' \
    --exclude='logs/*' \
    --exclude='tools/*' \
    -czf "$OUT" -C "$JENKINS_HOME" .

sudo systemctl start jenkins

# The master key goes to a SEPARATE, more restricted location
sudo cp "$JENKINS_HOME/secrets/master.key" "${BACKUP_DIR}/master.key-${STAMP}"
sudo chmod 600 "${BACKUP_DIR}/master.key-${STAMP}"

find "$BACKUP_DIR" -name 'jenkins-*.tar.gz' -mtime +$RETENTION_DAYS -delete
echo "Backup written: $OUT ($(du -h "$OUT" | cut -f1))"
cronNightly at 02:15
15 2 * * * /home/ubuntu/jenkins-zero-to-hero/scripts/jenkins-backup.sh >> /var/log/jenkins-backup.log 2>&1
☁️Off-box copies A backup on the same disk as Jenkins is not a backup. Sync to S3 afterwards: aws s3 sync /var/backups/jenkins s3://your-bucket/jenkins/ --storage-class STANDARD_IA, and turn on versioning + a lifecycle rule. The ThinBackup plugin can do all of this declaratively if you prefer UI-driven backups.

22.3 Configuration as Code (JCasC) — the modern approach

Instead of backing up XML and hoping, describe your controller in YAML. Install Configuration as Code (configuration-as-code), then Manage Jenkins → System → Configuration as Code:

yamljenkins/jenkins.yaml (JCasC)
jenkins:
  systemMessage: "Managed by JCasC - do not edit by hand"
  numExecutors: 0                     # controller runs no builds
  securityRealm:
    local:
      users:
        - id: "admin"
          password: "${JENKINS_ADMIN_PASSWORD}"     # from an env var / secret
  authorizationStrategy:
    roleBased:
      roles:
        global:
          - name: "admin"
            permissions: ["Overall/Administer"]
            assignments: ["admin"]
  nodes:
    - permanent:
        name: "linux-1"
        remoteFS: "/home/jenkins/agent"
        numExecutors: 2
        labelString: "linux docker node20"

tool:
  git:
    installations:
      - name: "Default"
        home: "git"

credentials:
  system:
    domainCredentials:
      - credentials:
          - usernamePassword:
              id: "dockerhub-creds"
              username: "your-user"
              password: "${DOCKERHUB_TOKEN}"        # injected, never in Git

unclassified:
  sonarGlobalConfiguration:
    installations:
      - name: "sonar"
        serverUrl: "http://localhost:9000"
🚀Why JCasC is a career multiplier Your controller becomes rebuildable from a file: new server, apply YAML, done. It's reviewable in PRs, testable, and the modern standard (often combined with the Jenkins Operator on Kubernetes). Mentioning "I manage Jenkins with JCasC + a plugin manifest" instantly signals platform-level thinking.

22.5 Maintenance with the Script Console

groovyManage Jenkins → Script Console (run with care)
// 1. Delete builds older than 30 days from every job
import jenkins.model.Jenkins
import java.util.Calendar

def cutoff = Calendar.getInstance()
cutoff.add(Calendar.DAY_OF_MONTH, -30)

Jenkins.instance.allItems(hudson.model.Job).each { job ->
  job.builds.findAll { it.time < cutoff.time }.each { build ->
    println "Deleting ${job.fullName} #${build.number}"
    build.delete()
  }
}

// 2. Find jobs that have never been built
Jenkins.instance.allItems(hudson.model.Job).findAll { it.lastBuild == null }
        .each { println "Never built: ${it.fullName}" }

// 3. Which jobs are taking the longest?
Jenkins.instance.allItems(hudson.model.Job).collect { job ->
  def b = job.lastBuild
  [name: job.fullName, avg: job.builds.collect { it.duration }.with { it ? it.sum()/it.size() : 0 }]
}.sort { -it.avg }.take(20).each { println "${it.name}: ${(it.avg/1000 as int)}s" }

// 4. Reset a forgotten admin password
def u = hudson.model.User.get('admin')
u.addProperty(hudson.security.HudsonPrivateSecurityRealm.Details.fromPlainPassword('NewTempPass123!'))
u.save()
🚨The Script Console is root on Jenkins It executes Groovy with full controller privileges — including reading every credential. Restrict it with RBAC, never leave it open to non-admins, and always test scripts on a non-production controller first. Everything you run here is permanent.

22.6 The upgrade procedure

  1. Read the changelog and the upgrade guide for your LTS line (e.g. 2.440 → 2.452). Note Java version requirements.
  2. Back up JENKINS_HOME and master.key. Verify the archive opens.
  3. Update plugins first, on the old Jenkins version, and restart. Plugin incompatibilities are far more common than core problems.
  4. Upgrade core: sudo apt update && sudo apt install jenkins (or swap the WAR / container image).
  5. Restart and verify: plugins loaded, agents reconnected, one pipeline from each app runs green.
  6. Rollback plan: keep the previous WAR/package and the backup; restore = stop, restore files, start.
bashFind your version and check what's installed
java -jar /usr/share/jenkins/jenkins.war --version     # core version
# or: Manage Jenkins -> About Jenkins

# List installed plugins with versions (great for diffs)
curl -s -u user:$TOKEN "http://localhost:8080/pluginManager/api/json?depth=1" \
  | jq -r '.plugins[] | "\(.shortName) \(.version)"' | sort

22.7 ✅ Checklist

  • Nightly backup job runs and you have restored from it at least once (untested backups don't count).
  • master.key is backed up separately.
  • Discard-old-builds + workspace cleanup + Docker pruning are all in place.
  • You can describe the six-step upgrade procedure without notes.
  • You have written (or at least read) a JCasC file.

22.8 💬 Interview Q&A

Q1How do you back up Jenkins?
I back up JENKINS_HOME excluding workspaces, build archives and caches, with Jenkins stopped briefly for consistency. secrets/master.key is copied separately and tightly restricted, because without it credentials can never be decrypted. Copies go off-box to S3 with versioning, and I test the restore regularly — an untested backup isn't a backup.
Q2What's your upgrade process?
Read the changelog and Java requirements, verify the backup, update plugins first (they cause most breakage), then upgrade core, restart, and smoke-test one pipeline per project. I keep the previous package and the backup so rollback is a file restore away.
Q3Jenkins is slow. Where do you look?
Disk first (workspaces, Docker layers, build history), then the queue and executor usage, then memory and GC on the controller, then slow plugins (especially SCM scanning and heavy publishers). I add buildDiscarder, per-stage timeouts and the Timestamper plugin to find the specific slow stage.
Q4What is JCasC and why use it?
Jenkins Configuration as Code: the entire controller configuration — security, tools, agents, credentials — described in YAML and loaded at startup. It makes the controller reproducible, reviewable in Git, and trivial to recreate after a disaster, which is a big step up from restoring XML blobs.
Q5How would you rebuild Jenkins from scratch after losing the server?
Provision a box with the install script, restore the JENKINS_HOME backup (or apply the JCasC YAML plus the plugin manifest), restore master.key, start Jenkins, verify agents reconnect, and run one pipeline per project. Because Jenkinsfiles live in Git, no pipeline logic was ever lost.

22.8 Under the hood — JCasC and immutability

Jenkins Configuration as Code reads a YAML file at start-up and reconciles it with the live configuration. Its value is not "config in a file" — it's that configuration becomes reviewable, diffable and reproducible.

yamljenkins.yaml — a compact but real baseline
jenkins:
  systemMessage: "Managed by JCasC - manual changes will be reverted on restart"
  numExecutors: 0                       # never build on the controller
  labelString: "built-in"
  mode: EXCLUSIVE
  securityRealm:
    local:
      allowsSignup: false
      users:
        - id: "admin"
          password: "${ADMIN_PASSWORD}"   # injected from the environment
  authorizationStrategy:
    roleBased:
      roles:
        global:
          - name: "admin"
            permissions:
              - "Overall/Administer"
            assignments:
              - "admin"
  nodes:
    - permanent:
        name: "linux-1"
        remoteFS: "/home/jenkins/agent"
        numExecutors: 4
        labelString: "linux docker"
        launcher:
          ssh:
            host: "10.0.1.20"
            credentialsId: "agent-ssh"
  tool:
    git:
      installations:
        - name: "Default"
          home: "git"
security:
  queueItemAuthenticator:
    authenticators:
      - global:
          strategy: "triggeringUsersAuthorizationStrategy"
credentials:
  system:
    domainCredentials:
      - credentials:
          - usernamePassword:
              id: "dockerhub-creds"
              username: "${DOCKER_USER}"
              password: "${DOCKER_TOKEN}"
              description: "Docker Hub push account"
💡Secrets in JCasC Never commit real secrets: reference environment variables or files with ${VAR} and supply them from your secret manager at boot. Manage Credentials is for runtime use; JCasC bootstraps the config around them.

22.9 Backup and disaster recovery

WhatWhy it mattersHow often
$JENKINS_HOME job configsThe jobs themselvesDaily
credentials.xml + master.key / hudson.util.SecretWithout the key, credentials cannot be decrypted — the backup is uselessDaily, encrypted, stored separately
Plugin listReproducible installOn change
Build history & artifactsCompliance, debuggingWeekly (or external storage only)
🚨The backup trap Most teams back up $JENKINS_HOME and forget master.key, then discover during a restore that every credential is unreadable. Back up the key, encrypted, in a different location, and test a restore at least once.
bashMinimal, correct backup (ThinBackup-style, tar based)
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F-%H%M)
DEST=/backup/jenkins/$STAMP
mkdir -p "$DEST"

systemctl stop jenkins
tar --exclude='*/workspace/*' \
    --exclude='*/builds/*/archive/*' \
    --exclude='caches' --exclude='logs' \
    -czf "$DEST/jenkins-home.tgz" /var/lib/jenkins

# The decryption key -- without it the backup CANNOT restore credentials
cp /var/lib/jenkins/secrets/master.key "$DEST/" 2>/dev/null || true
cp /var/lib/jenkins/secrets/hudson.util.Secret "$DEST/" 2>/dev/null || true
systemctl start jenkins

# Retention
find /backup/jenkins -maxdepth 1 -mtime +14 -type d -exec rm -rf {} +
echo "backup complete: $DEST"

22.10 Lab — rebuild Jenkins from nothing

🧪Lab 22.1 · Prove you can recover This is the exercise that turns "I configured Jenkins" into "I can operate Jenkins". Do it once, on a spare EC2 instance.
  1. sudo systemctl stop jenkins and move /var/lib/jenkins aside.
  2. Install Jenkins fresh with jenkins/ec2-install.sh.
  3. Restore jenkins.yaml → start → confirm the controller comes back with your agents, users and roles.
  4. Restore credentials.xml plus the key files → confirm a pipeline can still push to Docker Hub.
  5. Point a Multibranch job at your GitHub repo and press Scan Repository Now — all branches reappear without a single manual click.
Time it. If recovery takes more than about 30 minutes, automate more of it.

22.12 More interview Q&A

Q6How do you manage Jenkins at scale?
Configuration as Code for the controller, a pinned plugin list (or a pre-baked image), agents provisioned from images or Kubernetes, and pipelines plus shared libraries in Git. No manual configuration, no snowflake controller — I should be able to delete it and have it back within the hour.
Q7How do you test a Jenkins upgrade safely?
Take a backup, restore it onto a staging controller, run a representative subset of jobs against it, and only then upgrade production — with a rollback path (AMI/snapshot) and a maintenance window. I read the plugin compatibility notes first, because plugin breakage is the usual failure mode, not Jenkins itself.
Q8How do you back up and restore Jenkins?
ThinBackup or a scripted tar of $JENKINS_HOME excluding workspaces and archived artifacts, including master.key so credentials remain decryptable, stored off the controller with retention. Restore is rehearsed, not assumed.
Q9How do you secure the controller itself?
HTTPS with a real certificate, no anonymous access, matrix or role-based authorisation, CSRF protection on, agent-to-controller access control, zero executors on the built-in node, secrets only in the credential store, and the controller isolated so build agents can't reach it except through the remoting channel.
Q10How do you monitor Jenkins health?
Prometheus metrics for queue depth, executor usage and build durations; alerts on agent offline, disk usage and queue backlog; plus trends for flaky tests and security findings. The goal is to notice degradation before developers start complaining.
