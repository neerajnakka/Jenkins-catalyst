Webhooks & automatic triggers

Goal: push code and see Jenkins start building within seconds — no human, no polling. Then understand every other trigger so you can pick the right one.

10.1 Every way a build can start

🧠Webhook vs Polling — the classic interview question Polling = Jenkins asks "anything new?" every few minutes: always works (even behind NAT/firewall), but wastes API calls and delays builds. Webhooks = Git tells Jenkins the instant something happens: fast and efficient, but Jenkins must be reachable by GitHub. Rule of thumb: webhooks in production, polling as the fallback when the network forbids webhooks.

10.2 Setting up the GitHub webhook

  1. Install the GitHub plugin (Manage Jenkins → Plugins → GitHub, id github). It creates the /github-webhook/ endpoint.
  2. Enable the trigger in the job: job → Configure → Build Triggers → tick GitHub hook trigger for GITScm polling. (For Multibranch: tick Scan by webhook and set a trigger token.)
  3. Create the webhook on GitHub: Repo → Settings → Webhooks → Add webhook:
    Payload URL: http://<JENKINS-IP>:8080/github-webhook/ (note the trailing slash)
    Content type: application/json · Secret: optional but recommended
    Events: Just the push event (add Pull requests for Block 15)
  4. Test it: push a commit. In GitHub → Webhooks → Recent Deliveries you should see a green 200. In Jenkins a new build appears within seconds.
groovytriggers {} in the Jenkinsfile — everything declarative
pipeline {
    agent any

    triggers {
        pollSCM('H/5 * * * *')          // poll every 5 minutes (H = hashed/staggered)
        cron('H 2 * * *')               // nightly at ~02:00, spread load with H
        // githubPush()                 // requires the GitHub plugin + job trigger ticked
        // upstream(upstreamProjects: 'library-pipeline', threshold: hudson.model.Result.SUCCESS)
    }
    ...
}
⚠️The triggers block doesn't create the webhook triggers { pollSCM(...) } only updates the job's internal configuration when the Jenkinsfile runs. The GitHub-side webhook must be created once, by hand (or by the GitHub Branch Source plugin in Block 15). If pushes do nothing, check GitHub → Recent Deliveries first.

10.3 Cron syntax, Jenkins style

cronMINUTE HOUR DAY-OF-MONTH MONTH DAY-OF-WEEK
H/15 * * * *     every 15 minutes
H 2 * * *        once a day around 02:00
H 2 * * 1-5      weekdays around 02:00
H(0-30) 9 * * *  between 09:00 and 09:30
0 3 1 * *        the 1st of the month at 03:00 sharp
💡Always use H (hash) H is a pseudo-random value derived from the job name. Ten jobs with 0 2 * * * all fire at exactly 02:00 and stampede the controller; H 2 * * * spreads them across the hour. Using H is a small habit that marks you as someone who has run Jenkins at scale.

10.4 Triggering from outside (API / remote token)

bashRemote trigger with an auth token
# 1. In the job: Build Triggers -> "Trigger builds remotely" -> Token: BUILD_ME
# 2. Create an API token: Manage Jenkins -> your user -> Security -> API Token
# 3. Fetch a CSRF crumb, then POST:
CRUMB=$(curl -s -u user:$TOKEN "$JENKINS_URL/crumbIssuer/api/xml?xpath=concat(//crumbRequestField,\":\",//crumb)")
curl -X POST -u user:$TOKEN -H "$CRUMB" \
     "$JENKINS_URL/job/nodejs-app/build?token=BUILD_ME"

# ...with parameters:
curl -X POST -u user:$TOKEN -H "$CRUMB" \
     "$JENKINS_URL/job/nodejs-app/buildWithParameters?token=BUILD_ME&ENV=qa&RUN_TESTS=true"

10.8 💬 Interview Q&A

Q1Webhook vs SCM polling — which do you choose and why?
Webhooks: instant, no wasted API calls, and they also deliver PR events. The requirement is that GitHub can reach Jenkins. If the controller is behind a firewall or on a private network, polling is the pragmatic fallback — I'd poll every 5–10 minutes and accept the latency.
Q2A webhook is configured but nothing happens. How do you debug?
Start at GitHub → Webhooks → Recent Deliveries: a 200 means GitHub delivered it, so the problem is on the Jenkins side (job trigger not ticked, wrong branch filter, multibranch scan not configured). A 403 is usually a missing CSRF crumb; a timeout means the security group blocks GitHub. Then check /var/log/jenkins/jenkins.log and the job's Git polling log.
Q3What is the H in H/5 * * * *?
A hash of the job name that Jenkins substitutes for a stable pseudo-random number. It staggers schedules so hundreds of jobs don't fire on the same minute and stampede the controller.
Q4How do you start pipeline B when pipeline A finishes?
With the build job: step, passing parameters and choosing wait/propagate. Or declaratively with triggers { upstream(...) }. I set propagate: false when I want to handle the downstream result myself (for example to mark the build unstable instead of failed).

10.10 Under the hood — what a webhook delivery actually is

GitHub sends an HTTP POST to /github-webhook/ with a JSON body describing the event and an X-GitHub-Event header (push, pull_request, …). The GitHub plugin:

  1. Verifies the payload (optionally with the HMAC secret you configured — always set it).
  2. Finds jobs whose SCM URL matches the repository.
  3. For classic jobs, triggers a build if GitHub hook trigger for GITScm polling is enabled; for Multibranch, triggers a repository scan.
  4. Returns 200. Any other code shows up red in GitHub's Recent Deliveries.
bashReplay a delivery by hand (great for debugging)
# Take the payload from GitHub -> Webhooks -> Recent Deliveries -> Request
curl -X POST http://<jenkins>:8080/github-webhook/ \
     -H "Content-Type: application/json" \
     -H "X-GitHub-Event: push" \
     -H "X-Hub-Signature-256: sha256=..." \
     --data @payload.json -i

10.12 Lab — webhook forensics

🧪Lab 10.1 · Diagnose a webhook that does nothing Work top-down; stop at the first failure.
bashThe decision tree
# 1. Did GitHub deliver it?  (GitHub -> Webhooks -> Recent Deliveries)
#      200/204  -> Jenkins received it: problem is inside Jenkins
#      302      -> missing trailing slash on /github-webhook/
#      403      -> CSRF crumb missing, or anonymous lacks Job/Build
#      timeout  -> security group / firewall blocks GitHub

# 2. Can GitHub reach you at all?
curl -sS -o /dev/null -w "%{http_code}\n" http://<jenkins>:8080/github-webhook/
# (a bare GET normally returns 405 or 302 -- that means you ARE reachable)

# 3. Is the Jenkins-side trigger enabled?
#    job -> Configure -> Build Triggers -> [x] GitHub hook trigger for GITScm polling

# 4. Does the repo URL in the job match the payload's repository URL exactly?
#    (ssh vs https, trailing .git, case) -- they must match

# 5. Still nothing? Watch the log while you push:
sudo tail -f /var/log/jenkins/jenkins.log | grep -i github

10.14 More interview Q&A

Q5How do you secure a webhook endpoint?
Set the webhook secret so Jenkins can verify the HMAC signature, allow only GitHub's IP ranges at the firewall (or put a proxy in front), use HTTPS, and grant the minimal permission needed to trigger builds rather than admin rights.
Q6Push events fire builds, but PR events do nothing. What's missing?
The webhook must subscribe to Pull requests, and the Multibranch job needs a PR discovery behaviour configured (e.g. "Discover pull requests from origin"). With those, Jenkins builds PR-<n> and exposes CHANGE_ID.
Q7How do you avoid a storm of builds when 10 commits are pushed quickly?
Enable the quiet period (a few seconds) so Jenkins coalesces changes, and use disableConcurrentBuilds(abortPrevious:true) on expensive jobs. For very busy repos, a branch-level strategy that builds only the latest commit is the answer.
Q8How do you rebuild only what a commit affected in a multi-service repo?
Compute changed paths from the changelog or use path filters in the branch source, then gate each service's stages with when. At scale I'd split into per-service jobs so the trigger itself is already scoped.
