Block 16 · DevSecOps & scale

DevSecOps part 1 — SAST with SonarQube

Goal: automatically analyse code quality and security on every commit, and have a quality gate decide whether the build may proceed. This is the block that turns a CI engineer into a DevSecOps engineer.

16.1 What SAST actually is

🔬 SAST — Static Application Security Testing

Reads your source code without running it. Finds SQL injection patterns, hardcoded secrets, null dereferences, and code smells. Runs in seconds, early in CI.

🎯 Quality Gate

A pass/fail policy: "coverage ≥ 70%", "zero blocker issues", "duplication < 3%". The gate is what makes scanning matter — a report nobody enforces is decoration.

🧭Where the pieces sit in the pipeline SAST (Block 16) → source code · SCA (Block 17) → your dependencies · Container + DAST (Block 18) → the built image and the running app. Together they cover the three places bugs and vulnerabilities hide.

  1. Create a project in SonarQube: Projects → Create Project → Manually → project key must match sonar.projectKey in your sonar-project.properties → nodejs-app / python-app.
  2. Generate a token: My Account → Security → name jenkins → Generate. Copy it once.
  3. Store it in Jenkins: Credentials → Secret text → ID sonar-token.
  4. Configure the server: Manage Jenkins → System → SonarQube servers → Add: Name sonar, Server URL http://<EC2-IP>:9000, Server authentication token → sonar-token.
  5. Configure the scanner tool: Manage Jenkins → Tools → SonarQube Scanner installations → Add sonar-scanner → Install automatically (latest).

16.3 The Jenkins pipeline steps

groovywithSonarQubeEnv + waitForQualityGate
stage('SonarQube Analysis') {
    agent { label 'linux' }
    steps {
        withSonarQubeEnv('sonar') {          // injects SONAR_HOST_URL + SONAR_AUTH_TOKEN
            sh '''
                sonar-scanner \
                  -Dsonar.projectKey=nodejs-app \
                  -Dsonar.sources=src \
                  -Dsonar.tests=tests \
                  -Dsonar.javascript.lcov.reportPaths=coverage/lcov.info
            '''
        }
    }
}

stage('Quality Gate') {
    agent { label 'linux' }
    steps {
        // SonarQube analyses asynchronously -> wait for the webhook callback
        timeout(time: 5, unit: 'MINUTES') {
            script {
                def qg = waitForQualityGate()
                echo "Quality gate status: ${qg.status}"
                if (qg.status != 'OK') {
                    error "SonarQube quality gate failed: ${qg.status}"
                }
            }
        }
    }
}
🚨The #1 SonarQube-in-Jenkins mistake waitForQualityGate() waits for SonarQube to call Jenkins back. If you don't create that webhook, the step hangs until your timeout expires. Add it in SonarQube:
uiSonarQube → Administration → Configuration → Webhooks
Name : jenkins
URL  : http://<JENKINS-IP>:8080/sonarqube-webhook/
Note the path is /sonarqube-webhook/ (provided by the SonarQube Scanner plugin), not /github-webhook/.

16.5 Fail fast — or warn only?

ApproachCodeUse when
Hard gateerror "gate failed"Release branches, mature codebase
Soft gatecatchError(buildResult:'UNSTABLE', stageResult:'FAILURE')Introducing scanning to a legacy repo — don't block the team on day one
Report onlyNo gate step, dashboard onlyInitial rollout / visibility phase
📈How to roll out scanning without being hated Week 1: report only, publish the dashboard. Week 2: soft gate (unstable) so people see yellow. Week 3+: hard gate on new code only — SonarQube's "new code" period means you never inherit a decade of technical debt as a CI blocker, you just refuse to add to it. That nuance is a strong interview answer.

16.7 💬 Interview Q&A

Q1How do you integrate SonarQube with Jenkins?
Install the SonarQube Scanner plugin, configure the server and its token credential, and add a stage wrapping sonar-scanner in withSonarQubeEnv('sonar'). Then a second stage calls waitForQualityGate() inside a timeout, which pauses until SonarQube posts the gate result back to /sonarqube-webhook/. Non-OK status fails the build.
Q2Why does waitForQualityGate hang?
Because SonarQube analyses asynchronously and notifies Jenkins via a webhook. If the webhook isn't configured (or Jenkins isn't reachable from SonarQube), the step waits until the timeout. Wrapping it in timeout() turns that into a clean failure instead of a stuck build.
Q3How do you introduce quality gates to a legacy codebase with thousands of issues?
Apply the gate to new code only — SonarQube's new-code period. Existing debt stays visible on the dashboard but doesn't block delivery, while every new line must be clean. Debt then shrinks naturally instead of blocking the team.
Q4SAST vs SCA vs DAST?
SAST analyses my own source without executing it (SonarQube, Bandit, ESLint security rules). SCA analyses third-party dependencies for known CVEs (npm audit, pip-audit, OWASP Dependency-Check, Trivy fs). DAST attacks the running application over HTTP (OWASP ZAP) and finds runtime issues like missing security headers or misconfigured cookies.

16.8 Under the hood — the analysis round trip

Because analysis happens on the SonarQube server, waitForQualityGate() must block until the callback arrives. If the webhook cannot reach Jenkins — wrong URL, firewall, self-signed certificate — the step waits for your timeout and then fails. That is why the timeout matters as much as the webhook itself.

16.10 Lab — fail the gate on purpose

🧪Lab 16.1 · Prove the gate blocks 1. Add obvious problems to src/routes/items.js — an unused variable, an empty if, and a duplicated block. Push to main.
javascriptDeliberately bad code
router.get('/', (req, res) => {
  const unused = 'I am never read';           // code smell
  if (req.query.done === undefined) { }       // empty block -> maintainability issue
  const result = items;                        // duplication candidate
  const result2 = items;
  res.status(200).json({ count: result.length, items: result2 });
});
2. Watch the pipeline: SAST succeeds because the analysis was uploaded, then Quality Gate fails with ERROR.
3. Open the SonarQube project UI and read the issues — the pipeline links straight to it.
4. Revert, push, confirm green. You now know the gate really does block.

16.12 More interview Q&A

Q5How is SonarQube different from a linter?
A linter catches style and simple bugs in one file. SonarQube maintains a project-wide model over time: cross-file duplication, coverage imported from your test reports, security hotspots, and — critically — a quality gate policy with trends and a new-code period, so you can enforce standards without inheriting all historical debt.
Q6Why analyse "new code" only?
Because applying today's standards to a ten-year-old codebase blocks delivery forever. The new-code period (since the last release, or a reference branch) means every change must be clean while existing debt stays visible and tracked separately — debt then shrinks naturally.
Q7Analysis succeeded but coverage shows 0% in SonarQube.
Either the report path is wrong, or the report was generated after the scanner ran. The order must be: tests first, producing coverage/lcov.info or coverage.xml, then sonar-scanner, with sonar.javascript.lcov.reportPaths or sonar.python.coverage.reportPaths pointing at the real file.
Q8How do you keep the SonarQube token safe?
It is stored as a secret-text credential in Jenkins and injected by withSonarQubeEnv, so it never appears in the Jenkinsfile or the console. I use a token per project or per team and rotate it on the same schedule as other CI credentials.
Q9How long should the quality gate wait?
Typically two to five minutes; I use timeout(time: 5, unit: 'MINUTES'). Very large projects can exceed that, in which case I raise the timeout rather than remove the gate — a silent pass is far worse than a slow one.
