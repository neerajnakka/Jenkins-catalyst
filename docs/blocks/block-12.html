Block 12 · Real engineering

RBAC, users & permissions

Goal: turn "anyone can do anything" into least privilege: the right people can do the right things, and nobody can read production secrets. This is the block that separates an admin from a user.

12.1 Authentication vs Authorization

🔐 Security Realm (authentication)

Who are you? Jenkins' own user database, LDAP/Active Directory, GitHub OAuth, SAML, SSO.

🛂 Authorization Strategy (authorization)

What may you do? Matrix-based, Project-based Matrix, or Role-Based Strategy.

Find both under Manage Jenkins → Security.

12.2 Why Role-Based beats Matrix at scale

StrategyHow it worksProblem
Anyone can do anythingNo restrictionsNever acceptable beyond a laptop
Logged-in users can do anythingOne checkbox per permissionEvery user is effectively admin
Matrix-based securityA grid of users × ~50 permissionsEdit 20 users' grids individually — unmaintainable
Project-based MatrixMatrix per jobBetter, but still per-job editing
Role-Based Strategy ⭐Define roles, assign users to rolesNeeds the plugin — and is what real companies use

12.3 Setting up Role-Based Authorization Strategy

  1. Install the plugin: Role-based Authorization Strategy (role-strategy).
  2. Manage Jenkins → Security → Authorization → select Role-Based Strategy → Save.
  3. Manage Jenkins → Security → Manage and Assign Roles appears. Configure three role types:
Role typeControlsExamples
Global rolesController-wide powersadmin (Overall/Administer) · readonly (Overall/Read) · developer (Overall/Read + Job/Read)
Item rolesJobs, by name patternnodejs-team → pattern nodejs-.* with Build/Cancel/Configure · python-team → python-.*
Agent rolesWhich agents a role may usecan-use-linux → pattern linux-.*
uiA sensible three-role setup for this project
Manage Roles
  GLOBAL
    admin       : Overall → Administer, Read · Credentials → Create/Delete/ManageDomains
                  (keep this to 1-2 people!)
    developer   : Overall → Read · Job → Read · View → Read
    readonly    : Overall → Read

  ITEM
    nodejs-team : Pattern  nodejs-.*   → Job: Build, Cancel, Read, Workspace, Configure
    python-team : Pattern  python-.*   → Job: Build, Cancel, Read, Workspace, Configure
    viewer      : Pattern  .*          → Job: Read

  AGENT
    linux-users : Pattern  linux-.*    → Agent: Build, Connect

Assign Roles
  you          → admin, nodejs-team, python-team
  teammate-a   → developer, nodejs-team
  teammate-b   → developer, python-team
  intern       → readonly, viewer
💡Item patterns are regex, and they're your whole security model nodejs-.* matches every job whose name starts with nodejs-. Combine that with Folders (New Item → Folder) and you get per-team namespaces where credentials can also be scoped — a team literally cannot see another team's secrets.

🚨Locked yourself out? Recovery If you enable Role-Based Strategy and remove your own admin rights, Jenkins will not let you back in through the UI. Recovery (needs server access):
bashEmergency admin recovery
# 1. Stop Jenkins
sudo systemctl stop jenkins

# 2. Edit the global config: disable authorization entirely
sudo vim /var/lib/jenkins/config.xml
#    <useSecurity>true</useSecurity>   ->   <useSecurity>false</useSecurity>
#    (also remove the <authorizationStrategy> block if you like)

# 3. Start, log in as admin, re-configure roles properly, re-enable security
sudo systemctl start jenkins
Always keep a second admin account. This is the #1 self-inflicted Jenkins outage.

12.5 RBAC in the real world — the story to tell

🎤How to describe it in an interview "Controllers used the Role-Based Authorization Strategy plugin. We had a global readonly role for everyone, a developer role with build and workspace access, and item roles scoped by folder pattern so the Node team could only configure nodejs-* jobs. Credentials were stored in folder domains, so a team physically couldn't use another team's secrets. Anonymous access was off, agents had restricted controller access, and every admin action was captured in an audit trail."

12.6 ✅ Checklist

  • Role-Strategy plugin installed and active.
  • Created readonly, developer and admin global roles.
  • Created two item roles with regex patterns and tested them with a second user account.
  • Anonymous read is off; you can prove it in a private/incognito window.
  • You know the config.xml lockout recovery procedure.

12.7 💬 Interview Q&A

Q1How do you implement RBAC in Jenkins?
With the Role-based Authorization Strategy plugin: global roles for controller-wide permissions, item roles scoped by job-name pattern or folder, and agent roles restricting which agents a user's builds may run on. Users are assigned to roles, and I follow least privilege — most people get read + build, a few get configure, and admin is limited to one or two people.
Q2How do you stop one team seeing another team's credentials?
Put each team's jobs in a folder, store their credentials in that folder's credentials domain, and grant the team's item role only on that folder pattern. Credentials outside the folder are neither visible nor referenceable by their pipelines.
Q3What did you lock down on a production controller?
Anonymous access off, CSRF on, agent→controller access control on, HTTPS via a reverse proxy, admins limited to a named few, API tokens instead of passwords, and an audit-trail plugin so configuration changes are attributable.
Q4You're locked out of Jenkins after a permissions change. What now?
I have server access, so I stop Jenkins, set <useSecurity>false</useSecurity> in /var/lib/jenkins/config.xml, restart, log back in as admin, fix the roles, and re-enable security. To prevent it happening I always keep a second admin account and test role changes with a non-admin user first.
Q5What's the difference between authentication and authorization here?
Authentication (the security realm) decides who you are — local database, LDAP, GitHub OAuth. Authorization (the strategy) decides what you may do — matrix or role-based permissions. They're configured independently in Manage Jenkins → Security.

12.8 Under the hood — how authorization is evaluated

Jenkins asks, for every action, "does this user hold permission X on item Y?" The AuthorizationStrategy answers using the ACL attached to the item. With Role Strategy, item roles contribute ACL entries matched by job-name regex, which is why folder structure is a security control, not just tidiness.

ConceptMeaning
PermissionAn atomic capability: Job/Build, Job/Configure, Credentials/Create, Overall/Administer, Run/Delete
RoleA named bundle of permissions (global / item / agent)
AssignmentUser or group → role. Groups come from the security realm (LDAP, GitHub orgs, SAML)
Item patternRegex over the full item name, e.g. nodejs-.* or team-a/.* for folders
FolderA namespace that scopes both item roles and credentials
groovyScript Console — audit who has what
import com.michelin.cio.hudson.plugins.rolestrategy.*
import jenkins.model.Jenkins

def strategy = Jenkins.instance.getAuthorizationStrategy()
if (strategy instanceof RoleBasedAuthorizationStrategy) {
    strategy.getRoleMaps().each { type, map ->
        println "=== ${type} ==="
        map.getRoles().each { role ->
            println "  ${role.name}  pattern=${role.pattern}"
            println "    perms : ${role.permissions.collect { it.name }.join(', ')}"
            println "    users : ${map.getAssignedSIDs(role.name).join(', ')}"
        }
    }
}

12.9 A complete hardening runbook

  1. Enable security with a real realm (local DB for labs, LDAP/OIDC/SAML in companies).
  2. Set Role-Based Strategy; create readonly, developer, admin global roles.
  3. Create folders per team and item roles scoped to <folder>/.*.
  4. Move credentials into folder domains; delete the global duplicates.
  5. Turn off anonymous access; verify in a private window.
  6. Enable Agent → Controller Access Control so agents can't read credentials or call controller APIs.
  7. Put HTTPS in front; bind 8080 to localhost.
  8. Issue API tokens for automation; never embed account passwords.
  9. Install an audit trail (Audit Trail + Job Config History).
  10. Keep a second admin account so one mistake can't lock you out.
⚠️The one that surprises people Overall/Read is required for almost anything to be visible at all — including for the github-webhook/ endpoint to work when using authenticated triggers. Grant it to a dedicated ci-trigger service account rather than to anonymous.

12.10 Lab — verify your RBAC like an attacker

🧪Lab 12.1 · Test with a second account Create user intern with only readonly, then log in as them (private window) and confirm:
bashWhat an unprivileged user must NOT be able to do
# 1. Anonymous sees nothing
curl -s -o /dev/null -w "anon: %{http_code}\n" http://<jenkins>:8080/

# 2. A read-only user cannot build
curl -s -o /dev/null -w "intern build: %{http_code}\n" \
     -u intern:pass -X POST http://<jenkins>:8080/job/nodejs-app/build

# 3. A read-only user cannot read credentials
curl -s -o /dev/null -w "intern creds: %{http_code}\n" \
     -u intern:pass http://<jenkins>:8080/credentials/store/system/domain/_/api/json

# Expected: 403 (or 401) on 1-3, never 200
Then in the UI confirm the intern can see nodejs-app but cannot click Build Now, and cannot see the Script Console.

12.11 More interview Q&A

Q6How do you integrate Jenkins with LDAP or SSO?
Change the Security Realm: LDAP plugin with a server URL, bind DN and user search base, or SAML/OIDC plugins for SSO. Authentication then delegates to the directory while authorization stays role-based, with groups from the directory mapped to Jenkins roles.
Q7What is Agent → Controller Access Control?
A security subsystem that restricts what an agent process can ask the controller to do — for example reading credentials or calling remoting APIs. Without it, anyone who can run a build on an agent effectively has controller-level access, which is a serious risk in shared environments.
Q8How do you give a contractor temporary access?
Create a named account, assign the least-privilege role on the specific folder, and set a calendar reminder or an expiry process to remove it. I never share accounts, and I review the user list quarterly.
Q9How do you prove compliance (who changed what)?
The Audit Trail plugin records authentication and configuration events, and Job Config History keeps every version of every job configuration — so I can show who changed a pipeline definition and when, which is what auditors ask for.
Q10Jenkins is fully open on a new install. What do you do on day one?
Run the setup wizard with my own admin account (never the default), disable anonymous access, enable role-based authorization, create folders and scoped credentials, enable agent→controller access control, and put it behind HTTPS.
