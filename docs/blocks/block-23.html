Troubleshooting playbook

Goal: stop guessing. A repeatable debugging method plus a reference of the errors that actually happen — 90% of "Jenkins is broken" is one of these.

23.1 The five-step debugging method

  1. Read the first error, not the last. Scroll the console log to the first ERROR or failing + command. Java stack traces list 50 lines of context but the cause is usually in the first 5.
  2. Reproduce as the Jenkins user. sudo -iu jenkins <command>. If it fails there too, it's not a Jenkins problem — it's permissions, PATH, or the environment.
  3. Compare environments. Add sh 'env | sort', sh 'whoami && pwd && node -v'. Differences in PATH, HOME and tool versions explain most "works locally" bugs.
  4. Isolate with Replay. Edit the Jenkinsfile in the browser, reduce it to just the failing step, iterate in seconds.
  5. Inspect the workspace. Job → Workspace. Are the files actually there? Did the checkout happen? Is a stale artifact breaking you? (Then cleanWs().)

23.2 Diagnostic snippets to keep in your pocket

groovyDrop-in debug stage
stage('Debug') {
    steps {
        sh '''
            set +e                     # keep going so we see everything
            echo "--- identity ---";  whoami; id
            echo "--- location ---";  pwd; ls -la
            echo "--- tools ---";     node -v 2>/dev/null; npm -v 2>/dev/null
                                      python3 -V 2>/dev/null; docker -v 2>/dev/null
                                      git --version; java -version 2>&1 | head -1
            echo "--- env ---";       env | sort
            echo "--- disk ---";      df -h . ; du -sh . 2>/dev/null
            echo "--- network ---";   curl -sS -m 5 -o /dev/null -w "github:%{http_code}\\n" https://github.com
                                      curl -sS -m 5 -o /dev/null -w "dockerhub:%{http_code}\\n" https://hub.docker.com
        '''
        echo "Jenkins env: BUILD=${env.BUILD_NUMBER} NODE=${env.NODE_NAME} LABELS=${env.NODE_LABELS}"
        echo "Params: ${params}"
        echo "Result so far: ${currentBuild.currentResult}"
    }
}

23.8 💬 Interview Q&A

Q1A build fails in Jenkins but works on my machine. Walk me through it.
Reproduce as the Jenkins user with sudo -iu jenkins — that alone catches most of it. Then compare: tool versions, PATH, working directory, lockfile/commit status, network access to registries, and disk. Then read the first error in the console log rather than the last, and isolate the failing step with Replay.
Q2A build is stuck in the queue. Why?
Either all executors are busy or no online agent matches the label expression. I check the queue's "why" text, then Nodes for offline agents and label spelling. Long term: more agents with those labels, and per-stage agents so a long stage doesn't hold a slot for the whole run.
Q3You see "Scripts not permitted to use method…". What do you do?
It's the Groovy sandbox blocking a signature. For a one-off I approve it in In-process Script Approval after reviewing what it does — it grants that permission controller-wide. For anything recurring I move the logic into a shared library, where it runs outside the sandbox deliberately and is code-reviewed instead of click-approved.
Q4How do you diagnose a slow pipeline?
Timestamper plus the Stage View shows exactly which stage is slow. From there: dependency download (add caching), Docker layer cache (--cache-from), sequential work that could be parallel, or an agent that's simply underpowered. I also check whether slowness correlates with concurrency — that's usually executors or I/O.

23.8 Under the hood — the plugin architecture

Every Jenkins feature you use is a plugin. Understanding four extension points explains most of what you see:

ConceptWhat it isExample
ExtensionA class annotated @Extension that contributes behaviour to an extension pointA new build step, a new SCM, a new credential type
Describable + DescriptorA configurable object with metadata (display name, help, validation)A step with a UI form in the Snippet Generator
Publisher / RecorderRuns in the post phase to consume build outputsjunit, archiveArtifacts, recordIssues
Builder / SimpleBuildStepDoes work during the buildsh, docker build steps
💡Why this helps you in an interview When someone says "we solved it with a custom plugin", being able to say "that would be a SimpleBuildStep with a Descriptor, or honestly a shared-library step if it's just orchestration" shows architectural judgement rather than tool ignorance.

23.9 The plugin selection checklist

CheckWhere to lookRed flag
Actively maintainedplugins.jenkins.io — last release date, changelogNo release in 2+ years

Open issues / security advisoriesJira, GitHub, Jenkins security advisoriesOpen unfixed advisory
CompatibilityRequired core versionForces a core downgrade
OverlapCompare with what you already haveThree plugins doing the same job
Exit costCan the logic live in the pipeline instead?Config only exists in the plugin
⚠️Prefer pipeline code over plugins Anything expressed in the Jenkinsfile is visible in code review, versioned with the app, and portable. Plugin configuration lives in the controller's XML. So: use plugins for capability (Kubernetes agents, SonarQube integration), but keep policy — thresholds, ordering, gating — in the pipeline.

23.10 Lab — install, audit, remove

🧪Lab 23.1 · Plugin hygiene in practice
bashInventory and dependency audit
# What is installed, with versions -- keep this in Git
JENKINS_URL=http://localhost:8080
curl -sS "$JENKINS_URL/pluginManager/api/json?depth=1" \
  | jq -r '.plugins[] | "\(.shortName):\(.version)"' | sort > plugins-installed.txt

# Which plugins are pinned / have updates / are deprecated
curl -sS "$JENKINS_URL/pluginManager/api/json?depth=1" \
  | jq -r '.plugins[] | select(.hasUpdate or .pinned or .deleted)
           | "\(.shortName) update=\(.hasUpdate) pinned=\(.pinned) deleted=\(.deleted)"'

# Who depends on a plugin you want to remove? (dependency graph)
curl -sS "$JENKINS_URL/pluginManager/api/json?depth=2" \
  | jq -r '.plugins[] | select(.shortName=="credentials") | .dependencies[] | .shortName'
Then: uninstall one plugin you added early but no longer use, restart, and confirm nothing breaks. Always check the dependency list first — removing a shared dependency can disable several others at once.

23.12 More interview Q&A

Q6How do you manage plugin risk?
Keep the installed set minimal and pinned, record it in Git (or a plugins.txt used to build the image), subscribe to Jenkins security advisories, and test upgrades on a staging controller. Every plugin is code running with controller privileges, so the set is an attack surface, not a feature list.
Q7A plugin breaks after an upgrade. What now?
Identify the culprit from the update history, roll back that plugin (keep the previous .jpi), or restore the controller from the pre-upgrade snapshot. If it's a longer fix, check whether the functionality can move into the pipeline or a shared library so the dependency disappears.
Q8Configuration as Code vs Job DSL vs manual setup?
JCasC configures the controller (security realm, agents, tools, credentials) from YAML at boot. Job DSL creates jobs from Groovy seed scripts. Manual setup is for exploration only. In a mature setup everything is one of the first two, and Multibranch plus Jenkinsfiles means most job definitions live in Git anyway.
Q9How do you introduce a new plugin to a team?
Add it in a staging controller, prove the value in one pipeline, document the integration steps, then promote it to the shared plugin list with a pinned version — and tell the team what it replaces. Never install directly on production first.
Q10When would you write your own plugin?
Only when the behaviour genuinely cannot be expressed in a pipeline or shared library — deep integration with an internal system, a new credential type, or a custom UI. Otherwise a shared-library step is cheaper to write, test and review, and it's portable.
