Block 4 · Foundation

Git + GitHub integration

Goal: Jenkins pulls your code from GitHub automatically, authenticated, without a human typing a password — the single most fundamental CI capability.

4.1 Two ways to authenticate (learn both)

🔑 SSH key Preferred for servers

A key pair. Private key lives in the Jenkins credentials store; public key is registered on GitHub. No expiry, no scope juggling, works for deploy keys too.

🎟️ HTTPS + Personal Access Token

Uses a GitHub PAT as the password. Easy to rotate, easy to revoke, and required for the GitHub API (Block 15 multibranch, PR status).

4.2 Option A — SSH key (recommended)

  1. Generate the key as the jenkins user — not as root, or the file permissions will be wrong and ssh will silently refuse to use it.
bashOn the EC2 box — as the jenkins user
sudo -iu jenkins bash                       # become the jenkins user
mkdir -p ~/.ssh && chmod 700 ~/.ssh
ssh-keygen -t ed25519 -C "jenkins@ci" -f ~/.ssh/id_ed25519 -N ""   # no passphrase
cat ~/.ssh/id_ed25519.pub                   # 1) copy this to GitHub

# 2) TRUST github.com's host key -- without this the first checkout hangs or fails
ssh-keyscan -t rsa,ed25519 github.com >> ~/.ssh/known_hosts
chmod 600 ~/.ssh/known_hosts

# 3) prove it before touching Jenkins (fail here = fail in the pipeline)
ssh -T git@github.com                       # -> "Hi <you>! You've successfully authenticated"
cat ~/.ssh/id_ed25519                       # 4) copy this PRIVATE key into Jenkins
uiRegister the key in both places
GITHUB  (public key)
  Repo → Settings → Deploy keys → Add deploy key    (read-only, per repo)   - preferred
  or: GitHub → Settings → SSH and GPG keys → New SSH key   (all your repos)

JENKINS (private key)
  Manage Jenkins → Credentials → System → Global credentials → Add Credentials
    Kind         : SSH Username with private key
    ID           : github-ssh            <-- you will reference this exact string
    Username     : git
    Private Key  : Enter directly → paste the whole -----BEGIN ... KEY----- block
                   (include the BEGIN and END lines)
⚠️Deploy key vs account key A deploy key is scoped to one repository and can be read-only — perfect for a CI that only clones. An account key grants access to every repo you can see. In interviews, "we used per-repo read-only deploy keys" is the stronger answer.

4.3 Option B — HTTPS with a Personal Access Token

  1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token. Scopes: repo (private repos) and admin:repo_hook if you want Jenkins to create the webhook for you (Block 10).
  2. Jenkins → Credentials → System → Global → Add Credentials → Kind: Username with password → Username: your GitHub username → Password: the token → ID: github-pat.
🚨Never put a token in the Jenkinsfile A PAT in a Jenkinsfile is a credential committed to Git, visible in every fork, clone and CI log. Tokens go in the credentials store and are referenced by ID. We cover injection in Block 8.

4.4 The checkout step

groovyGenerated by the Snippet Generator → "checkout: Check out from version control"
checkout scmGit(
    branches: [[name: '*/main']],
    extensions: [
        cleanBeforeCheckout(),                       // wipe workspace before cloning
        [$class: 'CloneOption', shallow: true, depth: 1, noTags: false],
        [$class: 'SubmoduleOption', recursiveSubmodules: true]
    ],
    userRemoteConfigs: [[
        credentialsId: 'github-ssh',
        url: 'git@github.com:<you>/jenkins-zero-to-hero.git'
    ]]
)
groovySimple, readable, enough for most repos
git branch: 'main',
    url: 'git@github.com:<you>/jenkins-zero-to-hero.git',
    credentialsId: 'github-ssh'
groovyInherits whatever the job's SCM config says (essential for Multibranch, Block 15)
// Reads the SCM + branch from the job configuration.
// In a Multibranch Pipeline, `scm` is the branch being built --
// so you MUST use this form there, never hard-code `main`.
checkout scm

// ...and to control it (skip the automatic checkout, do it yourself):
options { skipDefaultCheckout(true) }
stages {
    stage('Checkout') {
        steps { checkout scm }
    }
}
ExtensionWhy you'd use it
cleanBeforeCheckout()Delete stale files before cloning. Prevents "it works on my machine" from leftover artifacts.
[$class:'CloneOption', shallow:true, depth:1]Shallow clone — much faster on big repos. Not for pipelines that need full history/tags.
[$class:'SparseCheckoutPaths']Clone only nodejs-app/** in a monorepo.
[$class:'LocalBranch']Check out a real local branch instead of detached HEAD (needed if you push tags back).

4.5 Useful Git facts inside a pipeline

groovyRead commit metadata for image tags and reports
script {
    env.GIT_COMMIT_SHORT = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
    env.GIT_BRANCH_NAME  = sh(script: 'git rev-parse --abbrev-ref HEAD', returnStdout: true).trim()
    env.GIT_AUTHOR       = sh(script: "git log -1 --pretty=format:'%an'", returnStdout: true).trim()
    env.GIT_MESSAGE      = sh(script: "git log -1 --pretty=format:'%s'", returnStdout: true).trim()

}

4.6 ✍️ Jenkinsfiles v4 — real checkout

groovynodejs-app/Jenkinsfile — v4
pipeline {
    agent any
    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment {
        APP_NAME  = 'nodejs-app'
        REPO_URL  = 'git@github.com:<you>/jenkins-zero-to-hero.git'
        GIT_CRED  = 'github-ssh'          // credential ID from Manage Jenkins
    }

    stages {
        stage('Checkout') {
            steps {
                dir(APP_NAME) {                       // keep each app in its own folder
                    checkout scmGit(
                        branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: env.GIT_CRED, url: env.REPO_URL]]
                    )
                }
                script {
                    dir(APP_NAME) {
                        env.GIT_SHA = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
                    }
                    echo "Checked out ${env.GIT_SHA}"
                }
            }
        }
        stage('Build') { steps { echo 'Block 5' } }
        stage('Test')  { steps { echo 'Block 6' } }
    }

    post { always { echo "Result: ${currentBuild.currentResult}" } }
}

4.7 ✅ Checklist

  • ssh -T git@github.com succeeds when run as the jenkins user.
  • Credential github-ssh exists in Jenkins with ID spelled exactly as in the Jenkinsfile.
  • Both pipelines show a green Checkout stage that prints a commit SHA.
  • You know what changes when a branch is renamed (the branches value).

4.8 💬 Interview Q&A

Q1How does Jenkins authenticate to a private Git repo?
With a credential stored in the Jenkins credentials store and referenced by ID. Typically an SSH private key whose public half is registered as a GitHub deploy key, or a PAT over HTTPS. The private key never appears in the Jenkinsfile — only the credential ID does.
Q2checkout scm vs git ... — when do you use which?
checkout scm inherits the SCM and branch from the job configuration, so it's mandatory in Multibranch pipelines where the branch varies per build. An explicit git/checkout scmGit step is used when the pipeline must control URL, branch or clone extensions itself.
Q3Why use a shallow clone?
depth: 1 downloads only the latest commit, cutting clone time and disk on large repos. The trade-off is no history or tags, so it's unsuitable for pipelines that compute version numbers from history or push tags.
Q4How do you stop Jenkins from auto-checking out twice?
options { skipDefaultCheckout(true) } disables the implicit checkout, then I run checkout scm explicitly inside a stage — which gives control over ordering, extensions and workspace layout.

4.10 Under the hood — what "checkout" really does

The Git plugin keeps a real .git directory in the workspace: it fetches, checks out the ref, and optionally cleans. Three details that matter in practice:

ConceptWhat it meansWhy you care
Branch specifier*/main means "the main branch of any remote". Multibranch resolves */<branch> per build.A wrong specifier gives a silent "no changes".
Lightweight checkoutMultibranch reads the Jenkinsfile straight from the Git API, before allocating a workspace, to decide if a branch is buildable.Fast indexing — and why a Jenkinsfile syntax error appears at scan time.
ChangelogJenkins computes the commit range since the last successful build into currentBuild.changeSets.This is how you notify the person who broke it.
groovyExtracting authors, messages and changed files
script {
    def changes = currentBuild.changeSets.collectMany { cs ->
        cs.items.collect { c ->
            [ author: c.author.fullName,
              email : c.author.getProperty(hudson.tasks.Mailer.UserProperty)?.address,
              msg   : c.msg.take(120),
              files : c.affectedFiles.collect { f -> f.path } ]
        }
    }
    echo "This build contains ${changes.size()} commit(s)"
    changes.each { c -> echo "- ${c.author}: ${c.msg}" }
    env.CULPRIT_EMAILS = changes.collect { it.email }.findAll { it }.unique().join(',')
}

4.12 Lab — break the key, then repair it

🧪Lab 4.1 · The three failure modes of Git over SSH A. Wrong permissions.
bashReproduce then fix
sudo -iu jenkins chmod 644 ~/.ssh/id_ed25519     # break it
sudo -iu jenkins ssh -T git@github.com           # "UNPROTECTED PRIVATE KEY FILE"
sudo -iu jenkins chmod 600 ~/.ssh/id_ed25519     # fix it
B. Unknown host.
bashReproduce then fix
sudo -iu jenkins mv ~/.ssh/known_hosts /tmp/kh   # break it
sudo -iu jenkins ssh -T git@github.com           # "Host key verification failed"
sudo -iu jenkins ssh-keyscan -t rsa,ed25519 github.com >> ~/.ssh/known_hosts
C. Credential ID mismatch. Rename the Jenkins credential to github-ssh-typo and re-run: you get Could not resolve credentialsId. This proves credentials are matched by exact string, not by fuzzy name.

4.13 Monorepo patterns

Our repo holds two apps. Three ways to avoid building both on every commit:

groovyClone only the folder you need
checkout scmGit(
    branches: [[name: '*/main']],
    extensions: [[$class: 'SparseCheckoutPaths',
                  sparseCheckoutPaths: [[path: 'nodejs-app/']]]],
    userRemoteConfigs: [[credentialsId: 'github-ssh', url: env.REPO_URL]]
)
groovySkip the build when your folder didn't change
stage('Change detection') {
    agent { label 'linux' }
    steps {
        script {
            checkout scm
            def files = sh(script: 'git diff --name-only HEAD~1 HEAD', returnStdout: true).trim()
            env.CHANGED = files.readLines().any { it.startsWith('nodejs-app/') } ? 'true' : 'false'
            echo "nodejs-app changed: ${env.CHANGED}"
        }
    }
}
stage('Test') {
    when { expression { env.CHANGED == 'true' } }
    steps { dir('nodejs-app') { sh 'npm ci && npm test' } }
}

Caveat: HEAD~1 misses multi-commit pushes. Prefer git diff --name-only ${env.GIT_PREVIOUS_SUCCESSFUL_COMMIT} HEAD when that variable is set.

groovySimplest: one Multibranch job per app
# Job: nodejs-pipeline  -> Script Path: nodejs-app/Jenkinsfile
# Job: python-pipeline  -> Script Path: python-app/Jenkinsfile
#
# Each job still clones the repo (cheap for us) but executes only its own
# Jenkinsfile, so only that app is built, tested, scanned and pushed.

4.14 More interview Q&A

Q5How does Jenkins know who broke the build?
It computes the changelog between the last successful build and the current one and exposes it as currentBuild.changeSets, from which I read author, message and affected paths — that drives targeted notifications.
Q6Submodules, LFS and sparse checkouts?
All three are checkout extensions: [$class:'SubmoduleOption', recursiveSubmodules:true], Git LFS via the LFS pull extension, and SparseCheckoutPaths for monorepos. I generate them rather than hand-write the class names.
Q7Why would a branch not appear in a Multibranch scan?
Branch discovery disabled, the name filtered out by the include/exclude regex, no Jenkinsfile at the configured path, or the PAT lacks repo scope. The Scan Repository Log states which one it hit.
Q8How do you avoid building every app on every commit in a monorepo?
Sparse-checkout the relevant path, or compute changed paths from the changelog and gate stages with when. At larger scale, per-app jobs with path filters, or an orchestrator that fans out only to affected components.
