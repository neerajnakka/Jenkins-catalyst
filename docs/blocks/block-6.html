Block 6 · Foundation

TEST stage + reports & quality gates

Goal: run the test suites, publish machine-readable results Jenkins can graph, and make coverage a real gate — not a number nobody reads.

6.1 Why reports matter more than logs

Green text in a console log is worthless to a team: you can't trend it, filter it, or see which test broke. JUnit XML turns test output into data Jenkins stores per build — a trend graph, a per-test history, and a "this test has been flaky for 3 days" signal.

6.3 Publishing the reports

groovyThe three publish steps
post {
    always {
        // 1. Test results -> per-test history, trend graph, flaky detection
        junit testResults: 'reports/junit.xml',
              allowEmptyResults: true,
              skipPublishingChecks: false

        // 2. Coverage (modern "Coverage" plugin, replaces the old Cobertura plugin)
        recordCoverage tools: [[parser: 'COBERTURA', pattern: 'coverage/cobertura-coverage.xml']],
                       id: 'coverage', name: 'Code Coverage',
                       sourceCodeRetention: 'EVERY_BUILD'

        // 3. Keep the HTML report + artifacts for humans
        archiveArtifacts artifacts: 'reports/**,htmlcov/**,coverage/**',
                         allowEmptyArchive: true, fingerprint: true
    }
}
📦Plugin Install Coverage (coverage) — the modern successor to the Cobertura plugin. For Python point the parser at coverage.xml with parser: 'COBERTURA'; it's the same XML schema pytest-cov writes.

// catchError: the stage turns red, the build becomes UNSTABLE and CONTINUES

        catchError(buildResult: 'UNSTABLE', stageResult: 'FAILURE') {
            sh 'npm test'
        }
    }

// Set it manually from Groovy
script {
    if (env.COVERAGE_PCT && env.COVERAGE_PCT.toInteger() < 70) {
        currentBuild.result = 'UNSTABLE'
        echo "Coverage ${env.COVERAGE_PCT}% is below the 70% gate"
    }
}

6.5 A real coverage gate

Don't just report coverage — enforce it, so the number can't rot. Both ecosystems can do it natively:

jsonnodejs-app/package.json → jest.coverageThreshold
"jest": {
  "testEnvironment": "node",
  "collectCoverageFrom": ["src/**/*.js"],
  "coverageReporters": ["text-summary", "lcov", "cobertura"],
  "coverageThreshold": {
    "global": { "lines": 70, "statements": 70, "branches": 50, "functions": 60 }
  }
}

Jest exits non-zero when the threshold is missed — one line, no extra plugin.

bashpytest --cov-fail-under
. venv/bin/activate
pytest --cov=app --cov-report=xml:coverage.xml \
       --cov-report=term-missing --cov-fail-under=70

Or move it into pytest.ini so nobody can forget it: addopts = … --cov-fail-under=70.

6.6 ✍️ Jenkinsfiles v6 — tests + reports

groovynodejs-app/Jenkinsfile — v6 (Test)
pipeline {
    agent any
    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment { APP_NAME = 'nodejs-app'; npm_config_cache = '/var/lib/jenkins/.npm' }

    stages {
        stage('Checkout') {
            steps { dir(APP_NAME) { checkout scmGit(branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: 'github-ssh',
                            url: 'git@github.com:<you>/jenkins-zero-to-hero.git']]) } }
        }
        stage('Build') {
            steps { dir(APP_NAME) { sh 'npm ci' } }
        }
        stage('Test') {
            steps {
                dir(APP_NAME) {
                    // coverageThreshold in package.json enforces the quality gate
                    sh label: 'unit tests + coverage', script: 'npm run test:junit'
                }
            }
        }
    }

    post {
        always {
            dir(APP_NAME) {
                junit testResults: 'reports/junit.xml', allowEmptyResults: true
                recordCoverage tools: [[parser: 'COBERTURA', pattern: 'coverage/cobertura-coverage.xml']],
                               sourceCodeRetention: 'LAST_BUILD'
                archiveArtifacts artifacts: 'reports/**,coverage/**', allowEmptyArchive: true
            }
            echo "Result: ${currentBuild.currentResult}"
        }
    }
}

6.8 💬 Interview Q&A

Q1How does Jenkins know a test failed?
Two ways. The shell step's non-zero exit code fails the build immediately, or the junit step parses the XML and, if any test case is a failure/error, marks the build UNSTABLE. Publishing XML gives far better feedback because Jenkins then knows which test and keeps per-test history.
Q2What is the difference between UNSTABLE and FAILURE?
FAILURE means the pipeline threw an error — compile error, missing file, non-zero exit. UNSTABLE means it completed but quality criteria weren't met: failing tests, coverage under threshold, or a SonarQube quality gate in red. UNSTABLE is "built, but don't ship it".
Q3How do you enforce a coverage gate?
Make the test command exit non-zero below the threshold — Jest's coverageThreshold or pytest's --cov-fail-under — and publish the XML so the trend is visible. Later (Block 16) SonarQube enforces the same idea across duplication, smells and vulnerabilities.
Q4How do you handle flaky tests in CI?
Publish JUnit XML so Jenkins tracks flakiness per test, quarantine the flaky test out of the blocking gate, and fix or delete it with a deadline. My rule: a flaky test is a bug in the test or the product — never something you just retry away.

6.10 Under the hood — what JUnit XML contains

The report is just XML. Understanding its shape lets you debug "why is my test result empty" in seconds.

xmlreports/junit.xml — the schema Jenkins parses
<testsuites name="jest tests">
  <testsuite name="items API" tests="3" failures="1" errors="0" skipped="0" time="0.412">
    <testcase name="GET /api/items lists seeded items" classname="items API" time="0.031"/>
    <testcase name="POST /api/items creates an item (201)" classname="items API" time="0.019">
      <failure message="expected 201, received 400">
        at Object.<anonymous> (tests/app.test.js:31:26)
      </failure>
    </testcase>
  </testsuite>
</testsuites>
  • Jenkins builds its per-test history from the name + classname pair. Rename a test and you break its history — which is why flaky-test detection needs stable test names.
  • Any <failure> or <error> child marks the build UNSTABLE (not FAILED), because the pipeline itself completed.
  • allowEmptyResults: true stops the step failing when the file is missing — essential when tests didn't run at all.

6.11 Lab — break the pipeline three ways

🧪Lab 6.1 · Failure, unstable, and silent success 1. A failing test. Change an assertion in tests/app.test.js, commit, run. The stage goes red, the build is UNSTABLE (because junit reported failures) — unless your sh also exits non-zero, in which case it's FAILURE. Understand which one you got and why.
groovyMaking the distinction explicit
// A: command fails -> stage red, build FAILED, later stages skipped
sh 'npm test'

// B: command fails -> stage red, build UNSTABLE, pipeline continues
catchError(buildResult: 'UNSTABLE', stageResult: 'FAILURE') { sh 'npm test' }

// C: report published, result decided by the JUnit content only
sh(script: 'npm test', returnStatus: true)     // swallow the exit code
junit testResults: 'reports/junit.xml'         // UNSTABLE if any case failed
2. Coverage below the gate. Set --cov-fail-under=95 and watch the Test stage fail with a clear message.
3. Missing report. Point junit at the wrong path and see No test report files were found — then fix it with dir().

6.13 Flaky tests — policy, not hope

PracticeDetail
Never retry a test awayA retry hides the bug and destroys signal. Fix or quarantine.
Quarantine with a deadlineMove the flaky test to a non-blocking suite with a ticket and an expiry date.
Common causes to checkShared mutable state, real time/sleep, fixed ports, network calls, test order dependence, unseeded randomness.
Parallel safetyUse EXECUTOR_NUMBER for any port or temp directory, so parallel builds don't collide.
Track itJUnit history shows "failed 4 of last 20" — that's your evidence for prioritising the fix.

6.14 More interview Q&A

Q5Why is my build UNSTABLE instead of FAILED?
Because something reported a quality problem rather than an error — most often the junit step finding failing test cases, or a coverage/quality gate. The pipeline ran to completion; it just didn't meet the standard. I use that distinction to alert differently.
Q6How do you handle flaky tests?
Publish JUnit XML so Jenkins tracks per-test history, then quarantine the flaky test out of the blocking suite with a ticket and a deadline, and fix the root cause — usually shared state, real time, a fixed port or network dependency. I never add a blanket retry.
Q7How do you make tests safe to run in parallel on one agent?
Never bind fixed ports or use fixed temp paths. I derive them from env.EXECUTOR_NUMBER or env.BUILD_TAG, and keep all state inside the build's own workspace or a container.
Q8Coverage dropped from 85% to 40% overnight with no test changes. Why?
Almost always the collectCoverageFrom / --cov path changed, or new files were added outside the instrumented directory. Coverage measures what you told it to measure, so a renamed source folder silently resets the denominator.
