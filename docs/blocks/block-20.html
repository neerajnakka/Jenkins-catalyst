Notifications & human approvals

Goal: get the right message to the right channel, and put a deliberate human checkpoint in front of risky actions.

20.1 The input step — pausing for a human

groovyApproval gate with timeout, allowed approvers and captured values
stage('Approve production deploy') {
    when { branch 'main' }
    steps {
        script {
            timeout(time: 30, unit: 'MINUTES') {          // never wait forever
                def approval = input(
                    id: 'ProdDeploy',
                    message: "Deploy ${IMAGE}:${env.GIT_SHA} to PRODUCTION?",
                    ok: 'Ship it',
                    submitter: 'release-managers,admins',   // Jenkins users/groups allowed to approve
                    submitterParameter: 'APPROVER',         // who approved -> approval.APPROVER
                    parameters: [
                        choice(name: 'STRATEGY', choices: ['rolling','blue-green'], description: 'Deploy strategy'),
                        booleanParam(name: 'RUN_SMOKE', defaultValue: true, description: 'Run smoke tests after')
                    ]
                )
                env.APPROVER      = approval['APPROVER']
                env.DEPLOY_STRATEGY = approval['STRATEGY']
                echo "Approved by ${env.APPROVER} using ${env.DEPLOY_STRATEGY}"
            }
        }
    }
}
OptionPurpose
messageShown in the UI prompt — include what is being deployed
okLabel for the confirm button ("Deploy", not "Proceed")
submitterComma-separated users/groups allowed to approve (pairs with RBAC)
submitterParameterCaptures who approved, for the audit trail
parametersCollect extra decisions at approval time
idStable identifier — required if you use the API to approve
⚠️Always wrap input in timeout An input with no timeout holds an executor and a workspace indefinitely — the classic "why is Jenkins out of executors?" outage. Wrapping it in timeout() also gives you a defined result: timeouts abort the build, which you can handle in post { aborted { } }.
groovyApproval outside a stage's agent (best practice)
stage('Approve') {
    agent none                 // don't hold an agent while waiting for a human!
    when { beforeAgent true; branch 'main' }
    steps {
        timeout(time: 30, unit: 'MINUTES') {
            input message: 'Deploy to production?', ok: 'Deploy'
        }
    }
}

beforeAgent true evaluates the when condition before an agent is allocated — combined with agent none this means no executor is consumed while waiting.

20.3 Email (Extended E-mail Notification)

groovyemailext with an HTML body and a log excerpt
post {
    failure {
        script {
            def culprits = currentBuild.changeSets
                    .collectMany { it.items.collect { it.author.email ?: it.author.fullName } }
                    .unique().join(',')
            def log = currentBuild.rawBuild.getLog(60).join('\n')     // last 60 lines

            emailext(
                subject: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                to: culprits ?: 'devops@example.com',
                mimeType: 'text/html',
                body: """
                    <h3 style="color:#e11d48">Build FAILED</h3>
                    <p><b>Job:</b> ${env.JOB_NAME} #${env.BUILD_NUMBER}<br/>
                       <b>Branch:</b> ${env.BRANCH_NAME ?: 'n/a'}<br/>
                       <b>Commit:</b> ${env.GIT_SHA}<br/>
                       <a href="${env.BUILD_URL}">Open in Jenkins</a></p>
                    <pre style="background:#0d1526;color:#dce6f5;padding:12px">${log}</pre>
                """,
                attachLog: true,
                compressLog: true
            )
        }
    }
}

20.5 Notification design principles

PrincipleWhy
Notify on state change, not every build200 "build passed" messages a day = nobody reads any of them
Failures go to the person who broke itcurrentBuild.changeSets gives you the commit authors
Include a deep link and the artifact identity${BUILD_URL} and the SHA tag — no context switching
Page only for regressions on release branchesUse post { regression { } } and branch conditions
Never let notifications fail the buildWrap in try/catch or catchError — a Slack outage must not break CI

20.6 ✅ Checklist

  • An approval gate pauses the prod deploy and times out after 30 minutes.
  • Slack (or email) receives failure and success messages with a build link.
  • Notification failures cannot break the build.
  • Only changed-state events notify (no spam on every green build).

20.7 💬 Interview Q&A

Q1How do you add a manual approval to a pipeline?
With the input step inside a timeout(), restricted by submitter to a release group and captured with submitterParameter for the audit trail. I put it in a stage with agent none and when { beforeAgent true } so no executor is held while waiting for a human.
Q2Why is an un-timeout'd input dangerous?
It occupies an executor and a workspace indefinitely. Enough of them and the queue backs up until no build can run at all. A timeout turns that into a controlled abort I can handle in post { aborted { } }.
Q3How do you avoid notification fatigue?
Notify on state transitions — failure, fixed, regression — rather than on every success, route failures to the commit authors from currentBuild.changeSets, and reserve paging for regressions on release branches.
Q4Slack is down. Your build fails?
It must not. Notification steps are wrapped so their failure is logged, not propagated — losing a Slack message is acceptable, losing a build because the chat provider had an outage is not.

20.8 Under the hood — how approval actually works

💡The mental model While a pipeline is paused at input, the build is still occupying an executor and its state is persisted to disk. That's why it survives a controller restart. It's also why a long input inside node {} is expensive — prefer agent none plus a lightweight approval stage.
Where the approval comes fromMechanism
A human clicks in the UIJenkins renders the input form with your parameters and submitters
A script or chat bot approvesPOST to /job/<job>/<n>/input/<id>/submit with proceed= and the parameter JSON
A timeout firesThe step throws FlowInterruptedException → the build is aborted unless you wrap it

# List pending inputs
curl -sS -u "user:$API_TOKEN" \
  "$JENKINS_URL/job/nodejs-pipeline/job/main/42/wfapi/pendingInputActions" | jq

# Approve (parameter name must match the input parameter exactly)
curl -sS -u "user:$API_TOKEN" -X POST \
  "$JENKINS_URL/job/nodejs-pipeline/job/main/42/input/ProdDeploy/submit" \
  --data-urlencode 'json={"parameter":[{"name":"APPROVE","value":"true"}]}' \
  --data 'proceed=Approve'

20.9 Input patterns worth memorising

groovyPattern catalogue
// 1. Simple go/no-go restricted to a group
input message: 'Deploy to production?', ok: 'Deploy',
      submitter: 'release-managers',
      submitterParameter: 'APPROVED_BY'

// 2. Capture a value the pipeline then uses
def target = input(id: 'EnvChoice', message: 'Where?',
      parameters: [choice(name: 'ENV', choices: ['staging','prod'],
                          description: 'Target environment')])
echo "Deploying to ${target['ENV']}"

// 3. Timeout that FAILS FAST rather than aborting silently
timeout(time: 30, unit: 'MINUTES') {
    input message: 'Approve?'
}

// 4. Timeout that degrades gracefully (skip instead of fail)
def approved = false
try {
    timeout(time: 10, unit: 'MINUTES') {
        input message: 'Deploy now? (skips after 10 min)'
    }
    approved = true
} catch (err) {
    echo "No approval in time (${err}) - continuing without deploy"
}

// 5. Only ask when the change is risky
if (env.BRANCH_NAME == 'main' && currentBuild.number % 5 != 0) {
    input message: 'main branch - confirm'
}

20.10 Lab — approvals under pressure

🧪Lab 20.1 · Break the gate three ways 1. No submitter restriction. Remove submitter:, run the pipeline, and confirm any authenticated user can approve. That is a real audit finding.
2. Timeout with no handler. Set timeout(time: 1, unit: 'MINUTES') around the input, walk away, and observe the build result (ABORTED, not FAILED) and what post conditions fire.
3. Restart mid-approval. Start a build, wait for the prompt, then sudo systemctl restart jenkins. Log back in: the prompt is still there. This is durable pipeline state, and it's worth being able to describe it from memory.

20.11 Governance: who may approve what

Change typeApproval
Feature branch buildNone — automatic
Deploy to dev / stagingNone — automatic, self-service
Deploy to production (normal)One approval from the on-call engineer
Deploy to production (out of hours / Friday)Two approvals, one from release management
Schema migration or rollbackEngineering manager + DBA
HotfixAutomatic to staging, retro-approval logged
🚨Two approval anti-patterns
  • Approval on every commit. It becomes reflex clicking and provides no safety. Gate only consequential actions.
  • Self-approval. Enable Prevent self-approval or use a submitter group the author isn't in, otherwise the control is decorative.

20.12 More interview Q&A

Q6What happens to resources while waiting for input?
The build keeps its executor and its state is persisted, so it survives a controller restart. To avoid blocking an executor for hours, put the approval in a stage with a lightweight agent (or agent none at top level with a tiny agent for that stage), and set a timeout.
Q7Approval timed out — what build result do you get and how do you handle it?
ABORTED, via a FlowInterruptedException. If I want a different outcome I wrap the input in try/catch and decide: skip the deployment and continue, fail the build, or notify. I make sure the post block treats ABORTED explicitly rather than lumping it in with failure.
Q8How do you restrict who can approve a production deploy?
With the submitter parameter naming a user or group, plus submitterParameter to record who approved into the build record. I also enable "prevent self-approval" so the person who authored the change cannot be the one who approves it.
Q9How do you make approvals auditable?
Record the approver (submitterParameter), the timestamp, the artifact identifier and the environment in the build description, and ship that to the audit log or chat channel. The build record must be able to answer who deployed what, when, and on whose authority.
Q10Should production deploys be manual at all?
Mature teams gate on evidence rather than on a human: canary or blue-green with automated health checks and automatic rollback. Manual approval is right while that safety net is immature, and for genuinely irreversible actions like destructive schema changes. The goal is to earn the right to remove the gate.
