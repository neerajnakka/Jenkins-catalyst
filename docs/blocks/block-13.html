Block 13 · Real engineering

Nodes, agents, labels & tool installers

Goal: stop running builds on the controller. Add agents, route work with labels, and let Jenkins install toolchains for you.

13.1 First: set controller executors to 0

🚨The production rule Manage Jenkins → Nodes → Built-In Node → Configure → # of executors → 0. Builds on the controller can: exhaust memory and take the UI down, read every credential on the box, and break Jenkins for everyone. A controller orchestrates; agents execute.

13.2 Adding a permanent agent over SSH

  1. Prepare the agent machine (Ubuntu): install Java, git and whatever your builds need. Create the same user you'll connect as.
bashOn the new agent VM
sudo apt-get update -y
sudo apt-get install -y openjdk-21-jre-headless git docker.io
sudo useradd -m -s /bin/bash jenkins
sudo mkdir -p /home/jenkins/agent && sudo chown -R jenkins:jenkins /home/jenkins/agent

# The controller connects with an SSH key -> put its PUBLIC key here:
sudo -iu jenkins bash -c 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && \
  echo "ssh-ed25519 AAAA... jenkins@controller" > ~/.ssh/authorized_keys && \
  chmod 600 ~/.ssh/authorized_keys'
  1. Store the private key in Jenkins: Credentials → SSH Username with private key → ID agent-key.
  2. Register the node: Manage Jenkins → Nodes → New Node → name linux-1 → Permanent Agent:
    Remote root directory: /home/jenkins/agent
    Labels: linux docker node20 (space-separated)
    Usage: Only build jobs with label expressions matching this node
    Launch method: Launch agents via SSH → Host: private IP → Credentials: agent-key → Host Key Verification: Non verifying (or Known hosts file for production)
  3. Save and watch it connect. If it fails, click the node → Log — the launch log tells you exactly why.

13.3 Labels — how work is routed

groovyLabel expressions
agent { label 'docker' }                 // any agent labelled docker
agent { label 'linux && node20' }        // both labels
agent { label 'docker || aws' }          // either
agent { label 'linux && !experimental' } // linux, but not the experimental box
agent { label "${params.AGENT_LABEL}" }  // chosen at build time
🏷️Label naming conventions that scale Label by capability, not by hostname: linux, windows, docker, node20, python3.12, arm64, gpu. Then when a machine dies you replace it with another carrying the same labels and no pipeline changes. If you label by host (agent-7), every pipeline is hard-wired to a box.

13.4 Tool installers — no more "works on my machine"

Install the NodeJS plugin, then Manage Jenkins → Tools → NodeJS installations → Add NodeJS → name node20 → version NodeJS 20.x. Pipelines then reference it by name:

groovytools {} — auto-install + PATH injection
pipeline {
    agent { label 'linux' }

    tools {
        nodejs 'node20'          // name must match Manage Jenkins -> Tools
        // jdk   'jdk21'
        // maven 'maven3'
        // git   'Default'
    }

    stages {
        stage('Verify') {
            steps { sh 'node -v && npm -v' }   // PATH points at the installed tool
        }
    }
}
⚠️Installers download on every fresh agent Auto-installers fetch the toolchain on first use — great for correctness, slow on ephemeral agents. At scale, bake tools into the agent image (Packer/Ansible) and just declare them, or use Docker agents (next section).

13.5 Docker agents — the cleanest build environment

groovyRun stages inside containers
pipeline {
    agent none
    stages {
        stage('Node tests') {
            agent {
                docker {
                    image 'node:20-alpine'
                    args  '-v /var/lib/jenkins/.npm:/root/.npm'   // persist the npm cache
                    reuseNode true                                // stay on the same node/workspace
                }
            }
            steps { sh 'node -v && npm ci && npm run test:junit' }
        }

        stage('Python tests') {
            agent { docker { image 'python:3.12-slim'; reuseNode true } }
            steps { sh 'python -m venv venv && . venv/bin/activate && pip install -r requirements-dev.txt && pytest' }
        }

        stage('Build image') {
            agent { label 'docker' }          // needs the docker socket -> host agent
            steps { sh 'docker build -t app:$GIT_SHA .' }
        }
    }
}
🔁reuseNode matters By default a docker agent allocates a new workspace on a possibly different node. reuseNode true keeps the same node and workspace, so files from earlier stages are still there — usually what you want inside a single pipeline.

13.7 ✍️ Jenkinsfiles v13 — labelled + containerised

groovyPattern to add to BOTH apps
pipeline {
    agent none                       // nothing reserved for the whole run

    options { timestamps(); timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }

    stages {
        stage('Checkout') {
            agent { label 'linux' }
            steps { checkout scm }   // now correct: Multibranch supplies scm (Block 15)
        }

        // --- Node version of the test stage ---
        stage('Test (Node 20)') {
            agent { docker { image 'node:20-alpine'; args '-v /var/lib/jenkins/.npm:/root/.npm'; reuseNode true } }
            steps { sh 'npm ci && npm run test:junit' }
        }

        stage('Package & push') {
            agent { label 'docker' }
            steps {
                script {
                    def img = docker.build("${IMAGE}:${env.GIT_SHA}", '--pull .')
                    docker.withRegistry('https://index.docker.io/v1/', 'dockerhub-creds') {
                        img.push(env.GIT_SHA)
                    }
                }
            }
        }
    }

    post {
        always { junit testResults: 'reports/junit.xml', allowEmptyResults: true }
        cleanup { node('linux') { cleanWs() } }   // post has no agent -> ask for one
    }
}
⚠️The post-with-agent none trap When the pipeline uses agent none, a top-level post block has no node, so steps like sh or cleanWs fail with "Required context class hudson.FilePath is missing". Wrap them in node('label') { … } — as above.

13.8 ✅ Checklist

  • Controller executors set to 0 (or at least you know why you haven't yet).
  • One SSH agent connected, with meaningful labels.
  • NodeJS tool installer configured and referenced by tools { nodejs 'node20' }.
  • A stage ran inside node:20-alpine and you saw Jenkins pull the image.

13.9 💬 Interview Q&A

Q1Why shouldn't builds run on the controller?
Because the controller holds all credentials and serves the UI. A build running there can read every secret, consume all memory and take CI down for the whole company. I set the built-in node's executors to 0 and run everything on agents.
Q2How does Jenkins decide which agent runs a build?
By label expression. The pipeline declares agent { label 'docker && linux' }; Jenkins picks any connected agent whose labels satisfy it and has a free executor. If none qualifies the build waits in the queue.
Q3Permanent agents vs Docker agents vs Kubernetes?
Permanent agents are simple and give warm caches but need maintenance. Docker agents give a reproducible, version-pinned toolchain per stage with no host pollution — ideal for polyglot repos. Kubernetes agents auto-scale and are fully ephemeral, at the cost of setup complexity and cold-start time.
Q4An agent keeps going offline. How do you investigate?
Check the node's launch log in Jenkins first, then from the controller: network reachability, SSH credentials, Java present on the agent, disk space in the remote root directory, and clock skew. For flapping agents I look at journalctl on the agent and the controller's jenkins.log.
Q5What does the tools block do?
It references a tool configured under Manage Jenkins → Tools by name, installs it on the agent if needed, and prepends it to PATH for the duration of the pipeline — so node -v resolves to the exact version the project wants.

# On the agent: download the launcher and connect out to the controller
curl -sSLO http://<jenkins>:8080/jnlpJars/agent.jar
java -jar agent.jar \
  -url http://<jenkins>:8080/ \
  -secret <SECRET_FROM_NODE_PAGE> \
  -name linux-2 \

Description=Jenkins Inbound Agent
After=network.target
[Service]
User=jenkins

Restart=always
[Install]
WantedBy=multi-user.target
UNIT
sudo systemctl enable --now jenkins-agent

stage('Integration tests') {
    agent {
        docker {
            image 'node:20-alpine'
            args  '-v /var/lib/jenkins/.npm:/root/.npm ' +
                  '--network ci-net ' +                  // reach a sidecar by name
                  '-e TZ=UTC'
            reuseNode true
        }
    }
    steps {
        sh 'npm ci && npm run test:integration'
    }
}

13.12 Lab — capacity planning on one machine

🧪Lab 13.1 · How many executors should this box have?
bashMeasure, then decide
nproc                                  # vCPUs
free -g                                # RAM
# Rule of thumb for build agents:
#   executors ~= min(vCPU, floor(RAM_GB / 2))
#   4 vCPU / 8 GB  -> 4 executors (if builds are CPU bound, start with 2-3)
# A controller needs ~1 GB + 1 GB per 100 jobs for the UI alone.
Then deliberately over-subscribe: set 8 executors on a 2-CPU box, run 4 builds at once, and watch the queue and load average. You will feel why "more executors" is not automatically "faster".

13.13 Kubernetes agents (the scale answer)

groovyEphemeral pod agent — one pod per build, destroyed after
pipeline {
    agent {
        kubernetes {
            label 'nodejs-agent'
            defaultContainer 'node'
            yaml '''
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: node
    image: node:20-alpine
    command: ['cat']
    tty: true
    resources:
      requests: { cpu: "500m", memory: "1Gi" }
      limits:   { cpu: "2",    memory: "2Gi" }
  - name: dind
    image: docker:24-dind
    securityContext: { privileged: true }
'''
        }
    }
    stages {
        stage('Test')  { steps { container('node') { sh 'npm ci && npm test' } } }
        stage('Build') { steps { container('dind') { sh 'docker build -t app:$GIT_SHA .' } } }
    }
}
💡Why this matters at scale Every build gets a clean, disposable environment — no workspace drift, no "someone installed something weird on agent 3". The cost is pod start-up latency (typically 5–20 s) and the need to cache dependencies in a PVC or registry.

13.14 More interview Q&A

Q6SSH agent vs JNLP agent?
SSH agents are launched by the controller, so the agent needs a reachable SSH server — simple and firewall-friendly if the controller can reach it. JNLP/inbound agents dial out to the controller, which is the right choice when the agent sits behind NAT or a firewall. Both carry the same remoting traffic.
Q7How many executors per agent?
Roughly one per vCPU, bounded by RAM (≈2 GB per concurrent build for typical Node/Python work), and validated by watching load average and build duration. Over-subscribing makes every build slower and increases flakiness from resource contention.
Q8How do you keep agent toolchains consistent?
I don't rely on whatever happens to be installed: either the pipeline declares agent { docker { image 'node:20.17-alpine3.20' } } so the toolchain is pinned per stage, or the agent image is built by Packer/Ansible and version-controlled. Ad-hoc installs on long-lived agents always drift.
Q9What happens to running builds when an agent dies?
The remoting channel breaks, the build is marked as failed (or retried if you configured agent-loss retry conditions), and the queue reassigns waiting builds to another agent with the same label. With durable pipelines the state is preserved up to the last checkpoint.
Q10How would you autoscale Jenkins?
Kubernetes agents (one pod per build) or a cloud plugin (EC2, Azure VM agents) that provisions on demand and terminates idle agents. I'd set idle-retention to a few minutes, cap the maximum instances to control cost, and keep one small always-on agent for fast feedback.
