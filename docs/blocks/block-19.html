Deploy stages — shipping the image

Goal: take the exact image you scanned and push it to a running environment, verify it, and be able to roll back in one click.

19.1 Deployment strategies (know these four)

♻️ Recreate

Stop old, start new. Simplest, has downtime. Fine for dev.

🔄 Rolling

Replace instances gradually. No downtime, both versions briefly live — your API must tolerate that.

🔵🟢 Blue-Green

Run the new stack beside the old, switch the proxy/router when healthy. Instant rollback by switching back.

🐤 Canary

Send 5–10% of traffic to the new version, watch metrics, then ramp to 100%. Best for risky changes.

      interval: 30s

      interval: 30s

      retries: 3
      start_period: 15s
🎯The golden rule of deployment Deploy the same immutable artifact that passed tests and scans — referenced by digest or SHA tag, never rebuilt per environment. "Build once, deploy everywhere." Rebuilding for prod means prod is running code nobody tested.

19.3 Deploying over SSH

groovysshagent + docker compose pull/up + health check
stage('Deploy') {
    agent { label 'linux' }
    when { branch 'main' }
    steps {
        sshagent(credentials: ['deploy-key']) {          // SSH key credential, not a password
            sh """
                ssh -o StrictHostKeyChecking=no ${DEPLOY_USER}@${DEPLOY_HOST} <<'REMOTE'
                  set -e
                  cd ${DEPLOY_PATH}
                  export IMAGE_REPO=${IMAGE}
                  export IMAGE_TAG=${GIT_SHA}

                  docker compose pull                    # pull the exact scanned image
                  docker compose up -d --remove-orphans  # rolling replace
                  docker image prune -f

                  # wait for the healthcheck to go green
                  for i in \$(seq 1 30); do
                    if curl -fsS http://localhost:${APP_PORT}/health; then
                      echo "healthy after \${i}s"; exit 0
                    fi
                    sleep 2
                  done
                  echo "health check failed"; exit 1
REMOTE
            """
        }
    }
}
⚠️Two SSH gotchas
  • -o StrictHostKeyChecking=no skips host verification. Convenient, but it removes MITM protection — for production, pre-populate known_hosts for the deploy user instead.
  • The heredoc must be <<'REMOTE' (quoted) so the remote shell expands $IMAGE_TAG, not the local one. Unquoted heredocs are a classic source of "deployed the wrong tag".

19.4 Rollback

groovyOne-stage rollback using the previous successful build's tag
stage('Rollback on failure') {
    agent { label 'linux' }
    when { expression { currentBuild.currentResult == 'FAILURE' && params.AUTO_ROLLBACK } }
    steps {
        script {
            // lastSuccessfulBuild gives us the tag that was last known good
            def prev = currentBuild.previousSuccessfulBuild
            if (!prev) { error 'No previous successful build to roll back to' }
            def prevTag = prev.description?.trim() ?: prev.number.toString()
            echo "Rolling back to ${prevTag}"

            sshagent(credentials: ['deploy-key']) {
                sh """
                    ssh ${DEPLOY_USER}@${DEPLOY_HOST} \
                      "cd ${DEPLOY_PATH} && IMAGE_TAG=${prevTag} docker compose up -d --remove-orphans"
                """
            }
        }
        // let people know it happened
        currentBuild.description = "ROLLED BACK from ${env.GIT_SHA}"
    }
}

19.5 If you deploy to Kubernetes instead

groovyThe same stage, Kubernetes flavour
stage('Deploy to Kubernetes') {
    agent { label 'linux' }
    steps {
        withCredentials([file(credentialsId: 'kubeconfig', variable: 'KUBECONFIG')]) {
            sh """
                kubectl set image deployment/nodejs-app \
                        app=${IMAGE}:${GIT_SHA} --record -n ${params.ENV}
                kubectl rollout status deployment/nodejs-app -n ${params.ENV} --timeout=180s
            """
        }
    }
    post {
        failure {
            withCredentials([file(credentialsId: 'kubeconfig', variable: 'KUBECONFIG')]) {
                sh "kubectl rollout undo deployment/nodejs-app -n ${params.ENV}"
            }
        }
    }
}
💡Helm for real environments helm upgrade --install nodejs-app ./chart --set image.tag=${GIT_SHA} --namespace ${ENV} --atomic --timeout 5m — --atomic gives you automatic rollback on failure for free, which is why most teams prefer Helm over raw manifests.

19.6 ✅ Checklist

  • A deploy stage runs on main only and uses the SHA-tagged image.
  • The pipeline verifies /health after deployment and fails if it never becomes healthy.
  • Rollback path tested at least once (break the health check on purpose).
  • I can describe blue-green and canary, and when each is appropriate.

19.7 💬 Interview Q&A

Q1How does your pipeline deploy?
A deploy stage gated by when { branch 'main' } (and often an approval). It SSHes to the target with an SSH-agent credential, runs docker compose pull/up using the exact SHA tag that passed the scans, waits for the health endpoint, and on failure rolls back to the previous successful build's tag. The image is built once and promoted — never rebuilt per environment.
Q2How would you implement blue-green deployment in Jenkins?
Deploy the new version alongside the old on a different port or stack name, run health checks and smoke tests against it, then flip the load balancer or proxy target. Keep the old version running until the switch is verified, so rollback is just flipping back. In Kubernetes this is two deployments plus a service selector change; on VMs, two compose projects plus an nginx upstream swap.
Q3What's your rollback strategy?
Every deployment references an immutable tag, so rollback means redeploying the previous successful build's tag — I read it from currentBuild.previousSuccessfulBuild. On Kubernetes kubectl rollout undo or Helm's --atomic does it automatically. Crucially, database migrations must be backward compatible, otherwise rollback is impossible.
Q4Why build once and promote, instead of building per environment?
Building per environment means production runs an artifact that was never tested — a different dependency resolution, a different base image patch level. Promoting one immutable artifact makes "it worked in staging" meaningful and makes rollback deterministic.

19.8 Under the hood — the artifact lifecycle

⚠️Artifacts are not a package manager Jenkins stores artifacts on the controller's disk, forever, with no de-duplication. Using it as your long-term release store will fill $JENKINS_HOME and slow down backups. For real releases, push to a registry or artifact repository (Nexus, Artifactory, S3, GitHub Releases) and use Jenkins artifacts for build-scoped evidence only.
groovyFingerprints and cross-job artifact reuse
pipeline {
    agent { label 'linux' }
    options {
        // keep the controller healthy: only 20 builds' worth of artifacts
        buildDiscarder(logRotator(
            numToKeepStr: '40', artifactNumToKeepStr: '20'))
    }
    stages {
        stage('Build') {
            steps {
                sh 'npm ci && npm pack'
                archiveArtifacts(
                    artifacts: '*.tgz',
                    fingerprint: true,          // enable traceability
                    onlyIfSuccessful: true)
            }
        }
        stage('Promote') {
            when { branch 'main' }
            steps {
                // pull the exact artifact another job produced
                copyArtifacts(
                    projectName: 'nodejs-pipeline/main',
                    selector: lastSuccessful(),
                    filter: '*.tgz',
                    target: 'incoming/')
                sh 'ls -la incoming/'
            }
        }
    }
}

19.10 Lab — promote a build through environments

🧪Lab 19.1 · Build once, promote the same artifact The discipline that separates real CI/CD from "rebuild per environment":
groovyOne artifact, three environments
pipeline {
    agent { label 'docker' }
    parameters {
        choice(name: 'TARGET_ENV', choices: ['staging', 'prod'], description: 'Where to deploy')
        string(name: 'BUILD_TO_PROMOTE', defaultValue: '', description: 'Empty = this build')
    }
    environment { REGISTRY = 'https://index.docker.io/v1/' }
    stages {
        stage('Resolve image') {
            steps {
                script {
                    if (params.BUILD_TO_PROMOTE?.trim()) {
                        copyArtifacts(
                            projectName: env.JOB_NAME,
                            selector: specific(params.BUILD_TO_PROMOTE),
                            filter: 'image-tag.txt')
                        env.IMAGE_TAG = readFile('image-tag.txt').trim()
                        echo "PROMOTING already-built image tag ${env.IMAGE_TAG}"
                    } else {
                        env.IMAGE_TAG = env.GIT_SHA
                        writeFile file: 'image-tag.txt', text: env.IMAGE_TAG
                        sh 'docker build -t $DOCKER_USER/app:$IMAGE_TAG .'
                        archiveArtifacts artifacts: 'image-tag.txt', fingerprint: true
                    }
                }
            }
        }
        stage('Deploy') { steps { sh "./deploy.sh ${params.TARGET_ENV} ${env.IMAGE_TAG}" } }
    }
    post { success { archiveArtifacts artifacts: 'deploy-*.log', allowEmptyArchive: true } }
}
Run it twice: once with an empty BUILD_TO_PROMOTE (builds and archives), then again with that build number (reuses the identical tag). Nothing is rebuilt — that is the whole point.

19.12 More interview Q&A

Q6How do you promote the same artifact through environments?
Build once and record an immutable identifier (the git SHA or the image digest), then deploy that exact identifier to staging and production. Rebuilding per environment produces a different artifact, so what you tested is not what you shipped. Promotion reads the recorded identifier from the build's artifacts or from the registry.
Q7What is a fingerprint and why do you enable it?
A checksum Jenkins records for an archived file. It lets you answer "which build produced this file?" and "which builds consumed it?" — essential for traceability and for copyArtifacts relationships between upstream and downstream jobs.
Q8JENKINS_HOME is 90% full. What do you do?
Find the offenders with du -sh /var/lib/jenkins/jobs/* | sort -h, tighten the discard policies (especially artifact retention), clean old workspaces with cleanWs, and move real release artifacts to external storage. Then make it structural: a global discarder or JCasC defaults so new jobs inherit sane retention.
Q9How do you handle large binary artifacts (hundreds of MB)?
Don't put them in Jenkins at all. Push to S3, Nexus, Artifactory or the container registry, and archive only a small manifest or a URL file. Jenkins artifacts are for reports and small packages; anything large belongs in a system designed for it.
Q10How do you keep artifacts after deleting the build?
You can't — the archive lives under the build directory. If a build record is discarded, its artifacts go too. That's why anything with retention or compliance value must be copied to external storage inside the pipeline, in the same stage that archives it.
