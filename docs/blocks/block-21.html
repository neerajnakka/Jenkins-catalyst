Block 21 · DevSecOps & scale

Parallel, matrix, timeouts, retries & locks

Goal: make pipelines fast (parallelism, matrix) and safe under concurrency (timeouts, retries, locks, milestones).

21.1 Parallel stages

groovyDeclarative parallel block
pipeline {
    agent none

    stages {
        stage('Checkout') {
            agent { label 'linux' }
            steps { checkout scm }
        }

        stage('Quality & Security') {
            failFast true                       // one failure cancels the siblings
            parallel {
                stage('Unit tests') {
                    agent { label 'linux' }
                    steps { sh 'npm run test:junit' }
                }
                stage('Lint') {
                    agent { label 'linux' }
                    steps { sh 'npm run lint' }
                }
                stage('Dependency scan') {
                    agent { label 'linux' }
                    steps { sh 'trivy fs --exit-code 1 --severity HIGH,CRITICAL .' }
                }
                stage('Secret scan') {
                    agent { label 'linux' }
                    steps { sh 'gitleaks detect --source . --redact' }
                }
            }
        }

        stage('Package') {
            agent { label 'docker' }
            steps { sh 'docker build -t app:$GIT_SHA .' }
        }
    }
}
⚠️Parallel needs executors Four parallel stages need four free executors (or four agents). With two executors they simply queue and you gain nothing — parallelism is bought with infrastructure, not syntax. Check Manage Jenkins → Nodes before promising a 4× speed-up.

21.3 Matrix — the same job across many combinations

groovyMatrix with axes, excludes and per-cell behaviour
pipeline {
    agent none

    stages {
        stage('Cross-platform tests') {
            matrix {
                axes {
                    axis { name 'NODE_VERSION'; values '18', '20', '22' }
                    axis { name 'OS';           values 'linux', 'alpine' }
                }
                excludes {
                    exclude {   // Node 18 on alpine isn't supported by this project
                        axis { name 'NODE_VERSION'; values '18' }
                        axis { name 'OS';           values 'alpine' }
                    }
                }
                agent { docker { image "node:${NODE_VERSION}-${OS}"; reuseNode true } }
                stages {
                    stage('Test') {
                        steps {
                            echo "Testing on Node ${NODE_VERSION} / ${OS}"
                            sh 'node -v && npm ci && npm run test:junit'
                        }
                    }
                }
            }
        }
    }
}
🧪Real-world matrix uses Test across Node/Python versions, OSes and architectures; run the same smoke suite against multiple target environments; build multi-arch images (linux/amd64, linux/arm64) in parallel and combine them into one manifest.

21.4 Timeouts, retries and waiting

groovyThe resilience toolkit
// Pipeline-wide safety net
options { timeout(time: 45, unit: 'MINUTES') }

// Per-stage override
stage('Long scan') {
    options { timeout(time: 15, unit: 'MINUTES') }
    steps { sh 'trivy image --exit-code 1 app:latest' }
}

steps {
    retry(3) {                                   // retry the exact same block, 3 times
        sh 'docker pull node:20-alpine'
    }

    retry(count: 5, conditions: [               // only retry on specific causes
        agent(), nonresumable()
    ]) {
        node('flaky-agent') { sh 'true' }
    }

    waitUntil {                                  // poll until the block returns true
        def ok = sh(script: 'curl -fsS http://localhost:3000/health', returnStatus: true) == 0
        sleep(time: 3, unit: 'SECONDS')
        return ok
    }

    timeout(time: 2, unit: 'MINUTES') {          // hard cap on any of the above
        waitUntil { sh(script: 'curl -fsS http://localhost:3000/health', returnStatus: true) == 0 }
    }

    sleep(time: 10, unit: 'SECONDS')             // simple pause
}

21.5 Locks — serialising shared resources

groovyLockable Resources plugin
// Define resources: Manage Jenkins -> System -> Lockable Resources
//   Name: deploy-prod     (quantity 1)
//   Name: test-database   (quantity 3)

stage('Deploy to production') {
    steps {
        lock(resource: 'deploy-prod') {          // only one prod deploy at a time
            sh './deploy.sh prod'
        }
    }
}

stage('Integration tests') {
    steps {
        lock(label: 'test-database', quantity: 1, variable: 'DB_RESOURCE') {
            echo "Using database resource: ${env.DB_RESOURCE}"
            sh 'pytest tests/integration'
        }
    }
}

// Inverse: block concurrent runs of THIS job
options { disableConcurrentBuilds() }

// Or: kill the older build when a new one starts
options {
    disableConcurrentBuilds(abortPrevious: true)
}

21.6 Milestones — correct ordering of concurrent builds

groovyMilestone + lock for sane deploy ordering
stage('Deploy') {
    steps {
        milestone 1                       // build #5 reaches this first
        lock(resource: 'deploy-prod') {
            milestone 2                   // older builds that reach here are cancelled
            sh './deploy.sh'
        }
    }
}

Two pushes land close together. Without milestones, the older build could deploy after the newer one and silently roll you back. milestone cancels any build that is behind — exactly the semantics you want for a deploy stage.

21.7 ✅ Checklist

  • A parallel block runs 3+ checks simultaneously and failFast behaves as expected.
  • A matrix runs the same tests across multiple Node/Python versions.
  • Every long-running stage has a timeout; flaky network steps have retry.
  • Prod deploy is protected by a lock (and ideally a milestone).

21.8 💬 Interview Q&A

Q1How do you speed up a slow Jenkins pipeline?
Run independent work in a parallel block (tests, lint, scans), put the fastest and most-likely-to-fail checks first, use a matrix instead of sequential loops, cache dependencies and Docker layers, and make sure there are enough executors to actually run things concurrently.
Q2How do you handle flaky steps?
retry(n) for genuinely transient operations like registry pulls or network calls, and waitUntil for polling a service until it's ready. I do not use retry to hide flaky tests — those get quarantined and fixed, because retry only delays the failure.
Q3How do you prevent two deployments running at once?
lock(resource: 'deploy-prod') from the Lockable Resources plugin so only one build holds the deploy slot. Combined with milestone, an older build that arrives late is cancelled instead of rolling the environment backwards.
Q4What does disableConcurrentBuilds do, and what's the alternative?
It queues new runs while one is in progress. With abortPrevious: true the older run is cancelled instead — usually what you want on a fast-moving main branch, while for deployments you'd prefer queuing so every release is actually attempted.
Q5When would you use matrix over parallel?
When the branches are the same work across different dimensions — Node 18/20/22 × linux/alpine. Matrix gives me a compact declaration, automatic naming, exclusions for unsupported combinations, and per-cell results in one view, instead of me hand-writing six near-identical parallel stages.

21.8 Under the hood — the master/agent file path contract

⚠️The single most expensive mistake in Jenkins pipelines Using File, new FileOutputStream, Paths.get or Files.* in pipeline code operates on the controller's filesystem, not the agent's workspace. It appears to work when you test on a single-machine install, then silently reads or writes the wrong machine in production — and can corrupt $JENKINS_HOME. Always use pipeline steps: readFile, writeFile, sh, findFiles, archiveArtifacts.
Instead of this (Java/Groovy)Use this (pipeline step)
new File(path).textreadFile(path)
new File(path).write(...)writeFile(file:…, text:…) or sh 'cat > …'
file.eachLine {}readFile(...).split('\n') or sh '…' returning text
new File(p).exists()fileExists(p)
dir.listFiles()findFiles(glob: '**/*.json')
new File(p).delete()sh 'rm -f …' or deleteDir()
new XmlSlurper().parse(f)readJSON / readMavenPom / parse with sh 'jq'
groovyfindFiles — the agent-safe way to enumerate
steps {
    script {
        def reports = findFiles(glob: '**/coverage/*.xml')
        echo "Found ${reports.length} coverage reports"
        reports.each { f ->
            echo "${f.path} (${f.length} bytes, dir=${f.directory})"
        }
        if (reports.length == 0) { error 'No coverage report - failing fast' }
    }
}

groovyThe @NonCPS escape hatch, used correctly
// Runs as plain Groovy on the controller -- NO pipeline steps allowed inside.
// Perfect for string/JSON munging that would otherwise confuse CPS.
@NonCPS
String renderMarkdownTable(String json) {
    def rows = new groovy.json.JsonSlurper().parseText(json)
    def sb = new StringBuilder()
    sb.append('| Service | Version |\n|---|---|\n')
    rows.each { r -> sb.append("| ${r.name} | ${r.version} |\n") }
    return sb.toString()                       // return a plain String
}

pipeline {
    agent any
    stages {
        stage('Report') {
            steps {
                script {
                    def raw = sh(script: 'cat versions.json', returnStdout: true).trim()
                    def table = renderMarkdownTable(raw)     // call it from CPS code
                    writeFile file: 'report.md', text: table
                }
            }
        }
    }
}
🚨Rule Inside an @NonCPS method you may not call sh, echo, readFile or any other pipeline step — they will throw or silently do nothing. Keep @NonCPS for pure computation, and do the I/O in CPS code.

21.10 Lab — reproduce a real production failure

🧪Lab 21.2 · The file that isn't there Run this on a controller with a separate agent:
groovyDeliberately wrong, then corrected
pipeline {
    agent { label 'linux' }                 // runs on the AGENT
    stages {
        stage('Broken') {
            steps {
                script {
                    // WRONG: touches the CONTROLLER filesystem
                    def f = new File('/tmp/agent-proof.txt')
                    f.text = 'written from the pipeline'
                    echo "exists? ${f.exists()}"       // true -- on the controller!
                }
            }
        }
        stage('Fixed') {
            steps {
                // RIGHT: runs where the workspace is
                sh 'echo "written from the pipeline" > /tmp/agent-proof.txt && cat /tmp/agent-proof.txt'
                writeFile file: 'proof.txt', text: 'written via writeFile'
                echo readFile('proof.txt')
            }
        }
    }
}
Then SSH to the agent: /tmp/agent-proof.txt exists there. SSH to the controller: it does not. Meanwhile the new File version created the file on the controller. Once you have seen this once, you will never use new File in a pipeline again.

21.12 More interview Q&A

Q6Why must pipeline variables be serializable?
Because durable pipelines persist state to disk at every checkpoint so a build can survive a controller restart. Any object captured in the CPS state — including exceptions you let escape a node block — must be serializable. Non-serializable objects cause "java.io.NotSerializableException" at exactly the worst moment.
Q7When do you reach for @NonCPS?
Only for pure computation that CPS cannot express — Java streams, regex-heavy string work, JSON/XML parsing — and never for anything that calls pipeline steps. It runs as ordinary Groovy on the controller, which also means it must be cheap and must not touch the filesystem.
Q8How do you debug a pipeline that only fails on the agent?
Reproduce inside the same container with docker run --rm -it -v $PWD:/w -w /w node:20-alpine sh, dump the environment with sh 'env | sort', compare users and paths (id, pwd), and check that anything the build needs is actually installed in the image rather than on the long-lived host.
Q9How do you make a slow pipeline faster without adding risk?
Measure first — the Pipeline Timing or Blue Ocean view shows where the minutes go. Then parallelise independent stages, cache dependencies outside the workspace, order stages cheapest-first so failures surface in under a minute, and skip work that the changed paths cannot affect.
Q10What is the risk of running builds on the controller?
Everything the build does runs with controller privileges, has access to $JENKINS_HOME and all credentials, and competes with the UI for CPU and memory — a runaway build can take CI down for everyone. I set the built-in node to zero executors and run all builds on agents.
