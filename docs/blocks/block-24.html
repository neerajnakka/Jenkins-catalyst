24.1 The 60-second pitch (memorise this)

script"Tell me about your Jenkins project"
"I built a complete CI/CD platform on Jenkins LTS running on an AWS EC2 Ubuntu
instance. It has two production-shaped services - an Express API and a Flask API -
each with its own Jenkinsfile in a monorepo.

On every push, a GitHub webhook triggers the pipeline: Jenkins checks out the
branch, installs dependencies deterministically (npm ci / pinned requirements),
runs unit tests with coverage gates, and publishes JUnit and coverage reports.

Then the DevSecOps layer: SonarQube SAST with a quality gate that blocks bad
code, Trivy and npm audit / pip-audit for dependency CVEs, gitleaks for secrets,
and a container scan plus SBOM generation and cosign signing before the image is
pushed to Docker Hub tagged with the Git SHA.

Deployment goes over SSH with docker compose, gated by a manual approval and a
health check, with automatic rollback to the previous successful build.

The infrastructure side: the controller has zero executors and dispatches to
labelled agents, reusable logic lives in a shared library, Multibranch
pipelines build every branch and PR automatically, access is controlled with
Role-Based Authorization, and the whole thing is backed up nightly with a
tested restore.

Everything is in Git - Jenkinsfiles, shared library, Dockerfiles, plugin
manifest - so I can rebuild the entire CI system from scratch."
🎯Why this pitch works It names the stack, the trigger, the quality gates, the security layers, the deployment and rollback, and the operational concerns — in under a minute. Each clause is a hook the interviewer will pull on, and you have a block of this document behind every one.

24.2 Rapid-fire: 25 questions you must answer instantly

1Controller vs agent?
Controller orchestrates and stores everything; agents execute builds. Controller executors = 0 in production.
2Executor?
A slot for one concurrent build. N executors = N parallel builds on that node.
3Mandatory declarative blocks?
pipeline, agent, stages; each stage needs steps.
4Declarative vs Scripted?
Declarative is structured and validated; scripted is raw Groovy. Use declarative, escape to script { }.
5Where is data stored?
$JENKINS_HOME = /var/lib/jenkins.
6How do you generate step syntax?
Snippet Generator at /pipeline-syntax/; directives at /directive-generator/.
7What is Replay for?
Rerun a build with an edited Jenkinsfile without committing.
8npm ci vs npm install?
ci installs exactly from the lockfile and fails on mismatch — deterministic, therefore correct for CI.
9SUCCESS vs UNSTABLE vs FAILURE?
Passed / completed but below quality bar / errored.
10How do you publish test results?
junit testResults: 'reports/junit.xml' plus recordCoverage.
11env.X vs params.X?
Environment variables are set by/in the pipeline; parameters are user inputs shown in "Build with Parameters".
12How are secrets stored?
Credentials store, encrypted with master.key, referenced by ID, injected with withCredentials, masked in logs.
13How do you fail a build deliberately?
error 'message', or a non-zero exit from sh.
14Your image tagging strategy?
Git SHA (immutable) + build number + latest for dev only. Deploy by SHA/digest.
15Why not give Jenkins the Docker socket?
It's root-equivalent. Prefer Kaniko, rootless BuildKit, or ephemeral agents.
16Webhook vs polling?
Webhook = instant push notification; polling = Jenkins asks periodically. Webhooks if reachable, polling if not.
17What does H mean in cron?
A hash of the job name that staggers schedules to avoid a thundering herd.
18always vs cleanup?
Both always run; cleanup runs last, even if always failed.
19How do you implement RBAC?
Role Strategy plugin: global roles, item roles by name pattern/folder, agent roles; least privilege.
20What is a shared library?
A Git repo of Groovy (vars/ → steps, src/ → classes) imported with @Library('name@version') _.
21Multibranch pipeline?
One job that discovers branches/PRs and builds each one's Jenkinsfile automatically.
22SAST vs SCA vs DAST?
Source code / dependencies / running application.
23What is an SBOM?
A machine-readable inventory of everything in your artifact (CycloneDX/SPDX) — instant CVE impact answers.
24How do you add a manual approval?
input inside timeout(), restricted by submitter, in a stage with agent none.
25How do you stop two deploys colliding?
lock(resource: 'deploy-prod') plus milestone for ordering.

24.3 Scenario questions (the ones that decide the offer)

S1"Production is down after a deploy that passed all tests. What do you do?"
Roll back first, diagnose second: redeploy the previous successful build's tag (kubectl rollout undo / compose with the old tag) to restore service. Then read the deploy log and health-check output, compare the deployed digest with what was scanned, and check for a migration or config change. Then add the missing guard — smoke tests after deploy, a canary step, or a DB-migration compatibility check — so the same class of failure can't ship again.
S2"The team complains CI takes 40 minutes. Fix it."
Measure first: Timestamper + Stage View to find the slow stages. Then run independent work in parallel (tests, lint, scans), cache dependencies outside the workspace and Docker layers with --cache-from, put the fastest failing checks first, and make sure enough executors exist to actually parallelise. Finally cap it with per-stage timeouts so a hang never costs 40 minutes again.
S3"Developers can see other teams' credentials. How?"
Because credentials are global and everyone has read/configure rights. Fix: folders per team, credentials stored in folder domains, item roles scoped to folder patterns, anonymous access off, and an audit trail. Then rotate anything that was exposed.
S4"A secret was pushed to Git. Now what?"
Rotate the secret first — assume it's compromised the moment it's public, because deleting the commit doesn't un-leak it. Then purge it from history (git filter-repo or BFG) and force-push with team coordination. Then prevent recurrence: gitleaks as a pre-commit hook and a blocking CI gate.
S5"You need to onboard 30 repositories. Manual job creation?"
No. A GitHub Organization folder with the Branch Source plugin scans the org and creates multibranch jobs for every repo containing a Jenkinsfile. Standardise on a shared library (standardPipeline { }) so each repo's Jenkinsfile is a few lines, and use JCasC plus a plugin manifest to make the controller itself reproducible.
S6"Jenkins is down. How long until you're back?"
Restore from the nightly backup onto a fresh box (or apply JCasC + the plugin manifest), restore master.key, start, verify agents reconnect and one pipeline per project runs. Because Jenkinsfiles live in Git, no pipeline logic is ever lost — the recovery target is minutes, not days, and I test the restore regularly.
S7"How would you convince a team to adopt security scanning?"
Roll it out in phases so it never feels like a blocker: report-only first (visibility), then a soft gate (unstable), then a hard gate restricted to new code. Show the numbers — issues found before release vs. after. The pitch is "we catch it in 3 minutes instead of 3 weeks", not "compliance says so".

24.7 Final checklist — you are ready when…

  • You can write a full declarative Jenkinsfile from a blank file, without the Snippet Generator, except for exotic steps.
  • You can explain every stage of your pipeline and why it is there.
  • You have personally broken and fixed: a failing test, a failed quality gate, a CVE finding, a secret leak, a bad deploy, and a locked-out admin.
  • You can whiteboard the architecture: controller → labelled agents → registry → target server, with the security gates marked.
  • You can deliver the 60-second pitch without notes.
  • You can say "I don't know, but here's how I'd find out" — and mean it.
🏁Where to go next Once this is second nature, the natural next steps are: Kubernetes agents (ephemeral, auto-scaling), GitOps (ArgoCD pulling the image your Jenkins built), Terraform for the infrastructure, and GitHub Actions for contrast — knowing both makes you the person who chooses the right tool rather than the one who knows one tool.

24.8 The whiteboard round — draw this

💡How to narrate it "Developer pushes to a feature branch. GitHub Branch Source discovers it and the Multibranch job builds the Jenkinsfile from that branch — pipeline as code. Cheap stages run in parallel for fast feedback: build, lint, dependency scanning and secret scanning. Then tests with coverage, then SonarQube analysis with a quality gate that fails the build. On main we build a container, scan it, generate an SBOM, push an immutable tag to Docker Hub, deploy to staging behind an input gate, and finally deploy to production under a lock with milestones so concurrent builds can't interleave. Whatever happens, the post block publishes reports, notifies the team and cleans the workspace."

24.11 Thirty-day plan after this course

  1. Week 1 — Rebuild from scratch. Tear down your EC2 controller and rebuild it from your ec2-install.sh + jenkins.yaml + plugins.txt. Time it.
  2. Week 2 — Kubernetes agents. Add a k8s cloud (minikube is fine) and move the Node and Python builds to pod templates.
  3. Week 3 — Real delivery. Deploy both apps to a real target (EC2 with compose, or a k8s cluster) with blue-green or rolling updates and automated rollback.
  4. Week 4 — Prove it. Add synthetic monitoring post-deploy, publish a CI dashboard (build time, success rate, MTTR), and write two blog posts explaining a concept from this guide.
💡The highest-leverage habit Write up one Jenkins problem you hit and solved, every week, in public. Interviewers Google your name; a repo plus three clear write-ups beats any certification for demonstrating that you can operate the thing.

24.12 Final checklist before any Jenkins interview

  • I can explain the difference between declarative and scripted pipeline, and when I'd choose each.
  • I can write a full declarative pipeline from memory, including agent, environment, options, stages, post.
  • I know how credentials are stored, injected and masked — and how masking can be defeated.
  • I can explain CPS transformation, why variables must be serializable, and what @NonCPS is for.
  • I know how a Multibranch scan works and what lightweight checkout implies.
  • I can describe the agent model: labels, executors, SSH vs JNLP vs Docker vs Kubernetes.
  • I can name each DevSecOps stage and justify its position in the pipeline.
  • I can draw the whole delivery flow on a whiteboard and narrate it in under three minutes.
  • I have a story for "tell me about a time CI broke in production and how you fixed it".
  • I can say what I'd improve in their pipeline, and I have two questions ready for them.
🎤Closing advice Depth beats breadth. An interviewer will happily trade ten tool names for one detailed, honest story about a pipeline you designed, a failure you diagnosed, and the trade-off you made. You now have both apps, the library, the gates and the operational runbook — talk about those, and the conversation will be about engineering rather than trivia. Good luck.
