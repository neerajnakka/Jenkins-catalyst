Block 15 · Real engineering

Multibranch Pipelines

Goal: one job definition that automatically builds every branch and pull request — with the Jenkinsfile living in the branch, so CI evolves with the code.

15.1 What changes compared to a normal Pipeline job

Pipeline jobMultibranch Pipeline
JobsOne job, one branch (hard-coded)One folder, auto-created sub-job per branch/PR
BranchFixed in job configDiscovered by scanning the repo
JenkinsfileAny path you nameIn the repo root by default (configurable)
New branchSomeone creates a job by handAppears automatically on the next scan
Deleted branchJob lingers foreverRemoved by the orphaned-item strategy
PR validationManual setupBuilt-in (Branch Source plugin)

15.2 Creating one (GitHub Branch Source)

  1. Install GitHub Branch Source (github-branch-source).
  2. New Item → Multibranch Pipeline → name app-pipeline.
  3. Branch Sources → Add source → GitHub → Credentials: github-pat (needs a PAT, not SSH — it uses the API) → Repository HTTPS URL → Validate.
  4. Behaviours → add: Discover branches (all or "only branches that are also filed as PRs"), Discover pull requests from origin (merging the PR with the target branch), Filter by name (with wildcards) → main develop feature/*.
  5. Build Configuration → Mode: by Jenkinsfile → Script Path: nodejs-app/Jenkinsfile.
  6. Scan Repository Triggers → tick Periodically if not otherwise run (e.g. 1 hour) and/or Scan by webhook with a trigger token.
  7. Orphaned Item Strategy → tick Discard old items → keep 5 (stops deleted branches leaving zombie jobs).
  8. Save → Scan Repository Now → watch each branch become a job.
⚠️Script Path is per-multibranch-job, not per branch Since both apps live in one repo, create two multibranch jobs: nodejs-pipeline with Script Path nodejs-app/Jenkinsfile, and python-pipeline with python-app/Jenkinsfile. (A Jenkinsfile in the repo root is the common default; we keep them beside their app on purpose.)

15.3 Branch-aware pipeline logic

groovyenv.BRANCH_NAME · when { branch } · changeRequest
pipeline {
    agent none

    stages {
        stage('Info') {
            agent { label 'linux' }
            steps {
                echo "Branch      : ${env.BRANCH_NAME}"     // 'main', 'feature/login', 'PR-42'
                echo "Is PR build : ${env.CHANGE_ID ? 'yes' : 'no'}"
                echo "PR target   : ${env.CHANGE_TARGET ?: 'n/a'}"
                echo "Job name    : ${env.JOB_NAME}"        // 'app-pipeline/feature%2Flogin'
            }
        }

        stage('Test') { /* always runs */ }

        stage('Push image') {
            when {
                anyOf {
                    branch 'main'
                    branch 'develop'
                }
            }
            steps { echo 'pushing image' }
        }

        stage('Deploy to prod') {
            when {
                allOf {
                    branch 'main'
                    not { changeRequest() }          // never deploy from a PR build
                }
            }
            steps { echo 'deploying' }
        }

        stage('PR feedback') {
            when { changeRequest() }                 // only for pull requests
            steps {
                echo "Validating PR #${env.CHANGE_ID} targeting ${env.CHANGE_TARGET}"
                // Block 20: post the result back to the PR
            }
        }
    }
}

15.4 Automating the scan (webhook for multibranch)

bashGitHub webhook for branch indexing
# GitHub -> Settings -> Webhooks:
#   Payload URL : http://<JENKINS>:8080/github-webhook/
#   Content type: application/json
#   Events      : Push, Pull request          <-- PR needed for PR builds

# In the multibranch job: Scan Repository Triggers -> "Scan by webhook"
#   Trigger token: SCAN_ME   (or let the plugin generate one)

# Test the scan endpoint manually:
curl -X POST -u user:$TOKEN \
  "http://<JENKINS>:8080/job/nodejs-pipeline/build?token=SCAN_ME"
🔁Indexing vs building A scan (indexing) asks GitHub "which branches/PRs exist?" and creates/updates/removes sub-jobs. A build runs a Jenkinsfile. A push webhook triggers both: scan first, then build the affected branch.

15.5 Organization folders (enterprise scale)

New Item → GitHub Organization → point it at your GitHub org → Jenkins scans every repository, creates a multibranch job for each repo containing a Jenkinsfile, and keeps them in sync automatically. One configuration, hundreds of repos, zero manual job creation. This is what platform teams actually run.

15.6 ✅ Checklist

  • Two multibranch jobs exist and discover your branches.
  • Created a feature/test-ci branch, pushed, and saw a job appear automatically.
  • Deleted that branch, re-scanned, and watched the job disappear (orphaned strategy).
  • A PR build ran and printed env.CHANGE_ID.
  • The Push image stage is skipped on feature branches and runs on main.

15.7 💬 Interview Q&A

Q1What is a Multibranch Pipeline?
A job that scans a repository and automatically creates a sub-pipeline for each branch or pull request that contains a Jenkinsfile. Branch discovery, PR validation and cleanup of deleted branches are handled by the Branch Source plugin instead of by humans creating jobs.
Q2How do you run different steps on different branches?
With when { branch 'main' }, when { changeRequest() } and the environment variables BRANCH_NAME, CHANGE_ID and CHANGE_TARGET. Typically: tests on every branch, image push on main/develop, deployment only from main and never from a PR build.
Q3How do you stop deleted branches leaving dead jobs?
Configure the multibranch job's Orphaned Item Strategy to discard old items after N days (or immediately). Otherwise every short-lived feature branch leaves a job behind forever.
Q4Why does Multibranch need checkout scm instead of a hard-coded branch?
Because Jenkins injects the SCM configuration for whichever branch it is currently building. If I hard-code main in the Jenkinsfile, every branch build would check out main — so the feature branch would never actually be tested.
Q5Scanning found no branches — what do you check?
The credentials (Multibranch uses the GitHub API, so it needs a PAT with repo scope), the repository URL, the behaviours (is branch discovery actually enabled?), and the Script Path — if the Jenkinsfile isn't at the configured path, the branch is detected but not built.

15.8 Under the hood — scanning and lightweight checkout

A Multibranch job is a folder that holds child jobs. The scan (indexing) does three things:

  1. Enumerate branches and pull requests via the Git provider API — which is why it needs a personal access token, not just an SSH key.
  2. Lightweight checkout — fetch each candidate's Jenkinsfile straight from the API, with no workspace and no executor, just to see whether the branch is buildable.
  3. Reconcile — create a child job per qualifying branch, update existing ones, and apply the orphaned-item strategy to remove dead ones.
⚠️Lightweight checkout has a consequence Because the Jenkinsfile is read via the API, its environment is not a full workspace. Anything that needs a real clone during evaluation — for example loading another file from the repo — fails at scan time. If you need that, disable lightweight checkout in the job's Branch Source behaviours.

15.11 Jenkinsfile patterns for branches and PRs

groovyA complete branch-aware policy
pipeline {
    agent none

    options {
        // keep PR builds short-lived; keep release branches longer
        buildDiscarder(logRotator(numToKeepStr: '50'))
        timeout(time: 45, unit: 'MINUTES')
    }

    stages {
        stage('Build')  { agent { label 'linux' };  steps { sh './build.sh' } }

        stage('Test')   { agent { label 'linux' };  steps { sh './test.sh' } }

        stage('Full security scans') {
            when { not { changeRequest() } }      // full scans on branches, quick ones on PRs
            steps { sh './scan.sh --full' }
        }

        stage('Push image') {
            when { anyOf { branch 'main'; branch 'develop'; branch 'release/*' } }
            steps { sh './push.sh' }
        }

        stage('Deploy') {
            when {
                allOf {
                    branch 'main'
                    not { changeRequest() }
                }
            }
            steps { sh './deploy.sh' }
        }
    }

    post {
        always {
            script {
                // make the folder readable at a glance
                currentBuild.description = changeRequest()
                    ? "PR-${env.CHANGE_ID} -> ${env.CHANGE_TARGET}"
                    : "${env.BRANCH_NAME} - ${env.GIT_SHA}"
            }
        }
    }
}
📌Noteoptions { } is evaluated before the pipeline body, so calling changeRequest() inside it works only in recent Jenkins versions. If yours complains, move the conditional into the stages as shown above.

15.12 More interview Q&A

Q6How do you build pull requests safely?
Enable PR discovery with a trust policy: PRs from forks don't get credentials or write access, and I keep a separate, restricted credential scope for untrusted builds. PR builds run tests and scans but never deploy and never push images.
Q7What is the orphaned item strategy?
The policy for child jobs whose branch no longer exists — discard immediately or after N days, optionally keeping build records. Without it, every short-lived feature branch leaves a permanent job behind.
Q8How do you report CI status back to a pull request?
The GitHub Branch Source plugin reports build status to the PR automatically when the job is configured for it, and I add a post step to comment a summary. That status check is what lets branch protection require a green build before merge.
Q9Scanning is slow on a repo with 500 branches. What now?
Filter by name so only active prefixes are discovered, increase the scan interval, prefer webhook-driven scanning over periodic scans, and prune stale branches in the repository itself. Scans cost API calls, so they are also subject to provider rate limits.
Q10How do you deploy a preview environment per pull request?
Add a stage gated on when { changeRequest() } that deploys to a namespace or subdomain derived from CHANGE_ID, then tears it down in post { cleanup } or when the PR closes. Preview environments are the highest-value thing Multibranch enables.
