Block 9 · Real engineering

Docker build & push to Docker Hub

Goal: turn tested code into a versioned, immutable container image in a registry — the artifact every modern deployment consumes.

9.1 Concepts: image, tag, registry, digest

🏷️ Tag

A mutable pointer to an image: myapp:1.4.2. latest is a tag, not magic — and a dangerous one in production.

🔒 Digest

Immutable content hash: myapp@sha256:9f…. What you actually deploy when you need reproducibility.

📦 Registry

Storage + API: Docker Hub, ECR, GHCR, Harbor. Jenkins authenticates, then pushes layers.

🧱 Layer

Each Dockerfile instruction = a layer. Layers are cached, which is why instruction order decides build speed.

bashInstall the plugin + give Jenkins docker access

9.2 A tagging strategy that won't bite you

TagExamplePurposeGood practice?
Build numbernodejs-app:42Traceable back to a Jenkins build✅
Git SHAnodejs-app:1a2b3c4Traceable back to exact code✅ best
Semantic versionnodejs-app:1.4.2Human releases✅
latestnodejs-app:latestConvenience for dev only⚠️ never deploy from it
Mutable env tagnodejs-app:prodQuick rollback pointer⚠️ only with a digest recorded
🏆The pattern I use Push three tags per build: the immutable <git-sha> (what you deploy), <build-number> (traceable to CI), and latest (dev convenience only). Deployments always reference the SHA or digest, so "what is running in prod?" is never a guess.

9.3 Two ways to build & push

groovyDocker Pipeline DSL — handles login/logout for you
stage('Docker Build & Push') {
    steps {
        script {
            def imageName = "docker.io/${DOCKER_USER}/nodejs-app"     // no tag here
            def app = docker.build("${imageName}:${env.GIT_SHA}", "--pull --no-cache .")

            docker.withRegistry('https://index.docker.io/v1/', 'dockerhub-creds') {
                app.push()                       // pushes :<git-sha>
                app.push(env.BUILD_NUMBER)       // pushes :<build-number>
                if (env.BRANCH_NAME == 'main') {
                    app.push('latest')           // only main moves :latest
                }
            }
            env.IMAGE_DIGEST = sh(script: "docker inspect --format='{{index .RepoDigests 0}}' ${imageName}:${env.GIT_SHA}",
                                  returnStdout: true).trim()
            echo "Pushed ${env.IMAGE_DIGEST}"
        }
    }
}
groovyFull control — useful when you need buildx, secrets or --cache-from
stage('Docker Build & Push') {
    steps {
        withCredentials([usernamePassword(credentialsId: 'dockerhub-creds',
                                          usernameVariable: 'REG_USER',
                                          passwordVariable: 'REG_PASS')]) {
            sh '''
                set -e
                echo "$REG_PASS" | docker login -u "$REG_USER" --password-stdin

                docker build \
                  --pull \
                  --build-arg BUILD_ENV=ci \
                  --tag $IMAGE:$GIT_SHA \
                  --tag $IMAGE:$BUILD_NUMBER \
                  .

                docker push $IMAGE:$GIT_SHA
                docker push $IMAGE:$BUILD_NUMBER
                docker logout
            '''
        }
    }
}

9.4 Faster, smaller, safer images

TechniqueHowGain
Correct layer orderCopy package*.json / requirements.txt first, install, then copy sourceDependency layers stay cached across code changes
.dockerignoreExclude node_modules, .git, coverageSmaller context, faster builds, no secret leakage
Multi-stage buildBuild in one stage, ship a slim runtime stageImages 5–10× smaller, fewer CVEs
Non-root userUSER appuserPasses CIS benchmark & Trivy checks (Block 18)

--cache-fromPull the previous image and use its layersBig speed-up on ephemeral agents

🚨Security reality: mounting /var/run/docker.sock Our learning setup gives the jenkins user access to the host Docker socket. That is root-equivalent — any job, and anyone who can create one, can own the host. Production alternatives:
  • Kaniko / Buildah — build images in userspace without a docker daemon.
  • Rootless BuildKit — a daemon that runs unprivileged.
  • Docker-in-Docker (dind) — a real daemon in a container; still privileged, but isolated from the host.
  • Ephemeral cloud agents — a fresh VM per build, destroyed afterwards.
Say this in interviews: it shows you understand the risk, not just the syntax.

9.5 Smoke-test the image before you push it

groovyRun the container, hit /health, then tear it down
stage('Container smoke test') {
    steps {
        script {
            def img = docker.build("${IMAGE}:${env.GIT_SHA}", '.')
            img.inside("--rm -p ${3000 + env.EXECUTOR_NUMBER.toInteger()}:3000".toString() + ' -e PORT=3000') {
                // 'inside' runs the container, mounts the workspace, waits for health
                retry(10) {
                    sleep 3
                    sh "curl -fsS http://localhost:${3000 + env.EXECUTOR_NUMBER.toInteger()}/health"
                }
            }
        }
    }
}
💡Why the port maths? env.EXECUTOR_NUMBER gives each concurrent build a different port, so two builds running at once don't fight over 3000. That detail alone prevents a whole class of "it fails when two people push" bugs.

9.6 ✍️ Jenkinsfiles v9 — build & push

groovynodejs-app/Jenkinsfile — v9
pipeline {
    agent any
    options { timestamps(); timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }

    environment {
        APP_NAME    = 'nodejs-app'
        DOCKER_USER = '<your-dockerhub-user>'
        IMAGE       = "${DOCKER_USER}/${APP_NAME}"
        REGISTRY    = 'https://index.docker.io/v1/'
        CREDS       = 'dockerhub-creds'
    }

    stages {
        stage('Checkout') {
            steps {
                dir(APP_NAME) { checkout scmGit(branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: 'github-ssh',
                            url: 'git@github.com:<you>/jenkins-zero-to-hero.git']]) }
                script {
                    dir(APP_NAME) {
                        env.GIT_SHA = sh(script:'git rev-parse --short HEAD', returnStdout:true).trim()
                    }
                }
            }
        }
        stage('Build')  { steps { dir(APP_NAME) { sh 'npm ci' } } }
        stage('Test')   { steps { dir(APP_NAME) { sh 'npm run test:junit' } } }

        stage('Docker Build') {
            steps {
                dir(APP_NAME) {
                    script {
                        app = docker.build("${IMAGE}:${env.GIT_SHA}", "--pull .")
                    }
                }
            }
        }

        stage('Container Smoke Test') {
            steps {
                script {
                    app.inside('-p 3100:3000 -e PORT=3000') {
                        retry(10) {
                            sleep 3
                            sh 'curl -fsS http://localhost:3100/health || exit 1'
                        }
                    }
                }
            }
        }

        stage('Push') {
            when { branch 'main' }
            steps {
                script {
                    docker.withRegistry(env.REGISTRY, env.CREDS) {
                        app.push(env.GIT_SHA)
                        app.push(env.BUILD_NUMBER)
                        app.push('latest')
                    }
                }
            }
        }
    }

    post {
        always {
            dir(APP_NAME) { junit testResults: 'reports/junit.xml', allowEmptyResults: true }
            sh 'docker image prune -f || true'
        }
        success { echo "✅ Pushed ${IMAGE}:${env.GIT_SHA}" }
    }
}

9.8 💬 Interview Q&A

Q1How does Jenkins build and push a Docker image?
With the Docker Pipeline plugin: docker.build("image:tag", "--pull .") creates the image and docker.withRegistry(url, credentialsId) { img.push() } authenticates and pushes. Credentials come from the Jenkins store, so no password ever appears in the pipeline or logs.
Q2What's your image tagging strategy?
Immutable Git SHA as the primary tag, plus the build number for traceability to CI, and latest for developer convenience only. Deploys always reference the SHA or the digest so the running artifact is unambiguous and rollback is trivial.
Q3Is giving Jenkins access to the Docker socket safe?
No — socket access is effectively root on the host, so any job (and anyone who can create one) could take over the machine. For production I'd use Kaniko or rootless BuildKit to build without a privileged daemon, or run each build on an ephemeral agent that is destroyed afterwards.
Q4How do you keep Docker builds fast?
Order Dockerfile instructions so dependency layers change least often, keep a proper .dockerignore, reuse the previous image's layers with --cache-from, and use multi-stage builds so the pushed image contains only what it needs to run.

9.10 Under the hood — layers, cache and the build context

Every Dockerfile instruction creates a layer identified by a content hash. Docker reuses a cached layer when the instruction and its inputs are unchanged — which is why instruction order dominates build time.

bashInspect what your image is really made of
docker history user/nodejs-app:abc1234          # layer list + sizes
docker images --format '{{.Repository}}:{{.Tag}}	{{.Size}}'
docker inspect user/nodejs-app:abc1234 --format '{{.Id}} {{.RepoTags}} {{index .RepoDigests 0}}'
docker scout quickview user/nodejs-app:abc1234  # (or) trivy image ...
⚠️The build context trap docker build . sends the entire directory to the daemon — including .git, node_modules and coverage unless you have a .dockerignore. A 500 MB context can add minutes to every build and, worse, can leak files into image layers.

9.11 Multi-stage, distroless and size

Base imageTypical sizeWhen
node:20~1.1 GBAlmost never in production
node:20-slim~240 MBGood default

gcr.io/distroless/nodejs20~120 MBNo shell, no package manager — smallest attack surface

dockerfileDistroless runtime stage — no shell, no package manager, tiny surface
# ---- build stage ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

# ---- runtime stage ----
FROM gcr.io/distroless/nodejs20-debian12:nonroot
WORKDIR /app
ENV NODE_ENV=production PORT=3000
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER nonroot
EXPOSE 3000
CMD ["dist/server.js"]
💡Trade-off to mention in interviews Distroless images have no shell, so you cannot docker exec into them to debug and HEALTHCHECK CMD with shell syntax won't work. Teams that adopt them usually pair them with good observability (metrics, traces, structured logs) because live debugging inside the container is no longer an option.

9.12 Lab — a failing image, diagnosed properly

🧪Lab 9.1 · Build succeeds, container exits immediately Symptom: docker build is green; the container exits with code 1 and no useful log.
bashDiagnose in this order
docker run --rm user/nodejs-app:abc1234          # read the error
docker logs $(docker ps -lq)                     # logs of the last container

# 1) Is the entrypoint even present?
docker run --rm --entrypoint sh user/nodejs-app:abc1234 -c 'ls -la /app'

# 2) Is it a permissions problem? (non-root user can't read a file)
docker run --rm user/nodejs-app:abc1234 id
docker run --rm --entrypoint sh user/nodejs-app:abc1234 -c 'ls -la /app/node_modules | head'

# 3) Is the port/env wrong?
docker run --rm -e PORT=3000 -p 3000:3000 user/nodejs-app:abc1234

# 4) Does it start at all when you override the command?
docker run --rm -it --entrypoint sh user/nodejs-app:abc1234
Most common causes: app listens on 127.0.0.1 instead of 0.0.0.0 (unreachable from outside the container); USER can't read a file copied as root; missing NODE_ENV or PORT; distroless image with a shell-form CMD.

9.14 More interview Q&A

Q5Why does my Docker build take 10 minutes when nothing changed?
Almost always cache invalidation: the manifest is copied after the source, so npm ci re-runs every time; or --no-cache/--pull is forced; or the build context is huge. I check docker history, move the dependency layer up, and add a .dockerignore.
Q6How do you get a reproducible image?
Pin the base image by tag and ideally digest (FROM node:20.17-alpine3.20@sha256:…), install from a lockfile, avoid latest, and set a fixed build environment. Then reference the pushed image by digest in deployments.
Q7What is a dangling image, and why does my disk fill up?
A dangling image is a layer set no longer referenced by any tag — every rebuild leaves some. Prune them on a schedule (docker image prune -f) and cap build history; on a busy CI host this is the single biggest disk consumer.
Q8Multi-arch builds in CI?
With buildx: docker buildx build --platform linux/amd64,linux/arm64 -t img:tag --push. It needs QEMU emulation (slow) or native builders (fast). I'd run amd64 on every commit and the full multi-arch manifest on release branches only.
Q9How do you pass secrets into a build without leaking them into layers?
Use BuildKit secret mounts: RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci with --secret id=npmrc,src=…. Never ARG SECRET or COPY a secret — both persist in the image history.
