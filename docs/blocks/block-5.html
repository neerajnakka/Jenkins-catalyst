Block 5 · Foundation

BUILD stage — Node & Python

Goal: install dependencies deterministically and produce a build artifact. Understand why deterministic matters more than fast, and how caching changes the game.

5.1 What "build" means per ecosystem

StackBuild =Deterministic commandLockfile (must be committed)
Node.jsInstall dependencies into node_modulesnpm cipackage-lock.json
PythonCreate a venv, install dependenciespip install -r requirements.txtrequirements.txt (pinned!) / poetry.lock
🚨npm install vs npm ci — a guaranteed interview question npm install reads package.json and may update the lockfile and install slightly newer versions. npm ci ("clean install") deletes node_modules, installs exactly what package-lock.json says, and fails if the two disagree. CI must be reproducible — so CI always uses npm ci. Same reasoning for Python: pin your versions and use pip install -r.

5.2 Why your build is slow, and the cache fix

🟩 Node

Downloads land in ~/.npm. Point npm_config_cache at a stable directory and npm ci becomes seconds on a warm agent.

🐍 Python

Wheels land in ~/.cache/pip. Keep it between builds and pip install skips the network entirely.

groovyPersistent caches on the agent
environment {
    npm_config_cache = "${env.WORKSPACE_TMP}/.npm"     // or a fixed path: /var/lib/jenkins/.npm
    PIP_CACHE_DIR    = "/var/lib/jenkins/.cache/pip"
}
⚠️Cache in $WORKSPACE only survives if you don't wipe it If you use cleanBeforeCheckout() (Block 4) or cleanWs(), anything cached inside the workspace is deleted. Use a path outside the workspace — e.g. /var/lib/jenkins/.npm — for caches you want to keep.

5.3 Exit codes: how Jenkins decides success

A shell step succeeds when it exits 0. Anything else fails the stage and the build. Three escape hatches:

groovyControlling failure
// 1. Non-zero is fine -- give me the code instead of failing
def rc = sh(script: 'npm audit --audit-level=high', returnStatus: true)
echo "npm audit exit code: ${rc}"

// 2. Capture output (trailing newline needs .trim())
def nodeVersion = sh(script: 'node -v', returnStdout: true).trim()

// 3. Force a failure with a clear message
sh script: 'test -f package.json', label: 'verify manifest exists'
if (!fileExists('package-lock.json')) {
    error 'package-lock.json is missing -- `npm ci` cannot guarantee reproducibility'
}

5.4 Stash & unstash — moving files between agents

If stage A runs on agent linux and stage B on agent docker, they do not share a workspace. stash saves files on the controller; unstash restores them wherever you need them.

groovystash / unstash
stage('Build') {
    agent { label 'linux' }
    steps {
        sh 'npm ci --omit=dev'
        stash name: 'app-source', includes: 'src/**,package*.json', useDefaultExcludes: true
    }
}
stage('Package') {
    agent { label 'docker' }
    steps {
        unstash 'app-source'          // files reappear here, on a different machine
        sh 'docker build -t app .'
    }
}

5.5 ✍️ Jenkinsfiles v5 — real build stage

groovynodejs-app/Jenkinsfile — v5 (Build)
pipeline {
    agent any
    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment {
        APP_NAME       = 'nodejs-app'
        npm_config_cache = '/var/lib/jenkins/.npm'      // cache OUTSIDE the workspace
    }

    stages {
        stage('Checkout') {
            steps {
                dir(APP_NAME) {
                    checkout scmGit(branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: 'github-ssh',
                            url: 'git@github.com:<you>/jenkins-zero-to-hero.git']])
                }
            }
        }

        stage('Build') {
            steps {
                dir(APP_NAME) {
                    sh label: 'verify toolchain', script: 'node -v && npm -v'
                    sh label: 'install dependencies', script: 'npm ci'
                    // sanity gate: the app must actually load before we test it
                    sh label: 'smoke import', script: "node -e \"require('./src/app.js'); console.log('app loads OK')\""
                }
            }
        }

        stage('Test') { steps { echo 'Block 6' } }
    }

    post { always { echo "Result: ${currentBuild.currentResult}" } }
}
groovypython-app/Jenkinsfile — v5 (Build)
pipeline {
    agent any
    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment {
        APP_NAME     = 'python-app'
        PIP_CACHE_DIR = '/var/lib/jenkins/.cache/pip'
        VENV_DIR     = 'venv'                    // venv INSIDE the workspace (cheap to rebuild)
    }

    stages {
        stage('Checkout') {
            steps {
                dir(APP_NAME) {
                    checkout scmGit(branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: 'github-ssh',
                            url: 'git@github.com:<you>/jenkins-zero-to-hero.git']])
                }
            }
        }

        stage('Build') {
            steps {
                dir(APP_NAME) {
                    sh label: 'verify toolchain', script: 'python3 --version'
                    sh label: 'create virtualenv', script: 'python3 -m venv $VENV_DIR'
                    sh label: 'install dependencies', script: '''
                        . $VENV_DIR/bin/activate
                        pip install --upgrade pip
                        pip install -r requirements-dev.txt
                    '''
                    sh label: 'smoke import', script: '. $VENV_DIR/bin/activate && python -c "import app; print(\'app loads OK\')"'
                }
            }
        }

        stage('Test') { steps { echo 'Block 6' } }
    }

    post { always { echo "Result: ${currentBuild.currentResult}" } }
}
💡Why the venv lives inside the workspace for Python A venv is cheap (milliseconds) and disposable — recreating it is faster and safer than sharing a mutable one between builds. Node's node_modules is the same idea; the expensive part is the download cache, and that's what we keep outside the workspace.

5.7 💬 Interview Q&A

Q1What does your Build stage do?
It installs dependencies deterministically from a committed lockfile (npm ci / pinned requirements.txt), verifies the toolchain, and does a smoke check that the app imports. It produces no side effects outside the workspace, so any failure is safe to retry.
Q2How do you speed up slow CI builds?
Keep the package download cache outside the workspace so it survives cleanWs (npm_config_cache, PIP_CACHE_DIR), use shallow clones, cache base Docker layers with --cache-from, and split fast stages first so failures are discovered early.
Q3How do you share files between stages on different agents?
stash on the producing agent and unstash on the consuming one — the controller holds the files. Alternatively publish to an artifact repository (Nexus, S3, ECR) for anything you need to keep.
Q4Your build passes locally but fails in Jenkins. Walk me through it.
First reproduce as the Jenkins user with sudo -u jenkins …. Then compare: tool versions (node -v), lockfile committed, network access to the registry, filesystem permissions, and disk space. Then check the console log for the first + command line that failed — not the last.

5.8 Under the hood — determinism and caches

A build is deterministic when the same commit always produces the same result. Three enemies of determinism, and the fix for each:

EnemySymptomFix
Floating version ranges"express": "^4.19.2" resolves differently next weekCommit the lockfile; use npm ci / pinned requirements.txt
Unpinned base imagesFROM node:20 changes under youPin: FROM node:20.17-alpine3.20
System packages installed at build timeapt-get install curl picks a new versionPin versions, or bake them into a base image you control
Time/locale dependent outputSnapshot tests fail around midnightSet TZ and inject the clock in tests
Reproducibility is the whole point of CI. If a build can pass today and fail tomorrow on unchanged code, you don't have CI — you have a slot machine.Block 5

5.9 Lab — measure what caching actually buys you

🧪Lab 5.1 · Cold vs warm build
bashTime it yourself, as the jenkins user
sudo -iu jenkins bash -c '
  cd /tmp && rm -rf cachetest && mkdir cachetest && cd cachetest
  cp /var/lib/jenkins/jobs/nodejs-app/workspace/nodejs-app/package*.json . 2>/dev/null || true

  echo "--- COLD (empty cache) ---"
  rm -rf /tmp/coldcache && npm_config_cache=/tmp/coldcache npm ci --ignore-scripts
  echo "--- WARM (same cache again) ---"
  rm -rf node_modules && time npm_config_cache=/tmp/coldcache npm ci --ignore-scripts
'
Expect the warm run to be 3–10× faster. That ratio is exactly what your pipeline gains by pointing npm_config_cache at a path outside the workspace.

5.11 More interview Q&A

Q5What makes a CI build reproducible?
A committed lockfile, a deterministic install command (npm ci), pinned base images and pinned system packages, plus an isolated environment (container or venv) so the agent's global state can't leak in.
Q6Where should CI caches live?
Outside the workspace, at a stable absolute path like /var/lib/jenkins/.npm. Anything inside the workspace is destroyed by cleanWs() and cleanBeforeCheckout(), so it can't act as a cache.
Q7When would you use stash instead of just leaving files in the workspace?
When the next stage may run on a different agent — workspaces aren't shared across nodes, so stash copies the files via the controller. On a single agent, leaving them in place is faster.
Q8How do you fail fast in a build stage?
Put a cheap smoke check right after install (does the module import?), and rely on set -e semantics: any non-zero exit aborts the stage. I add label: to each sh so the console shows exactly which command failed.
