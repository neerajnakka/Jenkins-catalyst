DevSecOps part 2 — SCA, linting & secret scanning

Goal: catch vulnerable dependencies, insecure code patterns and leaked secrets before they are merged — the highest-value, lowest-effort security stage you can add.

17.1 Why dependencies are the real risk

Your code is a few thousand lines; your dependencies are a few hundred thousand. Most real-world breaches come from a vulnerable library you didn't write. SCA (Software Composition Analysis) compares your dependency tree against CVE databases.

17.3 Installing the tools on the agent

bashOne-time install on the Jenkins agent (or bake into the agent image)
# Trivy (Aqua Security) - filesystem, container, IaC and secret scanning
sudo apt-get install -y wget apt-transport-https gnupg lsb-release
wget -qO - https://aquasecurity.github.io/trivy-repo/deb/public.key | sudo gpg --dearmor -o /usr/share/keyrings/trivy.gpg
echo "deb [signed-by=/usr/share/keyrings/trivy.gpg] https://aquasecurity.github.io/trivy-repo/deb $(lsb_release -sc) main" \
  | sudo tee /etc/apt/sources.list.d/trivy.list
sudo apt-get update && sudo apt-get install -y trivy

# Gitleaks - secret scanning
GITLEAKS_VERSION=$(curl -s https://api.github.com/repos/gitleaks/gitleaks/releases/latest | jq -r .tag_name)
curl -sSfL "https://github.com/gitleaks/gitleaks/releases/download/${GITLEAKS_VERSION}/gitleaks_${GITLEAKS_VERSION#v}_linux_x64.tar.gz" \
  | sudo tar -xz -C /usr/local/bin gitleaks

# Python: tools come from requirements-dev.txt (pip-audit, bandit, flake8)
# Node:   npm audit is built in; add audit-ci with `npm i -g audit-ci`

trivy --version && gitleaks version

17.4 Pipeline stages for SCA (both apps)

groovyDependency + lint scanning for Node
stage('SCA · npm audit') {
    agent { docker { image 'node:20-alpine'; reuseNode true } }
    steps {
        dir('nodejs-app') {
            // JSON report for the record, then a blocking gate on high/critical
            sh '''
                npm audit --audit-level=high --json > npm-audit.json || true
                npm audit --audit-level=high            # non-zero exit => build fails
            '''
            archiveArtifacts artifacts: 'npm-audit.json', allowEmptyArchive: true
        }
    }
}

stage('Lint · ESLint') {
    agent { docker { image 'node:20-alpine'; reuseNode true } }
    steps {
        dir('nodejs-app') {
            // warnings-only: lint should not block a hotfix
            catchError(buildResult: 'UNSTABLE', stageResult: 'FAILURE') {
                sh 'npm run lint'
            }
        }
    }
}
groovyDependency + security + style scanning for Python
stage('SCA · pip-audit') {
    agent { docker { image 'python:3.12-slim'; reuseNode true } }
    steps {
        dir('python-app') {
            sh '''
                . venv/bin/activate
                pip-audit -r requirements.txt --format json --output pip-audit.json || true
                pip-audit -r requirements.txt                 # blocking gate
            '''
            archiveArtifacts artifacts: 'pip-audit.json', allowEmptyArchive: true
        }
    }
}

stage('SAST · Bandit') {
    agent { docker { image 'python:3.12-slim'; reuseNode true } }
    steps {
        dir('python-app') {
            sh '''
                . venv/bin/activate
                bandit -r app.py -f json -o bandit-report.json || true
                bandit -r app.py -ll            # -ll = fail on MEDIUM and above
            '''
            archiveArtifacts artifacts: 'bandit-report.json', allowEmptyArchive: true
        }
    }
}

stage('Lint · flake8') {
    agent { docker { image 'python:3.12-slim'; reuseNode true } }
    steps {
        dir('python-app') {
            catchError(buildResult: 'UNSTABLE', stageResult: 'FAILURE') {
                sh '. venv/bin/activate && flake8 app.py tests/'
            }
        }
    }
}
groovyTrivy filesystem + secret scan, and gitleaks
stage('SCA · Trivy filesystem') {
    agent { label 'linux' }
    steps {
        sh '''
            trivy fs --scanners vuln,secret \
                     --severity HIGH,CRITICAL \
                     --exit-code 1 \
                     --format table \
                     --output trivy-fs.txt . || true

            trivy fs --scanners vuln,secret \
                     --severity HIGH,CRITICAL \
                     --exit-code 1 \
                     --ignore-unfixed \
                     .                          # blocking gate
        '''
        archiveArtifacts artifacts: 'trivy-fs.txt', allowEmptyArchive: true
    }
}

stage('Secrets · gitleaks') {
    agent { label 'linux' }
    steps {
        sh '''
            # scan the whole history available in this clone
            gitleaks detect --source . --report-path gitleaks-report.json --redact || found=1
            if [ -n "${found:-}" ]; then
              echo "::SECRET DETECTED:: rotate it, then purge it from history"
              exit 1
            fi
        '''
    }
    post {
        always { archiveArtifacts artifacts: 'gitleaks-report.json', allowEmptyArchive: true }
    }
}

17.5 OWASP Dependency-Check (the enterprise option)

Common in regulated companies. Install the OWASP Dependency-Check plugin, configure the tool in Manage Jenkins → Tools, then:

groovyDependency-Check step + publisher
stage('OWASP Dependency-Check') {
    agent { label 'linux' }
    steps {
        dependencyCheck additionalArguments: '''
            --scan .
            --format HTML --format XML
            --out .
            --suppression suppression.xml
            --nvdApiKey $NVD_API_KEY
        ''', odcInstallation: 'dependency-check'

        dependencyCheckPublisher pattern: 'dependency-check-report.xml'
    }
}
💡Two practical notes Dependency-Check downloads the whole NVD database on first run (slow — run it nightly, not per-commit). Get a free NVD API key or downloads get throttled. Keep a suppression.xml for accepted risks, and always record why a finding is suppressed with an expiry date.

17.6 Publishing everything with Warnings NG

Install Warnings NG (warnings-ng) to trend issues across builds instead of dumping them into logs:

groovyrecordIssues — trend graphs for every scanner
post {
    always {
        recordIssues(
            enabledForFailure: true,
            tools: [
                eslint(pattern: 'nodejs-app/eslint-report.json'),
                flake8(pattern: 'python-app/flake8-report.txt'),
                pyLint(pattern: 'python-app/pylint-report.txt')
            ],
            qualityGates: [[threshold: 10, type: 'TOTAL', unstable: true]]
        )
    }
}

17.7 ✅ Checklist

  • Trivy and gitleaks installed on the agent.
  • npm audit / pip-audit stage runs and fails on HIGH/CRITICAL.
  • Bandit runs on the Python app; you can explain the B104 finding in app.py.
  • A secret I planted in a test file was caught by gitleaks.
  • Scan reports are archived and (ideally) trended with Warnings NG.

17.8 💬 Interview Q&A

Q1How do you scan dependencies in CI?
With SCA tools in a dedicated stage: npm audit --audit-level=high for Node, pip-audit for Python, plus Trivy in filesystem mode across the repo. They exit non-zero on high/critical CVEs, which fails the build. I archive the JSON report for the record and use a suppression file with justifications for accepted risks.
Q2How do you prevent secrets being committed?
Two layers: a pre-commit hook (gitleaks or detect-secrets) so it never leaves the developer's machine, and the same scan in CI as a blocking gate. If a secret is found I treat it as compromised — rotate first, then purge from history — because removing the commit does not un-leak it.
Q3Found a critical CVE in a transitive dependency with no fixed version. Now what?
Assess real exposure: is the vulnerable code path reachable from our usage? If yes, mitigate (upgrade the parent, patch, or remove the dependency); if no, record a documented, time-boxed suppression so the build stays green without hiding the risk. I'd also add an alert so we revisit it when a fix lands.
Q4What does Bandit check, and what's a finding you've seen?
Bandit is a Python AST-based SAST tool: hardcoded passwords, eval, weak crypto, shell injection, and binding to 0.0.0.0 (B104). In this repo it flags B104 in app.py where the dev server binds all interfaces — acceptable for a dev entrypoint because production runs gunicorn behind a proxy, so I'd suppress it with a comment explaining why.
Q5Reporting vs blocking — how do you choose?
Blocking gates for exploitable, high-confidence, fixable issues (critical CVEs, secrets, quality gate on new code). Reporting-only for advisory signals (style lint, low severity, informational) — those trend on a dashboard and can be promoted to gates later.

17.9 Under the hood — how SCA finds vulnerabilities

SCA tools build a dependency graph — your direct dependencies plus every transitive one — map each package to a PURL (package URL) or CPE identifier, and look it up in vulnerability databases (GitHub Advisory DB, OSV, NVD, npm and PyPI advisories). Three practical consequences follow:

  • Transitive dependencies matter most. You rarely chose the vulnerable package; a dependency of a dependency did. That is why "we only use three libraries" is not a security argument.
  • Accuracy depends on identification. Wrong identifiers produce false positives — which is what suppression files are for, always with a written reason and an expiry date.
  • Not every CVE is exploitable. A vulnerable function you never call is lower priority than one on a request path. Triage by reachability, not by severity alone.

17.12 Secret scanning in depth

bashgitleaks — configuration and pre-commit hook
# .gitleaks.toml — allow-list for known-safe strings
[extend]
useDefault = true

[[allowlist]]
description = "local test fixtures"
paths = ['''^tests/fixtures/.*''']

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
🚨If a secret reaches a remote branch, it is compromised Deleting the commit does not un-leak it — bots scrape public repositories continuously, often within seconds. The only correct response is: rotate first, then purge history, then add the prevention layer (pre-commit hook plus CI gate).

17.13 More interview Q&A

Q6Trivy vs OWASP Dependency-Check?
Trivy is a single fast binary covering dependencies, containers, IaC and secrets with no database bootstrap — ideal for pipelines. Dependency-Check is JVM-based, downloads the NVD (slow first run, needs an NVD API key) and is common in regulated enterprises with existing suppression files. I would use Trivy for speed and Dependency-Check where compliance requires it.
Q7How do you keep false positives from blocking delivery?
A version-controlled suppression file where every entry carries an owner, a reason and an expiry date, reviewed periodically. A suppression without justification is just a hidden risk.
Q8Should scans run on every commit?
Fast ones, yes — npm audit, pip-audit, Trivy filesystem and gitleaks all run in seconds. Slow or noisy scans (full Dependency-Check, active DAST) go nightly, with the fast subset blocking every commit.
Q9How do you report security findings to developers?
Publish machine-readable reports (SARIF or JSON) as build artifacts and trend them with Warnings NG, link the failing build in chat, and keep the finding next to the code that caused it. The goal is a thirty-second path from alert to offending line.
Q10What is SBOM-driven vulnerability management?
Generate an SBOM at build time and store it alongside the artifact. When a new CVE appears you query your SBOMs instead of re-scanning everything, so you know within minutes which services are affected — exactly the capability that was missing during Log4Shell.
