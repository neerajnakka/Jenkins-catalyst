Block 2 · Foundation

Declarative Pipeline anatomy

Goal: be able to write the skeleton pipeline → agent → stages → stage → steps → post from memory, and know why each block exists and what order is legal.

2.1 Two flavours: Declarative vs Scripted

📐 Declarative Learn this

Starts with pipeline { }. Fixed, opinionated structure. Jenkins can validate it, visualise it, and Blue Ocean can render it. Easy to read, hard to abuse. Use this 95% of the time.

🐍 Scripted

Starts with node { }. Raw Groovy — loops, classes, try/catch anywhere. Maximum power, easy to make unreadable. Use it inside a script { } block when declarative genuinely can't express something.

🧠The mental model Declarative says what should happen ("run these four stages, then always clean up"). Scripted says how ("do this Groovy, step by step"). Declarative pipelines are still Groovy underneath, which is why a syntax slip produces Groovy stack traces.

2.2 The skeleton — every legal top-level block

groovyThe complete declarative skeleton (all sections, correct order)
pipeline {                 // 1. REQUIRED. The whole file lives inside it.

    agent any              // 2. REQUIRED. WHERE the pipeline runs.

    options {              // 3. optional. Pipeline-wide behaviour.
        timestamps()                                  // add timestamps to logs
        timeout(time: 30, unit: 'MINUTES')            // kill runaway builds
        buildDiscarder(logRotator(numToKeepStr: '30'))// keep disk sane
        disableConcurrentBuilds()                     // one build at a time
    }

    parameters {           // 4. optional. Inputs the user fills before "Build".
        choice(name: 'ENV', choices: ['dev','qa','prod'], description: 'Target')
        booleanParam(name: 'RUN_TESTS', defaultValue: true)
    }

    triggers {             // 5. optional. WHAT starts the pipeline.
        pollSCM('H/5 * * * *')   // check Git every 5 minutes
    }

    tools {                // 6. optional. Auto-install & put tools on PATH.
        nodejs 'node20'
    }

    environment {          // 7. optional. Variables for every step.
        APP_NAME = 'nodejs-app'
    }

    stages {               // 8. REQUIRED. The work.
        stage('Build') {
            steps {        //    REQUIRED inside a stage.
                echo "Building ${APP_NAME}"
                sh 'npm ci'
            }
        }
    }

    post {                 // 9. optional. Runs after stages, whatever happened.
        always   { echo 'always' }
        success  { echo 'green' }
        failure  { echo 'red' }
        cleanup  { echo 'last' }
    }
}
⚠️Four rules that cause 90% of "why won't my Jenkinsfile compile"
  1. pipeline, agent and stages are mandatory at the top level.
  2. Every stage must contain a steps block (or parallel/matrix/when variants).
  3. Order matters at the top level: agent → options → parameters → triggers → tools → environment → stages → post.
  4. stages can contain only stage blocks — no naked steps floating inside it.

2.3 agent — where the work happens

agent answers one question: on what machine, and inside what container, do these steps run? Jenkins allocates a workspace and an executor there.

FormMeaningWhen you use it
agent anyAny available node/executorLearning, single-server setups
agent noneNo global agent — each stage declares its ownMixing OSes/tools in one pipeline (Block 13)
agent { label 'docker' }Run only on nodes labelled dockerRouting builds to capable machines
agent { node { label 'linux'; customWorkspace '/data/ci' } }Node + custom workspace pathDisk or path constraints
agent { docker { image 'node:20-alpine' } }Run steps inside a containerZero-install toolchains (Block 13)
agent { dockerfile { filename 'Dockerfile.ci'; args '-v /tmp:/tmp' } }Build an image from a Dockerfile, run inside itReproducible build environments
groovyagent none + per-stage agents (the professional pattern)
pipeline {
    agent none                       // no machine reserved for the whole pipeline
    stages {
        stage('Test on Node 20') {
            agent { docker { image 'node:20-alpine' } }   // reserved just for this stage
            steps { sh 'node -v && npm test' }
        }
        stage('Build image') {
            agent { label 'docker' }                      // needs the docker socket
            steps { sh 'docker build -t app .' }
        }
    }
}
💡What agent really does It (1) picks a node by label, (2) grabs an executor slot, (3) creates/locks a workspace directory, and (4) for docker/dockerfile, starts a container and mounts that workspace inside it as the working directory. All later sh steps run there — which is why files created in one stage are visible in the next on the same agent.

2.4 stages, stage and steps

  • stages is a container — it holds one or more stage blocks and nothing else.
  • stage('Name') is a logical unit with a name shown in the UI. It is not a sandbox: it does not isolate files or change directories. It exists so you can see timing, pass/fail and rerun per unit.
  • steps holds the actual commands. Steps are things Jenkins knows how to run: sh, echo, git, junit, archiveArtifacts.
groovySteps you will use constantly
steps {
    echo 'Print a line to the console'                 // built-in
    sh 'npm ci'                                        // run a shell command (Linux/macOS)
    sh label: 'install deps', script: 'npm ci'         // with a nicer log label
    sh returnStdout: true, script: 'git rev-parse --short HEAD'   // capture output
    sh returnStatus: true, script: 'grep -q X file'    // get exit code without failing
    bat 'mvn test'                                     // Windows
    dir('python-app') { sh 'pytest' }                  // run inside a sub-directory
    deleteDir()                                        // wipe the workspace
    script {                                           // escape hatch: real Groovy
        def v = sh(script: 'node -v', returnStdout: true).trim()
        echo "Node version is ${v}"
    }
}

Single quotes vs double quotes — the #1 beginner bug

groovyGString interpolation
def TAG = 'v1.4'

echo "Tag is ${TAG}"    // ✅ double quotes  -> "Tag is v1.4"   (GString, interpolates)
echo 'Tag is ${TAG}'    // ❌ single quotes  -> "Tag is ${TAG}" (plain String, literal)

2.5 post — the cleanup & notification block

post runs after all stages finish. Conditions are evaluated in a fixed order, and multiple conditions can run (e.g. always and success both fire on a green build).

ConditionRuns whenTypical use
alwaysEvery time, no matter the resultPublish reports, clean workspace, notify
successAll stages passedSlack "green", tag image as stable
failureAny stage threw an errorAlert, attach log, open ticket
unstableBuild marked unstable (failed tests, quality gate)Warn but don't page anyone
abortedSomeone cancelled itRelease locks, scale down
changedResult differs from the previous build"Back to green" messages
fixedFailed before, success nowCelebrate, close incident
regressionSuccess before, failing nowEscalate immediately
unsuccessfulNot success (failure/unstable/aborted)Generic alerting
cleanupAlways, and last — after everything elseDelete temp files, stop containers

2.6 ✍️ Your first real Jenkinsfiles (v2)

Replace nodejs-app/Jenkinsfile and python-app/Jenkinsfile with these, commit, push, and run. Nothing fancy yet — the point is that the structure works and the UI shows four stages.

groovynodejs-app/Jenkinsfile — v2
// ============================================================
//  nodejs-app/Jenkinsfile  --  v2  (Block 2: anatomy)
// ============================================================
pipeline {
    agent any

    options {
        timestamps()
        timeout(time: 15, unit: 'MINUTES')
    }

    environment {
        APP_NAME = 'nodejs-app'
    }

    stages {
        stage('Info') {
            steps {
                echo "Building ${APP_NAME} - build #${env.BUILD_NUMBER}"
                echo "Workspace: ${env.WORKSPACE}"
                sh 'node -v && npm -v'
            }
        }

        stage('Build') {
            steps {
                echo 'Block 5 will install dependencies here'
            }
        }

        stage('Test') {
            steps {
                echo 'Block 6 will run the Jest suite here'
            }
        }
    }

    post {
        always  { echo "Finished with status: ${currentBuild.currentResult}" }
        failure { echo 'Something broke - Block 11 will notify us properly' }
    }
}

  2. Point it at Git: Pipeline section → Definition: Pipeline script from SCM → SCM: Git → Repository URL: your repo → Script Path: nodejs-app/Jenkinsfile.
  3. Save → Build Now. Watch the Stage View fill in. Click any stage → Logs to see only that stage's output.
  4. Do it again for python-app with Script Path python-app/Jenkinsfile.

2.8 💬 Interview Q&A

Q1Declarative vs Scripted pipeline — which do you use and why?
Declarative. It has a fixed structure Jenkins can validate and visualise, it's readable for the whole team, and it prevents the "clever Groovy nobody can maintain" problem. I drop into script { } only when I genuinely need Groovy logic that declarative can't express.
Q2What are the mandatory sections of a declarative pipeline?
pipeline at the root, and inside it agent and stages. Every stage must then contain a steps block.
Q3What does agent none mean?
No agent is allocated for the pipeline as a whole; each stage declares its own agent. It lets one pipeline run tests inside a Node container and build an image on a Docker host, without holding two executors for the whole run.
Q4Do stages run in parallel by default?
No — sequentially, in the order written. Parallelism is explicit with a parallel block (Block 21), and it still needs executors available.
Q5What's the difference between always and cleanup in post?
Both always run, but cleanup runs last, after every other post condition — including after a failure in always. Anything that must happen even if notifications break (removing temp files, stopping containers) belongs in cleanup.

2.10 Under the hood — how a declarative pipeline actually runs

This is the most useful piece of Jenkins theory there is, and it explains errors that otherwise look random.

  1. Parse. The declarative structure is validated first — which is why a missing steps block fails instantly with a structural message instead of a Groovy stack trace.
  2. CPS transformation. Your Groovy is rewritten into Continuation Passing Style so the pipeline can be paused and resumed — that's what lets a build survive a controller restart.
  3. Execution. Steps dispatch: sh forks a process on the agent, echo writes to the build log, junit parses files on the controller, docker.build talks to the daemon.
  4. Durability. Program state is flushed to jobs/*/builds/<n>/program.dat so a crash resumes from the last checkpoint.
🧠Why Groovy behaves oddly inside a pipeline Because of CPS, some ordinary Groovy is unsafe: closures that mutate state, loops over non-serialisable objects, and certain collection methods. Annotate pure helper functions with @NonCPS:
groovy@NonCPS — pure computation only, never steps
import com.cloudbees.groovy.cps.NonCPS

@NonCPS
String joinNames(List<String> names) { names.join(', ') }

pipeline {
    agent any
    stages {
        stage('Demo') {
            steps {
                script { echo joinNames(['jenkins', 'docker', 'sonar']) }
            }
        }
    }
}
Rule: an @NonCPS method must never call a pipeline step (sh, echo), because it cannot be suspended.

2.13 More interview Q&A

Q6What is CPS in Jenkins pipelines?
Continuation Passing Style: Groovy is transformed so execution can be paused and resumed, which is how a build survives a controller restart. It also explains why some ordinary Groovy misbehaves in pipelines and why pure helpers are annotated @NonCPS.
Q7Why do some Groovy methods fail inside a pipeline?
CPS-transformed code must be serialisable and resumable. Collection methods with closures, each over non-serialisable objects and mutating shared state can throw NotSerializableException. I move that logic into an @NonCPS method or a shared-library class under src/.
Q8Can a running pipeline survive a Jenkins restart?
Yes, up to the configured durability level: program state is written to disk, so after a restart the build resumes at the last checkpoint and in-flight steps are re-run. That is a direct consequence of the CPS design.
Q9When do you use script{}?
When declarative genuinely can't express the logic — building a dynamic parallel map, conditional loops, parsing JSON into variables, calling Groovy libraries. Everything else stays declarative so it can be validated and visualised.
Q10How do you keep Jenkinsfiles readable as they grow?
Move reusable logic to a shared library, keep stages short and outcome-named, use parameters instead of hard-coded values, and set currentBuild.description so the history page explains itself. Past roughly 150 lines, the repeated parts belong in vars/.
