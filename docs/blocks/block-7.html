Block 7 · Real engineering

Environment variables & build parameters

Goal: control your pipeline's behaviour without editing code — the difference between a script that builds one thing and a pipeline a whole team can use.

7.1 Three levels of environment variables

LevelWhere it's setScopeUse for
1. GlobalManage Jenkins → System → Global properties → Environment variablesEvery job on the controllerCompany-wide things: REGISTRY, SLACK_CHANNEL, proxy settings
2. Pipelineenvironment { } in the JenkinsfileEvery step in that pipeline (or one stage)APP_NAME, IMAGE, tool flags
3. StepwithEnv([...]) { } or inline sh 'VAR=x cmd'Only inside that blockTemporary overrides, per-command config
groovyAll three in action
pipeline {
    agent any

    environment {
        APP_NAME   = 'nodejs-app'
        IMAGE      = "docker.io/<youruser>/${APP_NAME}"   // variables can reference each other
        BUILD_TS   = """${sh(returnStdout: true, script: 'date +%Y%m%d-%H%M%S').trim()}"""
    }

    stages {
        stage('Demo') {
            environment {
                STAGE_ONLY = 'yes'                          // visible only in this stage
            }
            steps {
                echo "Global? ${env.REGISTRY}"              // set in Manage Jenkins
                echo "Pipeline: ${env.IMAGE} built at ${env.BUILD_TS}"
                echo "Stage: ${env.STAGE_ONLY}"

                withEnv(['NODE_ENV=ci', 'CI=true']) {        // block-scoped
                    sh 'echo $NODE_ENV $CI'
                }

                sh 'INLINE=yes; echo $INLINE'               // per-command
            }
        }
    }
}

7.3 Parameters — inputs before the build starts

DirectiveUI widgetRead as
string(name:'X', defaultValue:'…')Text boxparams.X (String)
text(name:'X', defaultValue:'…')Text areaString (multi-line)
booleanParam(name:'X', defaultValue:true)CheckboxBoolean
choice(name:'X', choices:['dev','qa','prod'])Drop-downString
password(name:'X', defaultValue:'…')Masked boxString — avoid, use credentials (Block 8)
file(name:'X')UploadFile in the workspace
groovyParameters + conditional behaviour
pipeline {
    agent any

    parameters {
        choice   name: 'ENV',        choices: ['dev', 'qa', 'prod'], description: 'Deploy target'
        booleanParam name: 'RUN_TESTS',   defaultValue: true,  description: 'Run the unit test suite'
        booleanParam name: 'PUSH_IMAGE',  defaultValue: false, description: 'Push to Docker Hub'
        string   name: 'IMAGE_TAG',  defaultValue: '', description: 'Override tag (default: build number)'
    }

    environment {
        // params is null on the very first build -> use the ?: fallback pattern
        TAG = "${params.IMAGE_TAG ?: env.BUILD_NUMBER}"
    }

    stages {
        stage('Test') {
            when { expression { params.RUN_TESTS } }
            steps { echo 'running tests' }
        }
        stage('Push') {
            when {
                allOf {
                    expression { params.PUSH_IMAGE }
                    anyOf { branch 'main'; expression { params.ENV == 'prod' } }
                }
            }
            steps { echo "pushing tag ${env.TAG} to ${params.ENV}" }
        }
    }
}
⚠️The first-build gotcha Parameters don't exist until the job has been built once — params.RUN_TESTS is null on build #1, so when { expression { params.RUN_TESTS } } is skipped. Always provide defaults and write params.X ?: 'fallback'. After the first build the "Build Now" button becomes "Build with Parameters".

7.5 ✍️ Jenkinsfiles v7 — parameterized

groovynodejs-app/Jenkinsfile — v7
pipeline {
    agent any

    parameters {
        booleanParam name: 'RUN_TESTS', defaultValue: true,  description: 'Run Jest suite'
        choice       name: 'LOG_LEVEL', choices: ['info','debug'], description: 'Shell verbosity'
    }

    options { timestamps(); timeout(time: 20, unit: 'MINUTES') }

    environment {
        APP_NAME        = 'nodejs-app'
        npm_config_cache = '/var/lib/jenkins/.npm'
        TAG             = "${env.BUILD_NUMBER}-${env.GIT_COMMIT_SHORT ?: 'nogit'}"
    }

    stages {
        stage('Checkout') {
            steps {
                dir(APP_NAME) { checkout scmGit(branches: [[name: '*/main']],
                        extensions: [cleanBeforeCheckout()],
                        userRemoteConfigs: [[credentialsId: 'github-ssh',
                            url: 'git@github.com:<you>/jenkins-zero-to-hero.git']]) }
                script {
                    dir(APP_NAME) {
                        env.GIT_COMMIT_SHORT = sh(script:'git rev-parse --short HEAD', returnStdout:true).trim()
                    }
                    echo "Build ${env.BUILD_NUMBER} · commit ${env.GIT_COMMIT_SHORT} · ${params.LOG_LEVEL}"
                }
            }
        }
        stage('Build') { steps { dir(APP_NAME) { sh 'npm ci' } } }
        stage('Test')  {
            when { expression { params.RUN_TESTS } }
            steps { dir(APP_NAME) { sh 'npm run test:junit' } }
        }
    }

    post {
        always {
            dir(APP_NAME) { junit testResults: 'reports/junit.xml', allowEmptyResults: true }
            echo "Result: ${currentBuild.currentResult} · ${env.BUILD_URL}"
        }
    }
}

7.7 💬 Interview Q&A

Q1What's the difference between environment variables and parameters?
Environment variables are values the pipeline sets or inherits and that steps read (env.BUILD_NUMBER, REGISTRY). Parameters are inputs supplied by the user (or API trigger) before the build starts, read via params.X, and declared in a parameters block. Parameters become environment variables too, but only they show up in the "Build with Parameters" UI.
Q2How do you pass a value from one stage to the next?
Assign to env inside a script block: env.VERSION = sh(script:'…', returnStdout:true).trim(). Later stages read env.VERSION. Across agents I use stash/unstash or write a file, because the workspace isn't shared.
Q3Why would a parameterised stage be skipped on the first build?
Because params is empty until the job has run once and Jenkins has materialised the parameter definitions. I guard with defaults: params.X ?: 'fallback'.

7.8 Under the hood — the three scopes in practice

Variables resolve in a predictable order, and knowing it saves you from "my variable is empty":

textPrecedence (later wins)
1. Jenkins built-ins          (BUILD_NUMBER, JOB_NAME, WORKSPACE …)
2. Global properties          (Manage Jenkins -> System -> Global properties)
3. environment { }  at pipeline level
4. environment { }  at stage level      <- overrides pipeline-level
5. withEnv([...]) { }                   <- overrides everything for that block
6. inline shell:  VAR=x command         <- only that command
groovyPrecedence demo
pipeline {
    agent any
    environment { LOG = 'pipeline-level' }
    stages {
        stage('A') {
            environment { LOG = 'stage-level' }
            steps {
                echo "1: ${env.LOG}"                    // stage-level
                withEnv(['LOG=withEnv']) { echo "2: ${env.LOG}" }   // withEnv
                sh 'echo "3: $LOG"'                     // stage-level again
                sh 'LOG=inline; echo "4: $LOG"'         // inline
            }
        }
        stage('B') {
            steps { echo "5: ${env.LOG}" }              // pipeline-level
        }
    }
}
⚠️env.X vs X Inside sh, environment variables are shell variables ($LOG). In Groovy they're env.LOG or LOG — but plain LOG only works if Jenkins created it as a binding. Use env.LOG consistently; it is never ambiguous.

7.9 Parameter types in depth

groovyEvery parameter directive, with defaults and safe reads
parameters {
    string(name: 'VERSION',   defaultValue: '1.0.0',  description: 'Semver to release')
    text  (name: 'RELEASE_NOTES', defaultValue: '',   description: 'Markdown notes')
    booleanParam(name: 'RUN_E2E',  defaultValue: false, description: 'Run the e2e suite')
    choice(name: 'ENV', choices: ['dev','qa','prod'], description: 'Target environment')

}

environment {
    // Safe read pattern: params is empty on the very first build
    TARGET  = "${params.ENV ?: 'dev'}"
    E2E     = "${params.RUN_E2E != null ? params.RUN_E2E : false}"
}

7.11 Production notes

PracticeReason
Never put a secret in parametersValues are stored in plain text in build history and are visible to anyone with read access
Provide a default for every parameterAPI and upstream triggers may omit them
Use choice over free text for environmentsPrevents prod vs production typos reaching a deploy step
Log the effective configuration at the startecho "ENV=${params.ENV}" makes post-mortems trivial
Prefer the Active Choices plugin for dynamic listsFill choices from an API (e.g. list of available versions) instead of hard-coding

7.12 More interview Q&A

Q4Are parameters available as environment variables?
Yes — Jenkins exports parameters into the build environment, so params.ENV and env.ENV (and $ENV in shell) refer to the same value. The difference is that params is empty on the very first build before the definitions are materialised.
Q5How do you trigger a parameterised build from another pipeline?
build job: 'deploy', parameters: [string(name:'IMAGE_TAG', value: env.GIT_SHA)], wait: true, propagate: false — then inspect result.result and decide whether to fail, mark unstable or continue.
Q6How do you pass a computed value from stage 1 to stage 3?
Assign it to env inside a script block (env.VERSION = …). Later stages read env.VERSION. If the stages run on different agents I also stash the files, since the workspace isn't shared.
Q7How do you keep secrets out of parameters?
I never use password parameters for real secrets — they're persisted in the build record. Secrets live in the credentials store and are bound with withCredentials at the moment of use.
