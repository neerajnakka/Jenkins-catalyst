Block 18 · DevSecOps & scale

DevSecOps part 3 — image scanning, SBOM, signing & DAST

Goal: scan what you actually ship (the image), prove what's inside it (SBOM), sign it, and attack the running app (DAST). This completes the DevSecOps story end to end.

18.1 The full pipeline picture

18.2 Scanning the image (Trivy)

groovyImage vulnerability gate
stage('Scan image · Trivy') {
    agent { label 'docker' }
    steps {
        script {
            // 1. Always produce a readable report (never blocks)
            sh """
                trivy image --format table --output trivy-image.txt \
                            --severity HIGH,CRITICAL ${IMAGE}:${env.GIT_SHA} || true
            """

            // 2. Blocking gate: fail on high/critical that HAVE a fix available
            sh """
                trivy image --exit-code 1 \
                            --severity HIGH,CRITICAL \
                            --ignore-unfixed \
                            ${IMAGE}:${env.GIT_SHA}
            """

            // 3. Also fail on any misconfiguration in the Dockerfile
            sh "trivy config --exit-code 1 --severity HIGH,CRITICAL ${CONTEXT} || true"
        }
    }
    post {
        always {
            archiveArtifacts artifacts: 'trivy-image.txt', allowEmptyArchive: true
        }
    }
}
FlagWhy
--ignore-unfixedDon't fail on CVEs with no fix released yet — otherwise your pipeline is permanently red for things you cannot fix
--severity HIGH,CRITICALStart strict on the top two; add MEDIUM once the noise is manageable
--exit-code 1Turn the scan into a gate
trivy configScans Dockerfiles and IaC (Kubernetes YAML, Terraform) for misconfigurations

18.3 SBOM — prove what's inside

An SBOM (Software Bill of Materials) is a machine-readable inventory of everything in your image. When the next Log4Shell happens, you answer "are we affected?" in seconds instead of days.

groovyGenerate + attach an SBOM (Syft / CycloneDX)
stage('SBOM') {
    agent { label 'docker' }
    steps {
        sh """
            syft ${IMAGE}:${env.GIT_SHA} -o cyclonedx-json=sbom.cdx.json
            # or, with Trivy alone:
            trivy image --format cyclonedx --output sbom.cdx.json ${IMAGE}:${env.GIT_SHA}
        """
        archiveArtifacts artifacts: 'sbom.cdx.json', fingerprint: true
    }
}

stage('Sign image · cosign') {
    agent { label 'docker' }
    when { branch 'main' }
    steps {
        withCredentials([file(credentialsId: 'cosign-key', variable: 'COSIGN_KEY')]) {
            sh '''
                export COSIGN_PASSWORD=""
                cosign sign --key $COSIGN_KEY ${IMAGE}:${GIT_SHA}
            '''
        }
    }
}
🔐Verify on the other side Signing only matters if someone checks it. In Kubernetes: Kyverno or Sigstore policy-controller rejects any pod whose image isn't signed by your key. On a plain VM: cosign verify --key cosign.pub <image> before docker run.

18.4 DAST — attack the running app (OWASP ZAP)

groovyZAP baseline scan against the container we just built
stage('DAST · OWASP ZAP baseline') {
    agent { label 'docker' }
    steps {
        script {
            // 1. Run the app in a throwaway container
            sh "docker run -d --name app-${env.BUILD_NUMBER} -p 8099:3000 ${IMAGE}:${env.GIT_SHA}"

            // 2. Wait for it to be ready
            retry(10) { sleep 3; sh 'curl -fsS http://localhost:8099/health || exit 1' }

            // 3. Attack it with ZAP (docker image, no install needed)
            sh """
                mkdir -p zap-reports && chmod 777 zap-reports
                docker run --rm --network host \
                  -v \$(pwd)/zap-reports:/zap/wrk:rw \
                  ghcr.io/zaproxy/zaproxy:stable \
                  zap-baseline.py -t http://localhost:8099 \
                                  -g gen.conf \
                                  -r zap-report.html \
                                  -w zap-report.md \
                                  -J zap-report.json || true
            """
        }
    }
    post {
        always {
            sh "docker rm -f app-${env.BUILD_NUMBER} || true"
            archiveArtifacts artifacts: 'zap-reports/**', allowEmptyArchive: true
        }
    }
}
⚠️Start with zap-baseline.py, not the full scan The baseline scan is passive and takes ~1 minute — safe for every commit. A full active scan (zap-full-scan.py) can take 30+ minutes and can be destructive; run it nightly against a staging environment, never against production.

18.5 Should security stages block the build?

ScanTimingGate
Secrets (gitleaks)Every commit🔴 Block always
SAST quality gate (new code)Every commit🔴 Block
SCA high/critical with fixEvery commit🔴 Block
Image scan high/critical fixableEvery build🔴 Block before push
Image scan, unfixed / mediumEvery build🟡 Report
ZAP baselineEvery commit🟡 Report (block later)
ZAP full scanNightly🟡 Report to security team
Lint / styleEvery commit🟡 Unstable at most

18.6 ✅ Checklist

  • Trivy image scan runs and blocks on fixable HIGH/CRITICAL.
  • An SBOM (sbom.cdx.json) is generated and archived per build.
  • ZAP baseline produces a report against the running container.
  • I know which scans block and which only report — and why.

18.7 💬 Interview Q&A

Q1Walk me through your DevSecOps pipeline.
Source stage: SonarQube SAST with a quality gate on new code. Dependency stage: npm audit / pip-audit plus Trivy filesystem and gitleaks for secrets. Build stage: multi-stage image, non-root, then Trivy image scan gating on fixable high/critical, an SBOM with Syft, and cosign signing on main. Runtime stage: the container is started, smoke-tested, and scanned with the OWASP ZAP baseline. Reports are archived and trended; only high-confidence, fixable issues block.
Q2What is an SBOM and why would a company want one?
A machine-readable inventory of every component in an artifact (CycloneDX or SPDX). It turns "are we affected by this CVE?" from a week of investigation into a query, and it's increasingly a compliance requirement (US executive orders, EU CRA, supply-chain questionnaires).
Q3Why sign container images?
To guarantee provenance: a signed image proves it was built by our pipeline and hasn't been tampered with between build and runtime. With cosign plus an admission controller like Kyverno, the cluster simply refuses to run unsigned images.
Q4How do you handle a critical CVE in a base image with no patched version yet?
First check exploitability — is the vulnerable package even invoked? Then reduce attack surface (slim/distroless base, remove the package), add a runtime control (WAF, seccomp, network policy), and record a time-boxed suppression with `--ignore-unfixed` so the build is not permanently red. When the upstream fix lands, the suppression expires and the gate re-arms.
Q5DAST in CI — how do you keep it fast?
Use the ZAP baseline (passive, ~1 minute) on every commit against a container started just for the scan, and reserve the full active scan for a nightly job against staging. Keep the scanner on the same network as the app with --network host so there's no external latency.

18.8 Under the hood — what an image scanner inspects

Trivy does not guess from image metadata; it unpacks the layers and reads the package databases inside the filesystem:

Source inside the imageEcosystem detected
/lib/apk/db/installedAlpine (apk)
/var/lib/dpkg/statusDebian / Ubuntu (dpkg)
/var/lib/rpmRHEL / CentOS (rpm)
**/node_modules/**/package.jsonNode (npm / yarn / pnpm)
**/*.dist-info/METADATAPython (pip)
**/Gemfile.lockRuby
**/go.mod and Go binary build infoGo
💡Why distroless images produce almost no findings There is no package manager database, so OS-level CVEs mostly vanish — what remains is your application dependencies (Node or Python), which the scanner still sees. That is a genuine security win, not a scanner blind spot.

18.9 Trivy in depth

bashA production-grade scan command
trivy image \
  --severity HIGH,CRITICAL \          # only what matters
  --ignore-unfixed \                  # no fix exists -> track, don't block
  --exit-code 1 \                     # gate
  --scanners vuln,secret \            # CVEs + embedded secrets
  --format table \                    # readable in the console
  --output trivy-image.txt \
  user/nodejs-app:abc1234

# Machine-readable for dashboards and the GitHub Security tab:
trivy image --format sarif     --output trivy.sarif     user/nodejs-app:abc1234
trivy image --format cyclonedx --output sbom.cdx.json   user/nodejs-app:abc1234

# Cache the database on the agent so scans start instantly
trivy image --cache-dir /var/lib/jenkins/.cache/trivy ...
FlagMeaning
--ignore-unfixedSkip CVEs with no released fix
--exit-code 1Turn the scan into a gate
--scanners vuln,secret,misconfigChoose what to look for
--pkg-types os,libraryOS packages and/or application dependencies
--ignore-policy trivy.policyRego-based, expiry-aware suppressions
--cache-dirPersist the vulnerability DB between builds

18.10 Signing and verification end to end

bashcosign: generate keys, sign, verify
# 1. Generate a key pair ONCE (store the private key as a Jenkins credential)
cosign generate-key-pair                     # -> cosign.key, cosign.pub

# 2. Sign the image DIGEST (never sign a mutable tag)
cosign sign --key cosign.key user/nodejs-app@sha256:9f8e7d...

# 3. Verify anywhere before running
cosign verify --key cosign.pub user/nodejs-app:abc1234

# 4. Keyless signing with OIDC (no long-lived key at all -- preferred)
cosign sign user/nodejs-app@sha256:9f8e7d...
cosign verify user/nodejs-app:abc1234 \
  --certificate-identity ci@example.com \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
yamlKyverno policy — reject unsigned images in the cluster
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce
  rules:
    - name: require-signature
      match:
        any:
          - resources: { kinds: ["Pod"] }
      verifyImages:
        - imageReferences: ["docker.io/*"]
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
                      -----END PUBLIC KEY-----

18.11 Lab — scan a deliberately insecure image

🧪Lab 18.1 · Watch the gate fire
bashBuild something old and vulnerable, then scan it
mkdir -p /tmp/lab18 && cd /tmp/lab18
cat > Dockerfile <<'EOF'
FROM node:14-alpine          # EOL Node with many known CVEs
RUN apk add --no-cache curl bash
USER root                     # running as root -> misconfiguration finding
CMD ["node", "-e", "console.log('hi')"]
EOF
docker build -t lab18/old-app:1 .
trivy image --severity HIGH,CRITICAL lab18/old-app:1        # lots of findings
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 lab18/old-app:1
trivy config .                                              # flags USER root
Then repeat with FROM node:20-alpine and a non-root USER and watch the finding count collapse. That difference is the entire argument for multi-stage builds, current base images and non-root users.

18.12 DAST depth — what the ZAP baseline checks

CheckExample
Missing security headersContent-Security-Policy, X-Content-Type-Options, Strict-Transport-Security
Cookie flagsMissing Secure, HttpOnly, SameSite
Information disclosureStack traces, server version headers, directory listings
Insecure transportForms posting over HTTP, mixed content
Known vulnerable componentsOutdated JavaScript libraries (retire.js rules)
💡Two DAST practices that make it stick Run ZAP against a container started just for the scan (as in Block 18.4) so there is no shared state, and fail only on WARN severity or above once the baseline is clean — otherwise the first run floods you with informational noise and the team learns to ignore it.

18.13 More interview Q&A

Q6When should you scan: before or after pushing the image?
Scan before pushing so a vulnerable image never reaches the registry — that keeps the registry trustworthy and prevents accidental pulls. I still re-scan after push as a backstop, and schedule periodic rescans of stored images because new CVEs appear for images that were clean when built.
Q7Why rescan images that already passed?
Vulnerability databases change daily. An image that was clean in January can have a critical CVE in March without a single byte changing. Continuous rescanning of deployed digests is the only way to know your current exposure.
Q8What is a policy-as-code admission controller?
A Kubernetes component (Kyverno, OPA/Gatekeeper, Sigstore policy-controller) that evaluates rules before a pod is admitted — for example "image must be signed by our key", "no latest tags", "no privileged containers". It turns your pipeline's guarantees into enforced runtime policy.
Q9How do you convince management to invest in signing?
Frame it as supply-chain integrity: signing plus admission control means an attacker who compromises the registry or a developer laptop cannot get unsigned code into production. It is a small pipeline change that closes a whole class of attacks, and it is increasingly a compliance requirement.
Q10Which single security stage gives the best return?
Secret scanning with gitleaks — it takes seconds, has near-zero false positives, and prevents the most expensive incident class there is: a leaked credential. Then dependency scanning, because that is where the majority of real-world vulnerabilities live.
